# Proposal

## Why

`run_production.bat` запускает `FilePickerAPI.exe` через `start` и сразу пишет в журнал «started», не проверяя, что сервис жив и отвечает. Если exe падает при старте (`FILES_DIRECTORY` в `.env`, занятый порт 8000, любая другая ошибка), в журнале остаётся «started», а о проблеме узнают только тогда, когда фронтенд не может получить список файлов. При запуске из Планировщика заданий ошибка вообще не видна: скрипт всегда завершается с кодом 0 (issue #21).

## What Changes

- `run_production.bat` после `start` несколько раз с паузой запрашивает `http://127.0.0.1:8000/openapi.json` через `curl.exe` и пишет в журнал `%LOCALAPPDATA%\FilePickerAPI\startup.log` строку `started`, только когда сервис ответил.
- Если сервис не ответил, exe завершился сразу после старта, Windows не дал запустить exe (AppLocker, нет прав) или порт 8000 уже отвечает до запуска, в журнал пишется строка `FAILED` с причиной, в консоль выводится понятное сообщение, а скрипт завершается с ненулевым кодом выхода.
- Порт проверяется HTTP-запросом и до запуска, чтобы уже работающий экземпляр не дал ложного успеха (проверка процесса через `tasklist` его даёт). Уже запущенный, но ещё не отвечающий `FilePickerAPI.exe` тоже останавливает запуск: иначе его ответ позже приняли бы за ответ нового.
- При ошибке скрипт не ждёт нажатия клавиши бесконечно: вместо `pause` окно закрывается само через 30 секунд, а в неинтерактивном запуске (Планировщик) скрипт завершается без ожидания ввода.
- Если в системе нет `curl.exe` (до Windows 10 1803), проверить запуск нельзя: скрипт пишет `FAILED` и не запускает сервис.
- README описывает, как читать журнал и код выхода `run_production.bat`.

Контракт HTTP API не меняется: поля, коды ответов и тексты `detail` остаются прежними. `/openapi.json` уже отдаётся сервисом и используется только как проверка готовности.

Вне рамок изменения:
- `run_test.bat` (интерактивный запуск с выводом в консоль) не меняется.
- Схема `pushd`/`popd` и запуск exe по исходному UNC-пути не меняются.
- Скрипт не останавливает уже запущенный экземпляр и не перезапускает упавший.
- Скрипт не передаёт приложению путь к директории с файлами и не добавляет способов его задать: директория по-прежнему зашита в сборку.
- Порт и адрес сервиса не становятся настраиваемыми.

### Modified Capabilities
- `distribution`: требование «Скрипты запуска для Windows» — `run_production.bat` проверяет, что сервис ответил по HTTP, пишет в журнал `started` или `FAILED` с причиной, при ошибке завершается с ненулевым кодом и не зависает в неинтерактивном запуске.

## Impact

- `run_production.bat` — проверка запуска, новый формат строк в журнале, код выхода.
- `.gitattributes` — bat-файлы в рабочей копии (и значит в сборке) с CRLF: с LF `cmd.exe` ошибается в `goto` и метках.
- `README.md` — раздел о проверке запуска в `run_production.bat`.
- `.github/workflows/release.yml` — описание `run_production.bat` в тексте релиза.
- `openspec/specs/distribution/spec.md` — после архивации изменения.
- Новая зависимость скрипта — системный `curl.exe` (`%SystemRoot%\System32\curl.exe`, есть в Windows 10 1803+ и Windows Server 2019+, подписан Microsoft, поэтому не мешает WDAC/AppLocker). Python-код и зависимости приложения не меняются.
