Веб-сервер на базе FastAPI для просмотра списка и загрузки файлов из настроенной директории.

## Возможности

- 🚀 Быстрый и легковесный API на базе FastAPI
- 📁 Просмотр списка файлов из настроенной директории
- ⬇️ Загрузка отдельных файлов
- 🔒 Безопасность: защита от атак обхода директорий
- 🌐 CORS включен для интеграции с фронтендом
- 🪟 Автоматическая сборка Windows исполняемого файла и установщика MSI через GitHub Actions
- 👤 Запуск при входе пользователя от его имени, журнал в файле и в журнале событий Windows

## API Endpoints

### `GET /files`
Получить список всех файлов в настроенной директории, отфильтрованных по размеру и формату.

Только файлы формата .txt возвращаются в ответе. Файлы разделяются на две категории:
- **availableFiles** - файлы формата .txt размером меньше 10 МБ (доступные для импорта)
- **unavailableFiles** - файлы формата .txt размером 10 МБ и больше (не доступные для импорта)

Файлы других форматов полностью игнорируются и не возвращаются в ответе.

Файлы в каждом списке отсортированы по `createdAt` в порядке убывания (новые файлы первыми). `createdAt` — время создания файла; на Linux, где ОС его не отдаёт, — время последнего изменения.

**Ответ:**
```json
{
  "availableFiles": [
    {
      "id": "example.txt",
      "name": "example.txt",
      "size": 1024,
      "createdAt": "2025-12-15T10:30:29.150000Z"
    }
  ],
  "unavailableFiles": [
    {
      "id": "large_file.txt",
      "name": "large_file.txt",
      "size": 15728640,
      "createdAt": "2025-12-15T10:30:29.100000Z"
    }
  ]
}
```

**Ошибки:**

| Код | `detail` | Когда |
|---|---|---|
| 404 | `Files directory not found` | директории нет или сетевая папка недоступна («сетевой путь не найден») |
| 400 | `Files path is not a directory` | настроенный путь указывает на файл |
| 403 | `Permission denied when reading directory: <текст ошибки>` | у учётной записи сервиса нет прав на чтение |
| 500 | `OS error when reading directory: <текст ошибки>` | прочие ошибки ввода-вывода (сбой сети, диска) |
| 500 | `Unexpected error when reading directory: <текст ошибки>` | любая другая ошибка |

Текст ошибки ОС с путём к папке попадает в `detail` намеренно, для диагностики: клиент здесь ничего не передаёт и не может так исследовать файловую систему.

### `GET /files/{fileId}`
Скачать определенный файл по его ID.

**Параметры:**
- `fileId` - ID файла для загрузки (имя файла)

**Ответ:** Загрузка файла (application/octet-stream)

**Ошибки:**

| Код | `detail` | Когда |
|---|---|---|
| 400 | `Invalid filename` | `fileId` — не имя файла (путь, UNC-путь, `..`, имя устройства Windows и т.п.), ОС отвергает имя, файл — символическая ссылка на Windows или лежит не прямо в директории |
| 400 | `Path is not a file` | `fileId` указывает на директорию |
| 403 | `File is not available for download` | файл не `.txt` или не меньше 10 МиБ |
| 403 | `Permission denied when reading file` | нет прав на файл |
| 404 | `File not found` | файла нет или сетевая папка недоступна |
| 500 | `OS error when reading file` | прочие ошибки ввода-вывода, в том числе сбой самой директории |

Здесь текст ошибки ОС клиенту не отдаётся (в нём путь к сетевой папке), он пишется в лог сервиса.

## Установка

### Запуск из исходного кода

1. Клонируйте репозиторий:
```bash
git clone https://github.com/Olegt0rr/FilePickerAPI.git
cd FilePickerAPI
```

2. Установите зависимости:
```bash
pip install -e .
```

3. Запустите приложение:
```bash
python -m app
```

API будет доступен по адресу `http://localhost:8000`

**💡 Совет:** Откройте `http://localhost:8000/docs` в браузере для доступа к интерактивной документации Swagger UI

### Установка на Windows (MSI)

Основной способ поставки — пакет `FilePickerAPI-<код филиала>.msi` из [Releases](../../releases/latest). Для каждого филиала собран свой пакет: директория с файлами зашита в сборку (см. [Сборка под филиалы](#сборка-под-филиалы)). Пакет и все `exe`/`dll`/`pyd` в нём подписаны.

#### Установка

MSI ставится на машину целиком и требует прав администратора:

- **вручную** — двойной щелчок по MSI;
- **без вопросов** — `msiexec /i FilePickerAPI-<код филиала>.msi /qn /norestart` (код выхода 0 — установлено, 3010 — установлено, но для завершения нужна перезагрузка);
- **на много машин** — через GPO (назначение пакета компьютеру) или SCCM.

Что делает пакет:

- кладёт сборку (без bat-скриптов) в `C:\Program Files\FilePickerAPI\`; другую папку установки задать нельзя;
- добавляет значение `FilePickerAPI` в `HKLM\Software\Microsoft\Windows\CurrentVersion\Run` с путём к `FilePickerAPI.exe` без аргументов: сервис запускается при входе **любого** пользователя машины;
- регистрирует источник `FilePickerAPI` в журнале Windows «Приложение» и файл сообщений `FilePickerAPI.messages.dll`, чтобы события читались в Event Viewer.

Продукт виден в «Программах и компонентах» как `File Picker API (филиал <код>)`. Пользовательских действий в пакете нет, сразу после установки сервис не запускается: он стартует при следующем входе пользователя. Чтобы не выходить из системы, пользователь может запустить `C:\Program Files\FilePickerAPI\FilePickerAPI.exe` сам.

#### Запуск при входе и учётная запись

Сервис запускается при входе пользователя **от его имени**, без окна, и работает, пока пользователь в системе. К сетевой папке филиала он обращается с учётными данными этого пользователя, поэтому право на чтение ресурса и папки нужно пользователю (или его группе). Служба Windows, учётная запись компьютера и сохранённые пароли не используются. Подробнее — в [Работа с сетевой папкой](#работа-с-сетевой-папкой).

Explorer запускает программы из `Run` с небольшой задержкой после входа. Если групповая политика «Не обрабатывать список автозапуска для старых версий» (`DisableLocalMachineRun`) включена, Explorer не запускает программы из `HKLM\…\Run` вовсе: MSI ставится с кодом 0, а сервис при входе не запускается и событий не пишет. Проверить политику можно отчётом `gpresult /h gpresult.html` (раздел «Административные шаблоны → Система → Вход в систему») или в реестре:

```cmd
reg query HKLM\Software\Microsoft\Windows\CurrentVersion\Policies\Explorer /v DisableLocalMachineRun
```

Значение `1` — политика включена, автозапуск из `HKLM\…\Run` отключён. Та же политика есть и в конфигурации пользователя: проверьте и `HKCU\Software\Microsoft\Windows\CurrentVersion\Policies\Explorer` (`reg query` под учётной записью пользователя). Её выключение — решение администраторов домена.

#### Несколько пользователей на машине

Второму пользователю свой экземпляр не нужен: сервис на порту 8000 уже работает у первого, и фронтенд второго получает файлы через него (с правами первого пользователя на сетевую папку). Экземпляр второго пользователя завершается с кодом 0 и пишет событие:

- **1005** (сведения) — сервис уже работает в другом процессе: в тексте PID владельца порта 8000 и его версия;
- **1006** (предупреждение) — порт 8000 занят File Picker API другой версии (например, после обновления у одного из пользователей).

По PID из события администратор найдёт процесс, который держит порт (в диспетчере задач или `Get-Process -Id <PID>`). Если первый пользователь выходит из системы, сервис останавливается вместе с его сеансом и не поднимается у второго, пока тот не войдёт заново или не запустит `FilePickerAPI.exe` сам.

#### Настройки

Единственная настройка — `CORS_ORIGINS` (см. [CORS Origins](#cors-origins)) — задаётся в файле `.env` в `C:\Program Files\FilePickerAPI\`. Файл создаёт администратор; обновление MSI его сохраняет. Директорию с файлами задать нельзя ни там, ни иначе (см. [Директория с файлами](#директория-с-файлами)).

#### Обновление

Обновление — установка MSI новой версии поверх прежней тем же способом, что и установка. `.env` остаётся на месте. Что происходит с работающим сервисом, зависит от того, кто ставит пакет:

- **Сам пользователь** (с повышением прав) — Windows Installer мягко останавливает сервис (событие 1001 с причиной «обновление или удаление программы»), и после установки он перезапускается новой версией от того же пользователя.
- **Администратор под своей учётной записью** в сеансе оператора — сервис мягко останавливается (1001) и **не работает, пока оператор не запустит `FilePickerAPI.exe` сам или не войдёт в систему заново**. От имени администратора сервис не запускается.
- **SCCM или GPO от SYSTEM** — работающий сервис не останавливается: старая версия обслуживает запросы до выхода пользователя, новая запускается при следующем входе. При коде 3010 замена файлов может быть отложена до перезагрузки. Поэтому обновления лучше ставить вне рабочего времени.

Код выхода `msiexec` 0 или 3010 означает, что продукт обновлён.

#### Откат и смена филиала

MSI той же или более старой версии поверх установленного не ставится: установка отказывает с сообщением, установленная версия остаётся. Чтобы откатить версию или сменить филиал при той же версии, удалите продукт и установите нужный MSI из релиза. `.env` при этом сохраняется. Файл сообщений остаётся от новейшей версии: коды событий только добавляются, поэтому события читаются полностью.

#### Удаление

«Программы и компоненты» или `msiexec /x FilePickerAPI-<код филиала>.msi /qn /norestart` (код 0 или 3010). Удаляются файлы сборки и значение `Run`: при следующем входе сервис не запускается. Источник `FilePickerAPI` и `FilePickerAPI.messages.dll` намеренно остаются, чтобы прошлые события читались в Event Viewer и после удаления. `.env` и файлы журнала пользователей тоже остаются.

#### Журнал

Сервис пишет журнал в файл `%LOCALAPPDATA%\FilePickerAPI\logs\FilePickerAPI.log` пользователя, от имени которого запущен: запуск и остановка, предупреждения и ошибки, HTTP-запросы и смена состояния сетевой папки. Файл переименовывается с датой в полночь, архивы старше 30 дней удаляются.

Предупреждения, ошибки, запуск и остановка дублируются в журнал Windows «Приложение» с источником `FilePickerAPI` (только при установке MSI: источник регистрирует пакет):

| Код | Уровень | Событие |
|---|---|---|
| 1000 | Сведения | сервис запущен: версия, филиал, директория, пользователь, способ запуска |
| 1001 | Сведения | сервис остановлен, с причиной (Ctrl+C, выход пользователя, обновление или удаление программы, выключение Windows) |
| 1002 | Ошибка | сервис не запустился или HTTP-сервер завершился с ошибкой |
| 1003 | Предупреждение | в папку сборки может писать не только администратор |
| 1004 | Предупреждение | не удаётся вести файл журнала |
| 1005 | Сведения | сервис уже работает в другом процессе, этот запуск завершён |
| 1006 | Предупреждение | порт 8000 занят File Picker API другой версии |
| 2000, 2002 | Предупреждение | сетевая папка недоступна, по-прежнему недоступна (раз в час) |
| 2001 | Сведения | сетевая папка снова доступна |
| 2003 | Предупреждение | запрос к папке шёл дольше 10 секунд |
| 2004 | Предупреждение | папку не удалось создать при запуске |
| 3000 | Предупреждение | ошибка доступа к файлу при скачивании |
| 3001 | Предупреждение | прочее предупреждение (например, от Uvicorn о некорректных HTTP-запросах) |
| 4000 | Ошибка | непредвиденная ошибка запроса |

В текстах ошибок ОС есть путь, код ошибки Windows и её описание. Повторяющиеся ошибки не засоряют журнал событий: одинаковые повторы сводятся в напоминание раз в час с их числом, а в файле журнала остаются все.

В Event Viewer: «Журналы Windows» → «Приложение» → «Фильтр текущего журнала…» → «Источники событий»: `FilePickerAPI`; в поле кодов можно указать, например, `2000-2004` (сетевая папка) или `1000-1006` (запуск и остановка). То же в PowerShell:

```powershell
Get-WinEvent -FilterHashtable @{ LogName = 'Application'; ProviderName = 'FilePickerAPI'; Id = 2000, 2002 } -MaxEvents 20 |
  Format-List TimeCreated, Id, LevelDisplayName, Message
```

#### Разбор ошибок запуска

Если сервис не отвечает, сначала посмотрите события 1002 и 1003 и файл журнала. Чтобы увидеть журнал в консоли, запустите exe из `cmd` через `start /wait`: `FilePickerAPI.exe` — программа без своего окна, и без `start /wait` `cmd` не ждёт её, и вывод перемешивается с вводом.

```cmd
cd /d "C:\Program Files\FilePickerAPI"
start /wait FilePickerAPI.exe
```

Журнал выводится в это окно, Ctrl+C останавливает сервис. Если сервис уже работает (у этого или другого пользователя), запуск сразу завершится с событием 1005 — сначала остановите работающий экземпляр. `FilePickerAPI.exe` не принимает аргументов: с любыми аргументами он выводит подсказку и завершается с кодом 2.

#### Брандмауэр

Сервис принимает запросы на всех интерфейсах на порту 8000. Если фронтенд обращается к нему с других машин, входящее правило брандмауэра создаёт администратор (у пользователя нет прав разрешить доступ в запросе Windows), например командой PowerShell от администратора или такой же настройкой через GPO:

```powershell
New-NetFirewallRule -DisplayName 'File Picker API' -Direction Inbound -Action Allow `
  -Program 'C:\Program Files\FilePickerAPI\FilePickerAPI.exe' -Protocol TCP -LocalPort 8000
```

#### Перевод филиала с `run_production.bat`

Филиалы переводятся по одному, в удобное время: до перевода новая сборка из архива работает с прежними bat-скриптами. На каждой машине:

1. Пользователь закрывает прежний сервис и удаляет свою задачу Планировщика или ярлык с `run_production.bat`, если они есть. Иначе при входе запустятся оба способа: второй экземпляр тихо завершится, а `run_production.bat` запишет `FAILED` в `startup.log`.
2. Администратор ставит `FilePickerAPI-<код филиала>.msi`. Если рядом с прежним exe лежал `.env` с `CORS_ORIGINS`, его нужно положить в `C:\Program Files\FilePickerAPI\`.
3. Со следующего входа сервис запускается сам; сразу — запуском `C:\Program Files\FilePickerAPI\FilePickerAPI.exe`. Права на сетевую папку менять не нужно, если сервис и раньше работал от имени этого пользователя.

Вернуться к bat-скриптам можно удалением продукта и прежней задачей или ярлыком с `run_production.bat` из архива.

### Архив и bat-скрипты (до перевода филиала на MSI)

Пока филиал не переведён на MSI, сборку можно запускать по-старому:

1. Скачайте из [Releases](../../releases/latest) архив своего филиала `FilePickerAPI-<код филиала>.zip`
2. Распакуйте архив в папку, куда у пользователей нет прав на запись (например, `C:\Program Files\FilePickerAPI`)
3. Запустите `run_production.bat` или `run_test.bat` из этой папки

Без MSI источник событий не зарегистрирован, и журнал пишется только в файл. Сборки из последних запусков CI также доступны как артефакты [GitHub Actions workflow runs](../../actions).

#### Скрипты запуска

- **`run_test.bat`** — запускает сервис в текущем окне консоли, ошибки запуска видны сразу. Используйте его, чтобы разобраться, почему сервис не стартует.
- **`run_production.bat`** — запускает сервис в фоне и проверяет, что он действительно отвечает. Своего окна exe не открывает, но присоединяется к консоли bat-файла (журнал идёт в неё): пока сервис работает, это окно остаётся открытым, и его закрытие останавливает сервис (событие 1001). Без консоли сервис запускает MSI (при входе пользователя). Подходит для ручного запуска и для Планировщика заданий, работает и из сетевой папки (UNC-путь).

После запуска `run_production.bat` до 30 раз с паузой 2 секунды опрашивает `http://127.0.0.1:8000/openapi.json` (если сервис так и не ответил, ожидание занимает 1–2 минуты) и дописывает итог в `%LOCALAPPDATA%\FilePickerAPI\startup.log`:
- `FilePickerAPI started in daemon mode at <дата> <время>` — сервис ответил, код выхода 0;
- `FilePickerAPI FAILED to start at <дата> <время>: <причина>` — сервис не запустился, код выхода 1. Причины: exe завершился при старте (например, из-за `FILES_DIRECTORY` в `.env`, см. «Директория с файлами», или потому что порт 8000 занят программой, которая не отвечает по HTTP), порт 8000 уже отвечает по HTTP (например, уже работающий экземпляр — второй не запускается), `FilePickerAPI.exe` уже запущен, но ещё не отвечает (остановите его в диспетчере задач или дождитесь ответа), Windows не дал запустить exe (например, его блокирует AppLocker), сервис не ответил за время ожидания (процесс при этом не останавливается, и пока его не завершить, следующий запуск будет сообщать, что exe уже запущен), рядом нет `FilePickerAPI.exe` или в системе нет `curl.exe`.

В Планировщике заданий результат виден в столбце «Результат последнего запуска»: `0x0` — сервис запущен, `0x1` — ошибка, причина в `startup.log`. Задание должно выполняться от имени пользователя, у которого есть права на сетевую папку (см. [Работа с сетевой папкой](#работа-с-сетевой-папкой)); журнал пишется в его профиль. При ошибке скрипт не ждёт нажатия клавиши: окно закрывается само через 30 секунд.

Для проверки запуска нужен системный `curl.exe` (Windows 10 версии 1803 и новее, Windows Server 2019 и новее). Скрипты не принимают параметров и не меняют директорию с файлами.

## Конфигурация

### Директория с файлами

Директория с файлами **зашивается в сборку** и не настраивается пользователем. Для каждого филиала собирается своя сборка со своим путём (см. [Сборка под филиалы](#сборка-под-филиалы)). При запуске из исходного кода, без шага `configure`, приложение обслуживает файлы из директории `./files`.

**Требование:** пользователь не должен иметь возможности подменить директорию, из которой API отдаёт файлы. Поэтому:

- путь объявлен как `ClassVar`, а не как поле настроек, и не читается из переменных окружения;
- переменная окружения `FILES_DIRECTORY` игнорируется;
- если в `.env` указан `FILES_DIRECTORY`, приложение не запускается (ошибка валидации), а не переключается на другую директорию;
- `FilePickerAPI.exe` не принимает аргументов (с любыми аргументами — код 2 без запуска), значение `Run` содержит только путь к exe, а у MSI нет свойств, задающих путь или папку установки.

Это поведение закреплено тестами (`TestFilesDirectoryIsFixed`). Изменить директорию можно только правкой `branches.toml` и новой сборкой (см. `openspec/specs/service-configuration/spec.md`).

### Сборка под филиалы

Список филиалов и их путей хранится в [`branches.toml`](branches.toml):

```toml
[[branch]]
name = "5400"
files_directory = '\\localmq.neadru.local\Payments\5400\CENTER\RSB'
```

CI собирает отдельную сборку под каждый филиал из этого файла из одной и той же кодовой базы. Чтобы добавить филиал, допишите новый блок `[[branch]]` и сделайте коммит. Строку пути пишите в одинарных кавычках: тогда обратные слэши указываются как есть, без экранирования. Путь должен быть абсолютным (UNC `\\сервер\...` или с буквой диска), а коды филиалов — уникальными без учёта регистра; иначе CI не запустит сборку. Для сетевой папки указывайте только UNC-путь: буква подключённого сетевого диска (`Z:\...`) существует лишь в сеансе пользователя, который его подключил, и не видна задаче Планировщика (см. [Работа с сетевой папкой](#работа-с-сетевой-папкой)). Букву диска используйте только для локального диска.

Перед сборкой `scripts/branches.py configure <код филиала>` записывает путь в `app/_build_config.py` (файл не хранится в git), и Nuitka компилирует его в exe.

### Работа с сетевой папкой

В филиалах сервис отдаёт файлы из сетевой папки по UNC-пути (`\\сервер\ресурс\...`). Что нужно учитывать при установке и эксплуатации:

**Учётная запись и права.** Доступ к сетевой папке с платёжками есть только у учётных записей пользователей. Сервис работает от имени пользователя, который вошёл в систему (MSI запускает его при входе), и обращается к папке с его учётными данными: право на чтение ресурса и папки нужно этому пользователю (или его группе). Служба Windows, задача Планировщика от имени SYSTEM, права для учётной записи компьютера, группы компьютеров или gMSA и сохранённый пароль пользователя не используются. Без прав `GET /files` отвечает 403, в журнал событий пишется 2000 с кодом ошибки Windows 5, а имя пользователя видно в событии запуска 1000.

**Только UNC-путь.** Подключённый сетевой диск (`Z:`) существует только в том сеансе, где его подключили, и может быть ещё не подключён, когда сервис запускается при входе; тогда сервис ответит 404. Поэтому в `branches.toml` для сетевой папки указывается UNC-путь.

**Создание папки при запуске.** При старте сервис создаёт обслуживаемую директорию вместе с недостающими родительскими, если у пользователя есть права на запись. При опечатке в пути на ресурсе появится пустая папка, а список файлов будет пустым — проверяйте путь в `branches.toml`. Если создать папку не удалось (ресурс недоступен, нет прав), сервис всё равно запускается и пишет предупреждение в журнал (событие 2004).

**Недоступная папка.** Пока сетевая папка недоступна, `GET /files` отвечает 404 (`Files directory not found`), 403 или 500, а скачивание — 404 или 500 (см. коды ошибок в [API Endpoints](#api-endpoints)). Когда папка снова становится доступна, сервис работает дальше без перезапуска. Если папка пропала, пока сервис читал список, ответ — 404, а не пустой список. В журнал событий пишется 2000 при первой ошибке и при смене причины (с UNC-путём, кодом ошибки Windows и его описанием), 2002 раз в час с числом ошибочных ответов, пока папка недоступна, и 2001 с длительностью недоступности, когда она снова доступна. Состояние папки сервис определяет только по запросам, которые и так выполняет: отдельных проверок папки нет.

**DFS и число обращений.** На Windows сервис обращается к файлу прямо по UNC-пути из сборки и не разрешает путь сам: скачивание делает два обращения к сетевой папке — за атрибутами файла и за его настоящим именем (плюс чтение содержимого), а переключение DFS на другой сервер обрабатывает SMB-клиент Windows. Настоящее имя ищется в директории, и для этого нужно право просмотра её содержимого. Если у учётной записи есть только чтение файлов, имя, которое по форме не может быть коротким именем 8.3 (длиннее 8 символов до точки или 3 после, с пробелами и т. п.), используется как есть: обойти им проверку расширения нельзя. Для имени в форме 8.3 (в том числе без `~`: короткое имя можно назначить вручную) сервис открывает файл для чтения атрибутов без перехода по ссылкам и запрашивает его настоящее имя. Если это не удаётся (например, нет доступа к родительской папке на сервере), ответ — 403.

**Зависшая папка.** У обращений к сетевой папке нет собственного таймаута: их длительность определяет SMB-клиент Windows. Запросы выполняются в пуле потоков (по умолчанию 40 потоков), поэтому медленная папка не блокирует остальные запросы, но если папка «повисла» и все потоки ждут её ответа, сервис перестаёт отвечать, пока Windows не прервёт обращения. Запрос к папке дольше 10 секунд даёт событие 2003 с маршрутом и длительностью.

**Безопасность.** Ни запрос, ни символическая ссылка в папке не заставят сервис подключиться к чужому хосту — только к серверам, через которые Windows обслуживает саму настроенную папку (сервер ресурса, цели DFS): `fileId` проверяется до любого обращения к файловой системе, а символическим ссылкам на Windows сервис не следует. Иначе ссылка или `fileId` вида `\\host\share\x.txt` заставили бы сервис подключиться к чужому хосту и отдать ему NTLM-хеш своей учётной записи (см. [Безопасность](#безопасность)). Остаётся узкое окно: если файл подменят ссылкой между проверкой и открытием, ОС при открытии пойдёт по ссылке; для этого нужно право записи в папку.

**Дата создания.** `createdAt` для файла в сетевой папке — время создания, которое отдаёт файловый сервер: время появления файла на ресурсе или время, сохранённое при копировании (например, robocopy), а не время на машине сервиса.

### CORS Origins

По умолчанию CORS включен для всех источников (`*`). Для производственного использования следует ограничить это определенными доменами, установив переменную окружения `CORS_ORIGINS` со списком источников через запятую:

**Linux/Mac:**
```bash
export CORS_ORIGINS="http://localhost:3000,https://yourdomain.com"
python -m app
```

**Windows (установка MSI):** сервис запускается при входе пользователя, поэтому список задаётся в файле `.env` в `C:\Program Files\FilePickerAPI\` (exe читает `.env` из своей папки, откуда бы его ни запустили). Файл создаёт администратор, обновление MSI его сохраняет:
```ini
CORS_ORIGINS=http://localhost:3000,https://yourdomain.com
```

Кроме `CORS_ORIGINS`, в `.env` ничего не настраивается; с `FILES_DIRECTORY` в `.env` сервис не запускается (см. [Директория с файлами](#директория-с-файлами)).

Передача учётных данных (куки, HTTP-аутентификация) разрешается только для явного списка источников. При `*` ответ содержит `Access-Control-Allow-Origin: *` без `Access-Control-Allow-Credentials`.

### Спецификации (OpenSpec)

Поведение сервиса описано в формате [OpenSpec](https://github.com/Fission-AI/OpenSpec) в директории `openspec/`:
- `openspec/config.yaml` — контекст проекта (стек, соглашения, проверки) для AI-ассистентов
- `openspec/specs/` — текущие требования по возможностям: `file-listing`, `file-download`, `service-configuration`, `api-documentation`, `distribution`
- `openspec/changes/` — предложения изменений, которые ещё не внесены в спецификации

Изменения поведения начинаются с предложения (`/opsx:propose` в Claude Code или `openspec new change`), а после реализации архивируются (`openspec archive`), обновляя `openspec/specs/`.

Версия openspec закреплена в `.github/openspec/package-lock.json` — той же версией проверяет CI. Установите её и запускайте из корня репозитория:

```bash
npm ci --prefix .github/openspec
npm exec --prefix .github/openspec -- openspec list --specs
npm exec --prefix .github/openspec -- openspec validate --all --strict
```

Ту же проверку (`--all`: спецификации и незаархивированные изменения) выполняет CI в workflow Docs. Если openspec установлен глобально (нужен для `/opsx:*` в Claude Code), держите его версию такой же: `npm install -g @fission-ai/openspec@<версия из package.json>`.

### Локальная сборка исполняемого файла

Сборка выполняется [Nuitka](https://nuitka.net/): код компилируется в C, а затем в нативный бинарник. Нужен компилятор C (на Windows — MSVC из Visual Studio Build Tools).

```powershell
pip install -e .[build]
# Зашить путь нужного филиала из branches.toml (создаёт app/_build_config.py)
python scripts/branches.py configure 5400
python -m nuitka --mode=standalone --msvc=latest --assume-yes-for-downloads --remove-output `
  --output-dir=build --output-folder-name=FilePickerAPI `
  --output-filename=FilePickerAPI.exe `
  --include-package=app --include-module=app._build_config `
  --include-package=uvicorn `
  app/__main__.py
```

Результат — папка `build/FilePickerAPI.dist/` с `FilePickerAPI.exe` и его зависимостями. Используется режим standalone (папка), а не onefile: onefile при запуске распаковывает неподписанные файлы во временную папку пользователя, что несовместимо с подписью и WDAC/AppLocker.

### Подпись кода

Бинарники подписываются только при релизе, в отдельном джобе `sign` воркфлоу `release.yml`. Подписываются все `exe`/`dll`/`pyd` сборки сертификатом Authenticode; уже подписанные сторонние файлы (например, `python311.dll`) не трогаются. MSI собирается из уже подписанных файлов в джобе `msi` без сертификата и подписывается тем же скриптом в джобе `sign-msi`. Обычные сборки из push и PR остаются неподписанными (MSI для дымовой проверки подписывается одноразовым сертификатом и в артефакт не попадает).

Сертификат хранится в секретах GitHub Environment `code-signing` (не в секретах репозитория):

- `WINDOWS_SIGNING_CERT_PFX_BASE64` — PFX-файл сертификата подписи кода в base64 (`[Convert]::ToBase64String([IO.File]::ReadAllBytes("cert.pfx"))`)
- `WINDOWS_SIGNING_CERT_PASSWORD` — пароль от PFX

Настройка окружения (Settings → Environments → `code-signing`):

1. **Deployment branches and tags** → *Selected branches and tags* → добавить правило для тегов `v*`. Без этого любая ветка или PR с изменённым воркфлоу сможет получить сертификат и подписать произвольный код.
2. Создавать теги `v*` должны только доверенные люди: Settings → Rules → Rulesets, правило для тегов `v*` с ограничением на создание.
3. По желанию — *Required reviewers*: подпись релиза потребует ручного подтверждения.

Без секретов в окружении релиз падает: неподписанный релиз не публикуется.

Подпись сама по себе не мешает запустить изменённый файл: она только позволяет это обнаружить. Чтобы подменённый или пропатченный бинарник не запускался, на рабочих местах нужно включить WDAC или AppLocker с правилом «разрешить только файлы, подписанные нашим сертификатом» (через доменную GPO), а пользователи не должны быть локальными администраторами. В политике также нужно разрешить издателей Microsoft и Python Software Foundation: их подписи остаются на `vcruntime*.dll`, `python311.dll` и других сторонних файлах сборки. Если в AppLocker включены правила для Windows Installer, разрешите MSI по издателю (нашему сертификату). Bat-файлы подписать нельзя, поэтому до перевода филиала на MSI при правилах AppLocker для скриптов разрешите `run_*.bat` правилом по пути к папке установки.

## GitHub Actions

Репозиторий включает несколько workflow GitHub Actions:

### Build and Test (`.github/workflows/build-exe.yml`)

Автоматически:
- Запускает набор тестов на Ubuntu и на Windows (на Windows — в том числе проверки UNC-путей, недопустимых имён файлов и символических ссылок)
- Параллельно с тестами собирает Windows-версию через Nuitka отдельно под каждый филиал из `branches.toml`
- Загружает отчеты о покрытии тестами
- На одном филиале проверяет установку на раннере: собирает MSI (WiX, версия закреплена в `.config/dotnet-tools.json`) из копий сборки, подписанных одноразовым сертификатом, и прогоняет дымовую проверку `.github/scripts/msi-smoke.ps1` — установка, запуск, события в журнале Windows, обновление, откат и удаление
- Загружает папку сборки каждого филиала как артефакт `FilePickerAPI-<код филиала>` (без MSI: в релиз идёт MSI, собранный из подписанной сборки) — только если прошли тесты и сборки всех филиалов. Кроме того, каждая сборка один день лежит во временном артефакте `untested-FilePickerAPI-<код филиала>`: его не скачивайте, тесты для него могли не пройти. Перезапустить только упавшие джобы можно, пока временные артефакты не истекли; позже нужен перезапуск всех джобов
- Проверяет скрипт подписи (`.github/scripts/sign.ps1`) на этих сборках с одноразовым самоподписанным сертификатом — боевой сертификат здесь не используется

Триггеры workflow:
- Push в ветку main/master (кроме изменений только в документации)
- Pull request в ветку main/master (кроме изменений только в документации)
- Ручной запуск workflow

Если в push или PR изменена только документация (`*.md`, `openspec/`, `.claude/`, `.github/openspec/`), workflow не запускается: код и сборка от неё не меняются. Если вместе с ней изменён любой другой файл, workflow запускается целиком. Так же устроен Dependency Audit, а вместо них запускается лёгкая проверка Docs.

Артефакты:
- Сборка для Windows: хранится 30 дней
- Отчет о покрытии: хранится 7 дней

### Dependency Audit (`.github/workflows/audit.yml`)

Проверяет зависимости на известные уязвимости через [pip-audit](https://github.com/pypa/pip-audit):
- Ставит проект со всеми extras (`dev`, `build`, `audit`) на Windows, как для сборки, и проверяет каждый установленный пакет по базе PyPI Advisory
- Падает, если у какого-либо пакета есть известная уязвимость или пакет не удалось проверить; в логе — идентификаторы (CVE, GHSA) и версии с исправлением
- Вызывается из Release: релиз с известной уязвимостью не подписывается и не публикуется

Триггеры workflow:
- Push в ветку main/master (кроме изменений только в документации)
- Pull request в ветку main/master (кроме изменений только в документации)
- Ежедневно по расписанию (новые CVE выходят без коммитов в репозиторий)
- Ручной запуск workflow

Если проверка упала, обновите уязвимый пакет в `pyproject.toml` (транзитивную зависимость закрепите явно, как `starlette`). Пропускать уязвимость через `--ignore-vuln` можно только с комментарием-причиной в workflow.

### Docs (`.github/workflows/docs.yml`)

Лёгкая проверка для изменений документации: на Ubuntu, без зависимостей проекта и сборки, проверяет спецификации и незаархивированные изменения OpenSpec командой `openspec validate --all --strict`. Версии Node и openspec закреплены: openspec со всеми зависимостями — в `.github/openspec/package-lock.json`, его обновляет Dependabot. Эти npm-пакеты проверяет на уязвимости (`npm audit`) отдельный джоб `npm-audit` раз в три дня, при ручном запуске и в push/PR, которые меняют `.github/openspec/` (в том числе PR Dependabot). Проверку спецификаций и релиз он не блокирует: в exe эти пакеты не попадают. Списки путей в трёх workflow сверяет тест `tests/test_workflows.py`.

Триггеры workflow:
- Push и pull request в ветку main/master, если изменены `*.md`, `openspec/`, `.claude/`, `.github/openspec/` или сам `docs.yml`
- Раз в три дня по расписанию — только джоб `npm-audit` (новые уязвимости в npm-пакетах)

О падении планового запуска (здесь и в Dependency Audit) GitHub пишет только тому, кто последним менял `cron` в workflow, а через 60 дней без активности в репозитории отключает расписание. Поэтому за падениями следите во вкладке Actions или по красным бейджам `Docs` и `Dependency Audit`; отключённое расписание включается там же кнопкой Enable workflow.
- Ручной запуск workflow

### Release (`.github/workflows/release.yml`)

Автоматически создаёт релизы с собранными артефактами:
- Срабатывает при создании тега версии (формат: `vX.Y.Z` из цифр, например `v2.3.0`)
- Собирает Windows-версии всех филиалов и подписывает их в окружении `code-signing` (без сертификата или при известной уязвимости в зависимостях релиз падает)
- Собирает из подписанных сборок MSI каждого филиала (джоб `msi` без окружения `code-signing` и без секретов, версия MSI — из тега) и подписывает только MSI в окружении `code-signing` (джоб `sign-msi`)
- Создаёт GitHub Release с описанием и прикрепляет к нему `FilePickerAPI-<код филиала>.msi` и архив `FilePickerAPI-<код филиала>.zip` для каждого филиала

**Создание нового релиза:**

Версия проекта хранится только в git-теге: `pyproject.toml`, `/docs` и свойства exe получают её автоматически через [setuptools-scm](https://setuptools-scm.readthedocs.io/). Поднимать версию в файлах не нужно — достаточно создать тег:

```bash
git tag v2.3.0
git push origin v2.3.0
```

Сборки между релизами получают версию вида `2.3.1.dev4+g1a2b3c4` (следующий патч, число коммитов после тега и хэш коммита).

Релиз запускают только теги вида `vX.Y.Z` из цифр; теги вроде `v2.3.0-rc1` релиз не создают.

При локальной разработке версия фиксируется в момент `pip install -e .`; чтобы `/docs` показал новую версию после коммитов или тега, выполните установку повторно.

После отправки тега workflow автоматически:
1. Соберёт и подпишет Windows-версии всех филиалов из `branches.toml`
2. Соберёт из них и подпишет MSI каждого филиала (версия MSI — номер тега; тег больше 255.255.65535 ронял бы сборку MSI)
3. Создаст GitHub Release с именем тега (например, `v2.3.0`)
4. Прикрепит к релизу `FilePickerAPI-<код филиала>.msi` и архивы `FilePickerAPI-<код филиала>.zip`

Релиз создаётся после сборки и подписи: сначала черновиком, к которому прикладываются MSI и архивы, затем публикуется.

Через интерфейс GitHub отдельный тег не создать, поэтому можно выпустить версию и там: Releases → Draft a new release → Choose a tag → ввести `v2.3.0`, Target: `main` → Create new tag → Publish release. Второго релиза workflow не создаёт: он прикладывает MSI и архивы к уже опубликованному релизу. Только до конца сборки релиз висит без файлов.

У выпуска через интерфейс есть ограничения, потому что релиз публикуется до сборки:
- Если сборка или подпись упала (например, нет сертификата), опубликованный релиз остаётся без MSI и архивов. Удалите его и тег вручную, исправьте причину и выпустите версию заново.
- Тег должен быть вида `vX.Y.Z` из цифр. Для тега вроде `v2.3.0-rc1` workflow не запускается, и опубликованный релиз так и останется без MSI и архивов.
- Если в настройках репозитория включены неизменяемые релизы (immutable releases), к опубликованному релизу MSI и архивы не приложить: выпускайте версию тегом из терминала.

Описание релиза в обоих случаях формирует workflow: сначала текст про установку и конфигурацию, ниже — автоматический список изменений GitHub с предыдущего релиза. Текст, вписанный при создании релиза через интерфейс, заменяется.

Пользователи смогут скачать MSI и архив своего филиала со страницы [Releases](../../releases)

## Безопасность

- `fileId` должен быть просто именем файла, и это проверяется до любого обращения к файловой системе: путь, UNC-путь, `..`, а на Windows двоеточие, символы `*?"<>|`, точка или пробел в конце имени и имена устройств (`CON`, `NUL`, `nul.txt`, `COM0`–`COM9`, `LPT0`–`LPT9` и т.п.) отклоняются с 400. Иначе на Windows `fileId` вида `\\host\share\x.txt` заставил бы сервис подключиться к чужому хосту и отдать ему NTLM-хеш своей учётной записи. Кроме того, Windows находит файл без учёта регистра и по короткому имени 8.3 (`REPORT~1.TXT` для `report.txtx`), поэтому проверка расширения и имя в ответе берутся из настоящего имени файла в папке, а не из `fileId`
- Отдаются только файлы, лежащие непосредственно в директории; символическая ссылка не может увести в поддиректорию или наружу. На Windows сервис символическим ссылкам не следует вовсе: в списке их нет, при скачивании — 400, а к цели ссылки (например, `\\host\share`) сервис не обращается
- Ошибки ОС при скачивании не раскрывают клиенту путь к сетевой папке: подробности пишутся в лог
- Только файлы (не директории) могут быть загружены
- Директория с файлами зашита в исполняемый файл при сборке и не может быть подменена пользователем: переменная окружения `FILES_DIRECTORY` игнорируется, а с `FILES_DIRECTORY` в `.env` приложение не запускается; ни аргументы exe, ни значение `Run`, ни свойства MSI путь не задают. Изменить путь филиала можно только через `branches.toml` и новую сборку
- При запуске сервис проверяет, что писать в папку сборки, её содержимое и папки выше могут только администраторы, SYSTEM и TrustedInstaller; иначе пишет предупреждение 1003 со списком нарушений
- CORS origins можно настроить через переменную окружения или `.env` в папке exe (по умолчанию разрешает все источники для разработки)
