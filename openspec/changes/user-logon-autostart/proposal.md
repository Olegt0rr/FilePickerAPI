# Proposal

## Why

Сейчас сервис запускают через `run_production.bat` от имени пользователя: вручную или задачей Планировщика. У такой схемы три проблемы.

- **Безопасность.** Запуск, проверка порта, поиск процесса и ожидание ответа написаны на 135 строках cmd. В таком коде легко ошибиться: системную утилиту может подменить одноимённая из `PATH` или текущей папки, `errorlevel` может проверяться неправильно, `pushd` по UNC-пути ведёт себя неочевидно. Автотестами это не проверить. Права на папку сборки никто не контролирует. Если кто-то другой может писать в эту папку, он подменит exe или dll, и его код выполнится от имени пользователя, у которого есть доступ к сетевой папке с платёжками.
- **Надёжность.** За упавшим процессом никто не следит и не перезапускает его. Если порт занят или сервис не стартовал, видно только `FAILED` в журнале скрипта.
- **Журнал.** Журнал ведёт только скрипт запуска, и в нём одна строка в `%LOCALAPPDATA%\FilePickerAPI\startup.log`. Работа сервиса никуда не пишется: ошибки, недоступность сетевой папки и запросы видны только в консольном окне и пропадают вместе с ним.

Есть и требование заказчика, которое задаёт форму решения. Доступ к сетевой папке с платёжками (`\\localmq.neadru.local\Payments\<филиал>\CENTER\RSB`) есть только у учётной записи пользователя. Права для учётных записей компьютеров, групп компьютеров и gMSA выдаваться не будут. Сервис нужен только пока пользователь работает за машиной. Поэтому служба Windows не подходит: от виртуальной учётной записи она ходит в сеть как учётная запись компьютера и получила бы отказ, а служба от имени самого пользователя требует хранить его пароль в настройках службы.

## What Changes

- Сервис ставится MSI-пакетом и запускается при входе пользователя в систему. MSI (WiX) раскладывает сборку в `C:\Program Files\FilePickerAPI\` и прописывает значение `FilePickerAPI` в `HKLM\Software\Microsoft\Windows\CurrentVersion\Run` с путём к exe без аргументов. Писать туда может только администратор; срабатывает оно при входе любого пользователя, процесс работает от его имени, с его доступом к сетевой папке, без повышения прав и без хранения пароля. Обновление, откат при сбое установки и замену занятых файлов делает Windows Installer. Администратор ставит один подписанный MSI вручную, через GPO или SCCM; пользователю делать ничего не нужно.
- Изменение совместимое: `run_test.bat` и `run_production.bat` остаются в архиве сборки и продолжают работать. Филиалы переводятся по одному. Сами скрипты удаляются отдельным изменением `remove-bat-scripts` (BREAKING, 3.0.0), когда переведены все машины.
- У `FilePickerAPI.exe` один режим — без аргументов: работа сервиса в окне консоли, если exe запущен из консоли, или без окна, если его запустил вход пользователя. Любые аргументы дают сообщение об использовании и код выхода 2.
- Если порт 8000 уже слушает File Picker API (например, у другого пользователя той же машины или второй запуск у того же), новый экземпляр пишет одну строку в файл журнала и завершается с кодом 0: фронтенд всех пользователей получает файлы через уже работающий сервис.
- `app/__init__.py` больше не создаёт HTTP-приложение и не читает настройки при импорте: это делает фабрика `create_app()`. Ошибочный `.env` не мешает настроить журнал и записать причину в журнал событий.
- Сервис останавливается мягко: по Ctrl+C или закрытию консоли, при выходе пользователя из системы, выключении Windows и при обновлении или удалении MSI (Restart Manager). Ошибка HTTP-сервера (например, порт 8000 занят другой программой) перезапускает его внутри процесса через 10, 30 и 60 секунд, после четвёртой неудачи процесс завершается с ошибкой.
- Сервис ведёт журнал:
  - файл с ежедневной ротацией в `%LOCALAPPDATA%\FilePickerAPI\logs\` пользователя (30 дней): запуск, остановка, предупреждения и ошибки, журнал запросов Uvicorn, смена состояния сетевой папки (недоступна / снова доступна);
  - журнал событий Windows (Application, источник `FilePickerAPI`), который регистрирует MSI: запуск и остановка как сведения и **все** ошибки и предупреждения — отказ запуска (например, `FILES_DIRECTORY` в `.env`), недоступность, медленный ответ и восстановление сетевой папки филиала, ошибки доступа к файлам, непредвиденные ошибки запросов с трассировкой. У каждого вида события постоянный код (1000–1004, 2000–2004, 3000, 4000), в тексте ошибок ОС — путь, код ошибки Windows и его описание, в тексте запуска и остановки — пользователь. Одинаковые ошибки пишутся в журнал событий не чаще раза в час с числом повторов, каждый случай есть в файле журнала.
- Текст событий в Event Viewer отображается полностью и по-русски: в сборку добавляется файл сообщений `FilePickerAPI.messages.dll` (таблица сообщений из `app/messages/FilePickerAPI.mc`, компилируется в CI). Источник событий и этот файл — постоянные компоненты MSI: прошлые события читаются и после удаления продукта.
- Повторы ошибок отправляются напоминанием по таймеру, а не только при следующей ошибке, и при остановке сервиса. Открытие и чтение тела скачиваемого файла учитываются в событиях так же, как обращения в обработчике.
- Сервис начинает принимать запросы, не дожидаясь создания директории с файлами: недоступная сетевая папка не задерживает запуск.
- CI собирает для каждого филиала подписанный `FilePickerAPI-<филиал>.msi` рядом с прежним архивом и проверяет его дымовой проверкой на Windows-раннере: установка, значение `Run`, источник событий, запуск, ответ по HTTP, журнал, второй экземпляр, обновление поверх работающего экземпляра с сохранением `.env`, отказ при `FILES_DIRECTORY` в `.env`, удаление. Проверка читает события так, как их показывает Event Viewer (`Get-WinEvent`, `wevtutil qe /f:text`), и сверяет коды, уровни и полный текст без искажений.
- Новые зависимости — `pywin32` (только для Windows, точная версия) и WiX Toolset в CI (точная версия).
- `openspec/config.yaml` получает неизменяемое требование: доступ к сетевой папке есть только у учётной записи пользователя, сервис работает от её имени и только пока пользователь в системе, служба от другой учётной записи, права для компьютеров и gMSA не допускаются. README, текст релиза в `release.yml` и `CLAUDE.md` описывают MSI как основной способ установки, а bat-скрипты — как способ, который действует до перевода филиала.

Контракт HTTP API не меняется: эндпоинты, поля, коды ответов и тексты `detail` остаются прежними, порт по-прежнему 8000 на `0.0.0.0`.

Вне рамок изменения:
- Способов задать директорию с файлами при запуске не появляется. Нет ни аргументов у exe, ни свойств MSI, задающих путь, ни конфига рядом с exe. Директория по-прежнему зашивается в сборку из `branches.toml`.
- Служба Windows, работа без вошедшего пользователя, права на сетевую папку для учётной записи компьютера, группы компьютеров или gMSA (см. «Why»).
- Включение и выключение автозапуска для отдельного пользователя: значение `Run` действует для всех пользователей машины.
- Перезапуск сервиса у второго пользователя, когда первый выходит из системы: сервис поднимется у второго при его следующем входе. README это описывает.
- Порт, адрес, папка журнала и срок хранения журнала не становятся настраиваемыми.
- Правило брандмауэра для порта 8000 и политики GPO/SCCM для развёртывания. Это делают администраторы, README описывает команды.
- Отправка журнала во внешние системы. Журнал событий Windows собирается штатными средствами (WEF и т. п.).

## Capabilities

### New Capabilities
- `user-logon-autostart`: режим работы `FilePickerAPI.exe`, установка MSI (раскладка, запуск при входе, источник событий, обновление, откат, удаление), проверка прав на папку сборки, поведение сервиса при запуске, остановке и сбоях, журнал в файле и в журнале событий Windows (коды событий, отображение в Event Viewer, повторяющиеся ошибки, сетевые проблемы).

### Modified Capabilities
- `distribution`: «Сборка для Windows» — в папке сборки дополнительно модули pywin32 и файл сообщений, для каждого филиала собирается и проверяется MSI, bat-скрипты остаются и работают. «Автоматический релиз» — к релизу прикладывается и подписанный MSI каждого филиала. «Скрипты запуска для Windows» — `run_production.bat` запускает новый exe в фоне без окна (раньше — в свёрнутом окне консоли), остальное поведение скриптов прежнее. Удаление «Скрипты запуска для Windows» — в изменении `remove-bat-scripts`.
- `service-configuration`: «Пользователь не может подменить директорию» — к параметрам bat-скриптов добавлены аргументы exe, значение `Run` и свойства MSI. «Запуск сервиса» — предупреждение пишется в журнал сервиса, рабочая папка exe — его папка. «Настройка CORS» — уточнено, где exe читает `.env`.

## Impact

- `app/__main__.py` — отказ от аргументов, переход в папку exe и запуск сервиса.
- `app/__init__.py` и новый `app/api.py` — фабрика `create_app()` вместо создания приложения при импорте пакета; тесты переходят на неё.
- Новые модули:
  - `app/runner.py` — работа сервиса: проверка прав на папку exe, второй экземпляр, Uvicorn, перезапуск при ошибке, мягкая остановка, скрытое окно для выхода из системы и Restart Manager;
  - `app/permissions.py` — проверка прав на папку и путь к ней;
  - `app/logging_setup.py` — настройка журнала, обработчик журнала событий;
  - `app/event_tracking.py` — коды событий, учёт повторов, состояние директории, медленная папка;
  - `app/messages/FilePickerAPI.mc` — таблица сообщений для Event Viewer.
- `installer/FilePickerAPI.wxs` — описание MSI (WiX): файлы сборки, значение `Run`, источник событий, `MajorUpgrade`.
- `app/handlers/files.py` — передача результатов обращений к папке в `app/event_tracking.py` и замер времени без дополнительных обращений к сетевой папке; `app/api.py` — обработчик непредвиденных исключений (500 с событием 4000, ответ прежний).
- `pyproject.toml` — `pywin32` с маркером `sys_platform == 'win32'`; `.config/dotnet-tools.json` — WiX с точной версией.
- `tests/` — тесты режима запуска, второго экземпляра, остановки, настройки журнала, событий (коды, уровни, текст, повторы, состояние директории), соответствия кодов файлу сообщений и содержимого `FilePickerAPI.wxs`. `TestFilesDirectoryIsFixed` расширяется проверкой аргументов exe.
- `.github/workflows/build-exe.yml`:
  - сборка `FilePickerAPI.messages.dll` (`mc`, `rc`, `link` из MSVC) и копирование в папку сборки;
  - ключи Nuitka для модулей pywin32 и режима консоли `attach`;
  - сборка MSI каждого филиала, пробная подпись, дымовая проверка установки и отображения событий (новый скрипт `.github/scripts/msi-smoke.ps1`).
- `.github/workflows/release.yml` — подпись и публикация MSI, текст об установке.
- `README.md`, `openspec/config.yaml`, `CLAUDE.md` — описание установки MSI, журнала и учётной записи.
- Эксплуатация. Филиалы переводятся по одному, без срочности: до перевода новая сборка работает со старыми bat-скриптами. При переводе администратор ставит `FilePickerAPI-<филиал>.msi` (вручную, через GPO или SCCM), а пользователь закрывает прежний сервис и удаляет свою задачу или ярлык с `run_production.bat`, если они есть. Со следующего входа сервис запускается сам.

  Когда переведены все машины, выполняется `remove-bat-scripts`.
