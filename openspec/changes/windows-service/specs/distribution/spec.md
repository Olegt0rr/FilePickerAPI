## MODIFIED Requirements

### Requirement: Сборка для Windows
Проект SHALL собираться через Nuitka в режиме standalone. Результат — папка `FilePickerAPI` с `FilePickerAPI.exe` и его зависимостями (включая модули pywin32 для работы службой, см. `windows-service`). Папка запускается без установленного Python. Bat-скрипты в папку сборки MUST NOT входить. Под каждый филиал из `branches.toml` SHALL собираться своя папка. Режим onefile MUST NOT использоваться: он распаковывает неподписанные файлы во временную папку пользователя, что несовместимо с подписью и WDAC/AppLocker. Сборка SHALL выполняться в CI только после успешного прохождения линтера и тестов. Каждая собранная папка SHALL проверяться в CI установкой и запуском службы на Windows.

#### Scenario: Сборка в CI
- **WHEN** в ветку `main`/`master` отправлен коммит или открыт pull request в одну из этих веток
- **THEN** CI запускает ruff и pytest на Linux и pytest на Windows. Если они прошли, CI собирает папку `FilePickerAPI` на Windows для каждого филиала из `branches.toml`, проверяет её дымовой проверкой службы и публикует как артефакт `FilePickerAPI-<филиал>` (например, `FilePickerAPI-5400`)

#### Scenario: Тесты упали
- **WHEN** линтер или тесты завершились с ошибкой
- **THEN** сборка не выполняется

#### Scenario: Путь филиала в сборке
- **WHEN** CI собирает папку филиала 5400
- **THEN** перед компиляцией CI сверяет записанный путь с `files_directory` филиала 5400 в `branches.toml`, и при расхождении сборка падает; сборки филиалов отличаются только зашитой директорией с файлами

#### Scenario: Ошибка в списке филиалов
- **WHEN** `branches.toml` не проходит проверку (см. «Список филиалов»)
- **THEN** джоб с тестами падает с сообщением о причине, и ни одна сборка не выполняется

#### Scenario: Дымовая проверка службы
- **WHEN** CI собрал папку филиала на Windows-раннере
- **THEN** CI проверяет по порядку:
  - `FilePickerAPI.exe install` из копии сборки в папке, доступной на запись только администраторам, завершается с кодом 0 и копирует сборку в `C:\Program Files\FilePickerAPI\<версия>\`;
  - служба зарегистрирована с учётной записью `NT SERVICE\FilePickerAPI` и путём к exe в папке версии, в кавычках, без аргументов;
  - `GET /openapi.json` отдаёт версию сборки, `GET /files` отвечает 404 `Files directory not found`;
  - в файле журнала и в журнале событий есть событие запуска, после остановки — событие остановки;
  - повторный `install` при работающей службе завершается с кодом 0: служба переустановлена, работает в новом процессе, параметры прежние;
  - после успешного `install` в `C:\Program Files\FilePickerAPI` остаются только папки текущей и прежней версии;
  - с `.env`, где указан `FILES_DIRECTORY`, служба не запускается;
  - `remove` завершается с кодом 0;
  - установка из папки, доступной пользователям на запись, отклоняется.

  При любой неудаче сборка падает, и артефакт не публикуется

#### Scenario: Проверка событий в журнале событий
- **WHEN** дымовая проверка службы прошла сценарии запуска, недоступной папки филиала (при создании директории и при `GET /files`), остановки и отказа запуска из-за `.env`
- **THEN** CI читает события источника `FilePickerAPI` через `Get-WinEvent` и `wevtutil qe /f:text` (тот же текст, что показывает Event Viewer) и проверяет коды 1000, 2004, 2000, 1001 и 1002, их уровни, полный текст без «Не найдено описание для события» и кириллицу без искажений; при расхождении сборка падает

#### Scenario: Нет bat-скриптов в сборке
- **WHEN** CI собрал папку филиала
- **THEN** в папке нет файлов `*.bat`

### Requirement: Автоматический релиз
При публикации тега вида `vX.Y.Z` из цифр SHALL создаваться GitHub Release. К нему для каждого филиала из `branches.toml` прикрепляется архив `FilePickerAPI-<филиал>.zip` с подписанной папкой сборки этого филиала, собранной из этого тега после успешного прохождения тестов и дымовой проверки службы. Теги с суффиксом (например, `v2.3.0-rc1`) MUST NOT создавать релиз.

#### Scenario: Публикация тега
- **WHEN** в репозиторий отправлен тег `v2.3.0`
- **THEN** создаётся релиз `v2.3.0` с архивами `FilePickerAPI-5000.zip`, `FilePickerAPI-5100.zip` и `FilePickerAPI-5400.zip`; внутри каждого лежит папка `FilePickerAPI` с подписанным `FilePickerAPI.exe` своего филиала и его зависимостями, без bat-скриптов

#### Scenario: Предварительная версия
- **WHEN** в репозиторий отправлен тег `v2.3.0-rc1`
- **THEN** релиз не создаётся

## REMOVED Requirements

### Requirement: Скрипты запуска для Windows
**Reason**: `run_test.bat` и `run_production.bat` заменены встроенной службой Windows (см. `windows-service`). Запуск, автозапуск и перезапуск выполняет диспетчер служб, журнал ведёт сама служба. Логика запуска на cmd не тестируется автоматически и даёт риск подмены системных утилит и файлов сборки, а для настройки задачи Планировщика нужны права администратора на каждой машине.
**Migration**: удалить задачу Планировщика с `run_production.bat`, распаковать архив релиза в папку, доступную на запись только администратору (например, в его «Загрузки»), и выполнить оттуда `FilePickerAPI.exe install` от администратора: сборка будет скопирована в `C:\Program Files\FilePickerAPI\<версия>\`. Вместо `run_test.bat` — запуск `FilePickerAPI.exe` без аргументов в консоли. Вместо `%LOCALAPPDATA%\FilePickerAPI\startup.log` — `%ProgramData%\FilePickerAPI\logs\FilePickerAPI.log` и журнал событий Application (источник `FilePickerAPI`).
