# Design

## Context

В `installer/FilePickerAPI.wxs` файл сообщений `FilePickerAPI.messages.dll` — отдельный постоянный компонент `MessageFile` с ресурсом VERSIONINFO, а источник `FilePickerAPI` (`util:EventSource`, компонент `EventSource` с постоянным GUID) регистрируется с `EventMessageFile="[#MessageDll]"`. Имя файла одно для всех версий, поэтому MSI новой версии заменяет его по версии файла. Откат (удаление и установка старого MSI) файл не трогает: компонент постоянный, а более старая версия файла новый не заменяет. Так после отката остаётся новейшая таблица (design.md изменения `user-logon-autostart`, «Содержимое MSI» и «Откат»).

Служба журнала событий загружает этот файл, когда форматирует события (`Get-WinEvent`, Event Viewer, `EvtFormatMessage`), и держит его открытым неопределённо долго. Windows Installer передаёт заменяемые файлы Restart Manager, тот находит `EventLog` и зависимые службы, и при `/qn` установка останавливает и перезапускает их (см. proposal.md). Exe работающего экземпляра тоже заменяется через Restart Manager: так сервис получает `WM_ENDSESSION` с `ENDSESSION_CLOSEAPP` и останавливается мягко (шаг 11 дымовой проверки), и это нужно сохранить.

## Goals / Non-Goals

**Goals:**
- Ни одна установка, обновление или откат не заменяют и не удаляют файл сообщений, который может держать `EventLog`.
- После отката и удаления источник зарегистрирован на новейшем из установленных файлов сообщений.
- Restart Manager по-прежнему закрывает работающий экземпляр при замене exe.
- Дымовая проверка ловит перезапуск `EventLog`.

**Non-Goals:**
- Удаление устаревших файлов сообщений.
- Пользовательские действия в MSI (их по-прежнему нет).
- Изменения таблицы сообщений, кодов событий и самого сервиса.

## Decisions

### Файл сообщений с версией в имени

Файл из папки сборки (`FilePickerAPI.messages.dll`) ставится под именем `FilePickerAPI.messages.$(var.Version).dll`: `File Name` с версией пакета, `Source` прежний. Компонент `MessageFile` остаётся постоянным и без явного GUID: WiX выводит GUID из пути ключевого файла, поэтому у каждой версии свой компонент, как и требуют правила компонентов при смене имени ключевого файла.

Новая версия добавляет новый файл и не трогает файлы прежних версий: прежний продукт при `MajorUpgrade` их не удаляет, потому что компонент постоянный. Заменять нечего, и Restart Manager не получает файла, который держит `EventLog`. Повторная установка той же версии (после отката) находит файл с той же версией и не копирует его.

Имя берётся из версии пакета, а выбор новейшего (ниже) — из версии файла, поэтому `build-msi.ps1` проверяет, что версия DLL сообщений в `VS_FIXEDFILEINFO` равна `X.Y.Z.0` версии пакета, и падает при расхождении. В CI это уже так (`FILE_VERSION` равна версии первого MSI, а копия для второго MSI получает версию второго), проверка закрепляет это для любой сборки пакета.

Отвергнутые варианты:
- **Отключить Restart Manager** (`MSIRESTARTMANAGERCONTROL=Disable` или `DisableShutdown`). Пропала бы мягкая остановка работающего экземпляра, а занятый файл ставился бы с перезагрузкой (код 3010).
- **Один и тот же файл без смены версии** (таблица с запасом кодов, версия файла постоянная). Таблица всё равно меняется при добавлении кодов, и в такие обновления `EventLog` снова перезапускался бы; кроме того, менялась бы схема `.mc`.
- **Удалять старые файлы** (`RemoveFile` по маске). Удаление занятого файла снова привлекает Restart Manager или откладывает удаление до перезагрузки. Файлы маленькие (единицы КБ), один на версию.
- **Файл вне папки установки** (например, в `CommonAppDataFolder`). Ничего не меняет: держит файл служба, а не папка; к тому же туда могут писать не только администраторы.

### Регистрация только на новейший файл

`util:EventSource` пишет `EventMessageFile` при каждой установке компонента `EventSource`. С именем по версии откат записал бы туда старый файл, и события новых кодов показывались бы без текста. Поэтому компонент получает условие `NOT NEWERMESSAGEFILE`.

Свойство `NEWERMESSAGEFILE` задаёт `AppSearch`: `RegistrySearch` значения `EventMessageFile` в `HKLM\SYSTEM\CurrentControlSet\Services\EventLog\Application\FilePickerAPI` (`Type="file"`, `Bitness="always64"`) с вложенным `FileSearch` и `MinVersion="$(var.Version).1"`. Поиск находит зарегистрированный файл, только если его версия не меньше `X.Y.Z.1`, то есть больше `X.Y.Z.0` устанавливаемого пакета (у DLL сообщений четвёртое число всегда 0, а равных версий с `.1` не бывает, поэтому правило о языке при равных версиях, описанное для `MinVersion`, не срабатывает).

Что получается:
- первая установка: значения нет, свойство пустое — регистрация на свой файл;
- обновление: зарегистрирован файл старой версии — регистрация на новый файл;
- откат (удаление новой, установка старой): зарегистрирован файл новой версии, он остался на диске — компонент не ставится, регистрация остаётся на новейшем; удаление продукта её и так не трогает (`Permanent`);
- повторная установка той же версии: зарегистрирован свой же файл — регистрация переписывается тем же значением;
- зарегистрированный файл удалён вручную: поиск ничего не находит — регистрация на свой файл.

Свойство публичное (`AppSearch` пишет только в публичные свойства) и `Secure`. Администратор может передать его в командной строке и тем самым не обновить регистрацию; к директории с файлами это отношения не имеет.

Имя `FileSearch` при поиске по пути из реестра Windows Installer не сверяет: путь берётся из значения целиком (так ведёт себя и реализация Wine). `Name` у `FileSearch` задан именем без версии, потому что столбец `FileName` таблицы `Signature` обязателен. Если на деле имя сверяется, поиск ничего не найдёт, и откат перепишет регистрацию на старый файл; дымовая проверка ловит это на шаге 6 (регистрация после отката).

Отвергнутые варианты:
- **Список файлов в `EventMessageFile`** (свой файл плюс прежнее значение). Значение растёт с каждой установкой и требует склейки строк в MSI; полагается на то, что форматирование перебирает файлы списка.
- **`NeverOverwrite` у компонента регистрации.** Не обновляет регистрацию и при обновлении версии.
- **Отдельное значение реестра с версией таблицы.** Нужно сравнение версий в условии MSI, а строки и числа там для этого не годятся.

### Дымовая проверка

`Invoke-Msi` перед запуском `msiexec` запоминает PID службы `EventLog` (`Win32_Service.ProcessId`), а после выхода проверяет, что PID тот же и служба работает. Так проверяются все установки и удаления сценария. Имён закрытых приложений в журнале `msiexec` при `/qn` нет, только строки «Successfully shut down…» и «Previously shut down applications have been restarted». Поэтому шаг 6 (обновление остановленного сервиса), где файл раньше заменялся, дополнительно требует, чтобы таких строк не было: сервис остановлен, и закрывать Restart Manager некого. Перед шагом 6 `EventLog` уже загрузил файл сообщений первого MSI: шаги 2–5 читают тексты событий через `Get-WinEvent`, поэтому проверка воспроизводит исходную ситуацию.

Сверка файлов установки знает имена файлов сообщений обеих версий: файл из папки сборки ожидается под именем с её версией, файл другой версии допустим и должен совпадать с DLL сообщений своей сборки. `Assert-Registration` принимает версию, на файл которой должен указывать источник: после отката и после удаления — вторую.

## Risks / Trade-offs

- [В папке установки копятся файлы сообщений, по одному на установленную версию] → Они размером в единицы КБ; удаляются вручную, когда не нужны тексты старых событий.
- [Windows Installer сверяет имя `FileSearch` при поиске по пути из реестра] → Дымовая проверка после отката сравнивает `EventMessageFile` с файлом второй версии и падает; тогда поиск переносится на `DirectorySearch` по папке установки с перебором известных имён или на другой признак новейшей таблицы.
- [Версия DLL сообщений не совпадает с версией пакета] → Сборка MSI падает (`build-msi.ps1`).
- [`EventLog` держит и другие файлы папки] → Других файлов служба не загружает; если появятся, проверка PID на каждом вызове `msiexec` это покажет.

## Migration Plan

Релизов с MSI ещё нет, поэтому переносить нечего. Если пакет со старой схемой где-то стоит, первое обновление поставит файл с версией в имени и перерегистрирует источник на него (поиск не находит у `FilePickerAPI.messages.dll` версии новее), а старый файл останется на месте и больше не заменяется.
