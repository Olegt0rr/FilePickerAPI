## ADDED Requirements

### Requirement: Режимы запуска FilePickerAPI.exe
`FilePickerAPI.exe` SHALL выбирать режим по аргументам:
- без аргументов — работа сервиса: с выводом журнала в консоль и остановкой по Ctrl+C, если exe запущен из консоли, и без окна в остальных случаях;
- `deploy` — раскладка сборки администратором;
- `install` — запуск при входе для текущего пользователя;
- `remove` — отключение запуска при входе для текущего пользователя.

#### Scenario: Запуск в консоли
- **WHEN** пользователь запускает `FilePickerAPI.exe` без аргументов из `cmd`
- **THEN** сервис работает, журнал (включая ошибки запуска) выводится в эту консоль и в файл журнала, а Ctrl+C останавливает сервис

#### Scenario: Запуск Планировщиком
- **WHEN** задача Планировщика запускает `FilePickerAPI.exe` при входе пользователя
- **THEN** сервис работает без окна, а журнал пишется в файл журнала пользователя

### Requirement: Недопустимые аргументы
Любые аргументы, кроме одной команды `deploy`, `install` или `remove`, включая лишние аргументы и ключи, MUST приводить к сообщению об использовании в stderr и коду выхода 2 без запуска сервиса и без изменений в системе. Ни один режим MUST NOT принимать путь к директории с файлами.

#### Scenario: Неизвестная команда
- **WHEN** пользователь запускает `FilePickerAPI.exe start` или `FilePickerAPI.exe install --force`
- **THEN** exe выводит сообщение об использовании с перечнем команд `deploy`, `install` и `remove` и завершается с кодом 2

### Requirement: Запуск из исходного кода
Запуск из исходного кода (`python -m app`) SHALL работать как сервис в консоли. Команды `deploy`, `install` и `remove` из исходного кода MUST завершаться ошибкой без изменений в системе: их выполняет только собранный `FilePickerAPI.exe`.

#### Scenario: Запуск при входе из исходного кода
- **WHEN** разработчик запускает `python -m app install`
- **THEN** команда завершается с ненулевым кодом и сообщением, что команда доступна только у собранного `FilePickerAPI.exe`; задача Планировщика не создаётся

### Requirement: Проверки перед раскладкой
Перед любыми изменениями в системе `deploy` MUST проверить права администратора, локальный несъёмный диск, права на исходную папку и путь к ней, корень установки (см. «Корень установки») и папку `%ProgramData%\FilePickerAPI` (см. «Папка файла сообщений»). При неудаче — причина и код 1, без копирования файлов, без изменения задач и регистрации источника. Одновременно MUST выполняться не больше одного `deploy`.

#### Scenario: Два deploy одновременно
- **WHEN** администратор запускает `deploy`, пока предыдущий `deploy` ещё выполняется
- **THEN** второй запуск сразу завершается с кодом 1 и сообщением, что `deploy` уже выполняется, ничего не меняя

#### Scenario: Без прав администратора
- **WHEN** пользователь без прав администратора (или администратор без повышения прав) выполняет `FilePickerAPI.exe deploy`
- **THEN** команда сообщает, что нужны права администратора, и завершается с кодом 1

#### Scenario: Сборка в сетевой папке
- **WHEN** администратор выполняет `deploy` для exe, лежащего по UNC-пути или на подключённом сетевом диске
- **THEN** команда сообщает, что раскладка возможна только с локального диска, и завершается с кодом 1

### Requirement: Права на исходную папку
Права записи, удаления, смены прав и владельца на исходную папку `deploy` и всё её содержимое, а для директорий и право удалять вложенные объекты (`FILE_DELETE_CHILD`), MUST быть только у `SYSTEM`, `Administrators`, `NT SERVICE\TrustedInstaller` и учётной записи, от имени которой выполняется `deploy`. Владельцем каждого из этих объектов MUST быть одна из этих учётных записей.

#### Scenario: Распакованный релиз в Загрузках администратора
- **WHEN** администратор распаковал архив релиза в `C:\Users\admin\Downloads\FilePickerAPI` и выполняет оттуда `deploy`
- **THEN** проверка исходной папки проходит: писать в неё могут только сам администратор и доверенные учётные записи

#### Scenario: Папка доступна пользователям на запись
- **WHEN** администратор выполняет `deploy` из папки, в которую у `Users` или `Authenticated Users` есть право записи (например, `C:\FilePickerAPI` или общая папка)
- **THEN** команда перечисляет объекты и учётные записи с правами записи, завершается с кодом 1, файлы не копируются

#### Scenario: Право удалять содержимое папки
- **WHEN** у `Users` есть `FILE_DELETE_CHILD` на исходной папке, хотя на сами файлы права удаления нет
- **THEN** `deploy` отклоняет раскладку с кодом 1 и называет это право

#### Scenario: Объект без DACL
- **WHEN** у исходной папки или файла в ней владелец `Administrators`, но DACL отсутствует (NULL DACL, полный доступ всем)
- **THEN** `deploy` отклоняет раскладку с кодом 1 и называет объект как доступный всем; объект с пустой DACL нарушением не считается

### Requirement: Защита пути к исходной папке
Ни одну папку на пути от корня тома до исходной папки MUST NOT можно было бы подменить: у каждой папки-предка права удаления, удаления вложенных объектов, смены прав и владельца MUST быть только у учётных записей, доверенных для исходной папки, и владелец каждой из них MUST быть такой учётной записью. Путь с junction, символической ссылкой или точкой монтирования MUST отклоняться.

#### Scenario: Junction на доверенную папку
- **WHEN** администратор выполняет `deploy` из `C:\link\release`, где `C:\link` — junction на папку, у которой все права и владельцы доверенные
- **THEN** `deploy` отклоняет раскладку с кодом 1 и называет `C:\link` точкой повторной обработки, хотя окончательный путь сам по себе проверку прошёл бы

#### Scenario: Сборка в папке другого пользователя
- **WHEN** администратор выполняет `deploy` для `C:\Users\alice\container\FilePickerAPI`, где сама папка защищена, но `alice` может удалять и переименовывать `container`
- **THEN** `deploy` отклоняет раскладку с кодом 1 и называет папку `container` и учётную запись

#### Scenario: Смена прав у предка
- **WHEN** у `Users` есть право `WRITE_DAC` на одну из папок-предков
- **THEN** `deploy` отклоняет раскладку с кодом 1

#### Scenario: Право создавать папки на корне диска
- **WHEN** у пользователей есть право создавать папки на `C:\`
- **THEN** проверка пути это нарушением не считает

### Requirement: Папка версии
`deploy` SHALL раскладывать сборку в `C:\Program Files\FilePickerAPI\<версия>\`, где `<версия>` — версия собранного exe. Если exe уже запущен из этой папки, файлы не копируются, но папка версии, её содержимое и предки MUST до любых изменений проверяться так же строго, как копия: без учётной записи администратора среди доверенных. Иначе сборка копируется туда (см. «Копирование в папку версии»).

#### Scenario: Первая раскладка из Загрузок
- **WHEN** администратор выполняет `deploy` из `C:\Users\admin\Downloads\FilePickerAPI` для версии 2.4.0
- **THEN** файлы скопированы в `C:\Program Files\FilePickerAPI\2.4.0\`, команда завершается с кодом 0

#### Scenario: Папка версии доступна администратору на запись
- **WHEN** в `C:\Program Files\FilePickerAPI\2.4.0\` у учётной записи администратора лично есть право записи, и он выполняет `deploy` из этой папки
- **THEN** `deploy` отклоняет раскладку с кодом 1 и перечнем объектов, задачи пользователей не меняются

### Requirement: Копирование в папку версии
`deploy` MUST копировать сборку во временную папку внутри `C:\Program Files\FilePickerAPI`, читая каждый файл через дескриптор без общего доступа на запись и удаление, затем сверить SHA-256 копий с прочитанным и проверить права на копию без учётной записи администратора среди доверенных. Только после этого временная папка SHALL переименовываться в папку версии.

#### Scenario: Файл подменён во время копирования
- **WHEN** содержимое скопированного файла не совпало с прочитанным исходным
- **THEN** `deploy` удаляет временную папку и завершается с кодом 1, задачи пользователей не меняются

### Requirement: Повторная раскладка той же версии
Если папка версии уже есть, `deploy` из другой копии SHALL заменять её, только если ни один процесс `FilePickerAPI.exe` не запущен из неё; иначе — код 1 с перечнем PID и пользователей без изменений. Старая папка MUST сначала переименовываться в сторону, и при неудаче любого переименования MUST возвращаться на место.

#### Scenario: Из папки работает экземпляр пользователя
- **WHEN** пользователь работает с сервисом версии 2.4.0, а администратор выполняет `deploy` версии 2.4.0 из другой распакованной копии
- **THEN** команда называет PID и пользователя, завершается с кодом 1, папка `2.4.0` не меняется

#### Scenario: Папку не удалось переименовать
- **WHEN** экземпляров нет, но файл в `C:\Program Files\FilePickerAPI\2.4.0\` открыт другой программой, и папку не удаётся переименовать
- **THEN** `deploy` завершается с кодом 1, называя папку и ошибку Windows, а файлы папки `2.4.0` остаются на месте

### Requirement: Перенос `.env` при раскладке
Если в исходной папке нет `.env`, а в папке прежней версии он есть, `deploy` SHALL скопировать его в папку версии. Прежняя версия — та, которую запускают задачи пользователей, а без задач — наибольшая из других папок версий с `FilePickerAPI.exe`. Перенос SHALL выполняться и тогда, когда копирование сборки пропускается, потому что exe запущен из папки своей версии.

#### Scenario: Перенос `.env`
- **WHEN** в папке прежней версии лежит `.env` с `CORS_ORIGINS`, а в исходной папке новой версии `.env` нет
- **THEN** `.env` копируется в папку новой версии, и сервис после обновления использует те же `CORS_ORIGINS`

#### Scenario: Откат в папку версии без `.env`
- **WHEN** задачи пользователей запускают `2.4.0` с `.env`, где задан `CORS_ORIGINS`, а администратор выполняет `deploy` из `C:\Program Files\FilePickerAPI\2.3.0\`, где `.env` нет
- **THEN** копирование сборки пропускается, `.env` переносится в `2.3.0`, и сервис после отката использует те же `CORS_ORIGINS`, а не `*`

### Requirement: Корень установки
У `C:\Program Files\FilePickerAPI` (папка `Program Files` определяется через `FOLDERID_ProgramFiles`) MUST быть доверенный владелец и права изменения только у `SYSTEM`, `Administrators` и `TrustedInstaller`; ни она, ни папки версий MUST NOT быть точками повторной обработки.

#### Scenario: Папка установки создана не администратором
- **WHEN** `C:\Program Files\FilePickerAPI` — junction или у неё недоверенный владелец
- **THEN** `deploy` завершается с кодом 1 до копирования файлов

### Requirement: Папка файла сообщений
`%ProgramData%\FilePickerAPI` MUST иметь владельца `Administrators` и защищённые права: `SYSTEM` и `Administrators` — полный доступ, `Users` — чтение. Отсутствующая папка SHALL создаваться сразу с этими правами. Если у существующей папки недоверенный владелец, права на изменение у недоверенных, она — точка повторной обработки или у неё нет DACL, `deploy` MUST отклоняться без изменения прав.

#### Scenario: Папку создал обычный пользователь
- **WHEN** обычный пользователь заранее создал `%ProgramData%\FilePickerAPI`, а администратор выполняет `deploy`
- **THEN** команда перечисляет объекты с недоверенным владельцем и завершается с кодом 1, файлы не копируются

#### Scenario: Папку создали во время раскладки
- **WHEN** между предварительными проверками и созданием папки обычный пользователь создал `%ProgramData%\FilePickerAPI`
- **THEN** `deploy` обнаруживает, что папка уже существует, проверяет её заново и завершается с кодом 1 и перечнем объектов, не задавая ей права

### Requirement: Регистрация источника событий
`deploy` SHALL копировать `FilePickerAPI.messages.dll` в `%ProgramData%\FilePickerAPI\` под именем с версией и хешем через временный файл, не перезаписывая существующий файл с тем же содержимым, и регистрировать источник `FilePickerAPI` в журнале Application с этой копией как файлом сообщений. Прошлые события SHALL читаться полностью и после удаления папки сборки.

#### Scenario: Источник после раскладки
- **WHEN** `deploy` завершился с кодом 0
- **THEN** источник `FilePickerAPI` зарегистрирован с файлом сообщений из `%ProgramData%\FilePickerAPI`

#### Scenario: Event Viewer открыт во время обновления
- **WHEN** у администратора открыт Event Viewer с событиями `FilePickerAPI`, и он раскладывает новую версию
- **THEN** `deploy` завершается с кодом 0, источник указывает на файл сообщений новой версии, а старые и новые события показываются с полным текстом

#### Scenario: История событий после удаления сборки
- **WHEN** администратор удалил `C:\Program Files\FilePickerAPI`
- **THEN** прошлые события `FilePickerAPI` в Event Viewer по-прежнему показывают полный текст, без «Не найдено описание»

### Requirement: Переключение задач пользователей
После раскладки `deploy` SHALL переключить все задачи Планировщика `FilePickerAPI-*` на exe новой папки версии и привести их параметры к «Параметры задачи». Ошибка изменения отдельной задачи SHALL выводиться предупреждением с её именем и не менять код выхода 0. Работающие экземпляры пользователей `deploy` MUST NOT останавливать; он SHALL выводить их перечень.

#### Scenario: Обновление версии
- **WHEN** у двух пользователей машины есть задачи на версию 2.3.0, и администратор выполняет `deploy` версии 2.4.0
- **THEN** обе задачи запускают `"C:\Program Files\FilePickerAPI\2.4.0\FilePickerAPI.exe"`, работающие экземпляры 2.3.0 продолжают работать и перечислены в выводе, команда завершается с кодом 0

### Requirement: Очистка старых версий
После раскладки `deploy` SHALL оставить в `C:\Program Files\FilePickerAPI` только папку текущей версии и одну папку для отката, а остальные папки версий и оставшиеся временные папки удалить. Папка для отката — прежняя версия, если это другая версия, иначе наибольшая из других версий с `FilePickerAPI.exe`. Папку, на которую указывает задача, удалять MUST NOT.

#### Scenario: Третья версия
- **WHEN** в `C:\Program Files\FilePickerAPI` есть папки `2.2.0` и `2.3.0`, задачи запускают `2.3.0`, и администратор раскладывает 2.4.0
- **THEN** остаются `2.3.0` и `2.4.0`, папка `2.2.0` удалена

#### Scenario: Откат на прежнюю версию
- **WHEN** задачи запускают `2.4.0`, и администратор выполняет `deploy` из `C:\Program Files\FilePickerAPI\2.3.0\`
- **THEN** задачи переключаются на `2.3.0`, обе папки остаются

#### Scenario: Пустая папка с бо́льшим номером
- **WHEN** задачи запускают `2.4.0`, рядом лежат `2.3.0` и пустая `2.9.0`, и администратор повторно раскладывает 2.4.0
- **THEN** папкой для отката остаётся `2.3.0`, а не `2.9.0`

### Requirement: Безопасность очистки
Удаление старых версий MUST NOT проходить по точкам повторной обработки и MUST NOT затрагивать файлы и папки, не похожие на папку версии или временную папку `deploy`. Ошибка удаления SHALL выводиться предупреждением и не менять код выхода 0.

#### Scenario: Посторонние файлы
- **WHEN** в `C:\Program Files\FilePickerAPI` лежат файлы прежней раскладки без папки версии (например, `FilePickerAPI.exe` прямо в ней)
- **THEN** `deploy` их не удаляет

#### Scenario: Из старой версии ещё работает экземпляр
- **WHEN** из папки старой версии ещё работает экземпляр пользователя, и её не удаётся удалить
- **THEN** `deploy` выводит предупреждение и завершается с кодом 0, папка будет удалена следующим `deploy`

### Requirement: Запуск при входе пользователя
`install` SHALL выполняться без прав администратора и создавать или обновлять задачу Планировщика текущего пользователя (см. «Параметры задачи»), затем запускать сервис. `install` MUST работать только из exe в `C:\Program Files\FilePickerAPI\<своя версия>\`, папка которого, её содержимое и предки проходят проверку прав без пользователя среди доверенных; иначе — код 1 без создания задачи.

#### Scenario: Включение запуска при входе
- **WHEN** пользователь без прав администратора выполняет `"C:\Program Files\FilePickerAPI\2.4.0\FilePickerAPI.exe" install`
- **THEN** создаётся задача на его вход, сервис запущен от его имени, `GET /openapi.json` отвечает, команда завершается с кодом 0

#### Scenario: Запуск из распакованного архива
- **WHEN** пользователь выполняет `install` из exe в своих «Загрузках»
- **THEN** команда сообщает, что сначала администратор выполняет `deploy`, и завершается с кодом 1; задача не создаётся

#### Scenario: Следующий вход
- **WHEN** пользователь, выполнивший `install`, выходит из системы и снова входит
- **THEN** сервис запускается от его имени без окна и отвечает на порту 8000

### Requirement: Параметры задачи
Задача SHALL называться `FilePickerAPI-<SID пользователя>` и лежать в корне Планировщика. Её триггер — вход этого пользователя, учётная запись — этот пользователь с типом входа «только при входе пользователя» (без хранения пароля) и без повышения прав. Действие — путь к exe в папке версии в кавычках, без аргументов. Ограничения времени работы нет, работа от батареи разрешена, новый экземпляр при работающем не запускается.

#### Scenario: Параметры созданной задачи
- **WHEN** пользователь выполнил `install`
- **THEN** `Get-ScheduledTask` показывает задачу с триггером входа этого пользователя, `LogonType` `Interactive`, `RunLevel` `Limited`, действием без аргументов и `ExecutionTimeLimit` `PT0S`

### Requirement: Прежний экземпляр при включении
Если порт 8000 слушает экземпляр сервиса этого же пользователя, `install` SHALL остановить его мягко (ожидание до 30 секунд, затем принудительно) и запустить сервис заново. Если порт слушает другой процесс, `install` MUST завершаться с кодом 1 с его PID без создания или изменения задачи.

#### Scenario: Повторный install
- **WHEN** сервис пользователя уже работает, и он снова выполняет `install`
- **THEN** прежний экземпляр пишет событие остановки и завершается, новый запускается, команда завершается с кодом 0

#### Scenario: Порт занят другой программой
- **WHEN** порт 8000 слушает другая программа, и пользователь выполняет `install`
- **THEN** команда сообщает PID и, если доступно, имя процесса, завершается с кодом 1, задача не создаётся

### Requirement: Проверка запуска при включении
После создания задачи `install` SHALL запустить сервис и до 60 секунд ждать, пока одновременно: процесс жив, порт 8000 слушает процесс с его PID и `http://127.0.0.1:8000/openapi.json` отвечает (без прокси). Тогда код выхода 0. Иначе — код 1 и путь к файлу журнала; задача при этом остаётся.

#### Scenario: Сервис не запустился
- **WHEN** в папке версии лежит `.env` с `FILES_DIRECTORY`, и пользователь выполняет `install`
- **THEN** `install` выводит код выхода процесса и путь к журналу, где записана причина, и завершается с кодом 1

#### Scenario: Отвечает другой процесс
- **WHEN** после запуска на `/openapi.json` отвечает процесс, PID которого не совпадает с PID запущенного сервиса
- **THEN** `install` не считает это успехом, выводит PID владельца порта и завершается с кодом 1

### Requirement: Отключение запуска при входе
`remove` SHALL выполняться без прав администратора: останавливать экземпляр сервиса текущего пользователя (мягко, до 30 секунд, затем принудительно) и удалять его задачу. Файл журнала, папки версий и регистрацию источника `remove` MUST NOT трогать. Если задачи и экземпляра нет, `remove` SHALL завершаться с кодом 0.

#### Scenario: Отключение
- **WHEN** пользователь выполняет `remove`, а его сервис работает
- **THEN** сервис пишет событие остановки и завершается, задача удалена, команда завершается с кодом 0

#### Scenario: Задачи нет
- **WHEN** пользователь выполняет `remove`, а задачи и экземпляра нет
- **THEN** команда сообщает, что запуск при входе не включён, и завершается с кодом 0

#### Scenario: Отключение при ошибочном `.env`
- **WHEN** в папке exe лежит `.env` с `FILES_DIRECTORY`, и пользователь выполняет `remove`
- **THEN** задача удаляется, команда завершается с кодом 0: `deploy`, `install` и `remove` настройки HTTP-приложения не читают

### Requirement: Учётная запись сервиса
Сервис SHALL работать от имени вошедшего пользователя и обращаться к сетевой папке с его учётными данными. Он MUST NOT требовать хранения пароля, прав администратора, службы Windows или прав на сетевую папку для учётной записи компьютера, группы компьютеров или gMSA.

#### Scenario: Доступ к сетевой папке
- **WHEN** у пользователя есть право чтения сетевого ресурса филиала, и его сервис запущен при входе
- **THEN** `GET /files` возвращает список файлов из UNC-папки филиала

#### Scenario: Нет прав на ресурс
- **WHEN** у пользователя нет права чтения сетевого ресурса
- **THEN** `GET /files` отвечает 403, а в журнал пишется предупреждение о недоступной директории с именем пользователя в событии запуска

### Requirement: Запуск сервиса
Сервис SHALL начинать принимать запросы, не дожидаясь создания директории с файлами (см. `service-configuration`, «Запуск сервиса»): она создаётся параллельно. Если порт 8000 уже слушает экземпляр этого же пользователя, новый процесс SHALL завершаться с кодом 0 без событий, записав это в файл журнала.

#### Scenario: Сетевая папка недоступна при запуске
- **WHEN** сервис запускается при входе, а UNC-путь филиала недоступен и обращение к нему ждёт таймаута SMB
- **THEN** сервис принимает запросы без ожидания таймаута, а после таймаута пишет предупреждение

#### Scenario: Второй запуск
- **WHEN** сервис пользователя работает, и он запускает `run_production.bat` или exe ещё раз
- **THEN** второй процесс завершается с кодом 0, первый продолжает работать, в журнале событий новых событий нет

### Requirement: Остановка сервиса
По Ctrl+C или закрытию консоли, по команде `install` или `remove` и при выходе пользователя из системы сервис SHALL завершать HTTP-сервер, ожидая текущих запросов не дольше 10 секунд, и записывать событие остановки ровно один раз. Остановка SHALL работать на любом этапе, включая запуск. Если обращение к сетевой папке не завершилось за 20 секунд, процесс MUST всё равно завершиться.

#### Scenario: Остановка по remove
- **WHEN** пользователь выполняет `remove`, а его сервис работает
- **THEN** сервис завершает HTTP-сервер, пишет событие остановки в журнал событий и файл журнала, и процесса не остаётся не позже чем через 30 секунд

#### Scenario: Остановка во время зависшего обращения к папке
- **WHEN** сервис только запущен, создание директории на сетевой папке висит в ожидании SMB, и пользователь выполняет `remove`
- **THEN** HTTP-сервер больше не запускается, если ещё не запущен, единственное событие 1001 отмечает незавершённое обращение к папке, процесса не остаётся не позже чем через 30 секунд

#### Scenario: Ошибка во время остановки
- **WHEN** во время мягкой остановки текущий запрос повторно завершается ошибкой, которая уже была записана в журнал событий
- **THEN** этот повтор попадает в напоминание, записанное перед событием 1001

### Requirement: Выход пользователя из системы
При выходе пользователя из системы или выключении Windows сервис SHALL получать уведомление о завершении сеанса и за 3 секунды отправлять накопленные повторы напоминаниями и записывать событие 1001 с причиной «выход пользователя или выключение Windows». Повторный сигнал MUST NOT запускать остановку второй раз.

#### Scenario: Выход с накопленными повторами
- **WHEN** пользователь выходит из системы, а его сервис накопил 5 повторов ошибки
- **THEN** до завершения процесса в журнале событий появляются напоминание с числом 5 и событие 1001 с причиной «выход пользователя или выключение Windows»

### Requirement: Ошибки сервиса
Ошибка HTTP-сервера (порт занят, исключение Uvicorn), если остановка не запрошена, MUST записываться событием 1002 с причиной, после чего сервис SHALL создавать HTTP-сервер заново через 10, 30 и 60 секунд, а после четвёртой неудачи подряд завершаться с кодом 1. Ошибка загрузки настроек MUST завершать процесс с кодом 1 сразу. Ошибка во время запрошенной остановки SHALL отмечаться в событии остановки, код 0.

#### Scenario: Путь в `.env`
- **WHEN** в папке exe лежит `.env` с `FILES_DIRECTORY`, и сервис запускается
- **THEN** сервис не начинает принимать запросы, в журнал событий пишется одно событие 1002 с причиной (лишний параметр `FILES_DIRECTORY`), процесс завершается с кодом 1 без повторных попыток

#### Scenario: Порт 8000 занят
- **WHEN** сервис запускается, а порт 8000 занят другой программой и не освобождается
- **THEN** на каждую из четырёх попыток в журнал событий пишется одно событие 1002 с причиной и номером попытки, а процесс завершается с кодом 1, а не остаётся без HTTP-сервера

#### Scenario: Порт освободился
- **WHEN** при запуске порт 8000 был занят, а через 20 секунд освободился
- **THEN** после события 1002 о первой попытке следующая попытка проходит, и сервис принимает запросы

#### Scenario: Ошибка после накопленных повторов
- **WHEN** сервис работал и накопил повторы ошибки, а HTTP-сервер завершился с ошибкой
- **THEN** в журнале событий появляются напоминание о повторах и событие 1002 с причиной, события 1001 нет

#### Scenario: Ошибка во время запрошенной остановки
- **WHEN** пользователь выполняет `remove`, а HTTP-сервер при мягкой остановке завершается с ошибкой
- **THEN** в журнале событий одно событие 1001 с пометкой об ошибке, процесс завершается с кодом 0

### Requirement: Проверка прав при запуске сервиса
При каждом запуске сервис SHALL проверять права на папку своего exe и путь к ней так же, как `deploy` проверяет копию в папке версии (доверенные только `SYSTEM`, `Administrators` и `TrustedInstaller`). При нарушении он пишет в журнал событий предупреждение и продолжает работу.

#### Scenario: Права на папку сборки изменили после раскладки
- **WHEN** после раскладки пользователям выдали право записи в папку версии, и сервис запускается
- **THEN** сервис пишет в журнал событий предупреждение с перечнем объектов и учётных записей и продолжает работу

### Requirement: Файл журнала
Сервис SHALL вести журнал в `%LOCALAPPDATA%\FilePickerAPI\logs\FilePickerAPI.log` пользователя с ежедневной ротацией и хранением 30 дней, в том числе при запуске из консоли. В каждой строке — время, уровень, источник и сообщение. В файл попадают:
- запуск (версия, код филиала, директория, пользователь) и остановка;
- предупреждения и ошибки;
- HTTP-запросы (адрес клиента, метод, путь, код ответа);
- смена состояния директории.

Содержимое файлов в журнал MUST NOT попадать.

#### Scenario: Журнал после запуска
- **WHEN** сервис запущен при входе и обработал `GET /files`
- **THEN** в `%LOCALAPPDATA%\FilePickerAPI\logs\FilePickerAPI.log` пользователя есть строка запуска с версией, кодом филиала, директорией и пользователем и строка запроса `GET /files` с кодом ответа

#### Scenario: Ротация
- **WHEN** сервис работает дольше суток
- **THEN** в полночь текущий файл переименовывается с датой в имени, запись продолжается в новый `FilePickerAPI.log`, а архивы старше 30 дней удаляются

#### Scenario: Файл открыт читателем в полночь
- **WHEN** в полночь пользователь держит `FilePickerAPI.log` открытым без права удаления (например, `Get-Content -Wait`), и переименование не удаётся
- **THEN** журнал продолжает писаться в текущий файл без потерянных строк, а ротация выполняется при следующей попытке после того, как читатель закроет файл

#### Scenario: Открыт старый архив
- **WHEN** в полночь пользователь держит открытым архив старше 30 дней
- **THEN** ротация проходит, журнал пишется в новый файл, а архив удаляется при следующей очистке после закрытия

#### Scenario: Старый архив после отпуска
- **WHEN** сервис запускается после двухмесячного перерыва, а в папке журнала один архив 60-дневной давности и несколько свежих
- **THEN** при запуске старый архив удаляется, хотя архивов меньше 30, а свежие остаются

#### Scenario: Файл журнала недоступен
- **WHEN** сервис не может писать в файл журнала
- **THEN** сервис запускается и принимает запросы, а в журнал событий пишется предупреждение о невозможности вести файл журнала

### Requirement: Ошибки в журнале событий
Если источник `FilePickerAPI` зарегистрирован, каждая ошибка и каждое предупреждение сервиса SHALL попадать в журнал событий Application от этого источника сразу или в напоминании о повторах (см. «Повторяющиеся ошибки»), включая отказ запуска и аварийное завершение, недоступность и медленный ответ сетевой папки, ошибки доступа к файлам и непредвиденные ошибки запросов (ответ 500). Запуск и остановка пишутся как сведения. HTTP-запросы в журнал событий MUST NOT попадать.

#### Scenario: Событие запуска
- **WHEN** сервис запущен и обработал `GET /files`
- **THEN** в журнале событий Application есть событие запуска от источника `FilePickerAPI` с именем пользователя, а события о запросе `GET /files` нет

#### Scenario: Источник не зарегистрирован
- **WHEN** сборку запускают на машине, где `deploy` не выполнялся
- **THEN** сервис работает, журнал пишется в файл, ошибок о журнале событий нет

#### Scenario: Непредвиденная ошибка запроса
- **WHEN** обработка запроса завершилась непредвиденным исключением, и клиент получил 500
- **THEN** в журнале событий есть ошибка с кодом 4000, маршрутом запроса и трассировкой исключения

#### Scenario: Ошибка, уже превращённая в ответ 500
- **WHEN** при чтении директории возникло непредвиденное исключение, и сервис ответил 500 `Unexpected error when reading directory: …`
- **THEN** `detail` ответа прежний, а в журнале событий одно событие 4000 с трассировкой исходного исключения

### Requirement: Коды событий сервиса
События сервиса SHALL иметь постоянные коды и уровни:
- 1000 и 1001 — сервис запущен и остановлен (сведения);
- 1002 — сервис не запустился или HTTP-сервер завершился с ошибкой (ошибка);
- 1003 — не только администраторы могут писать в папку сборки (предупреждение);
- 1004 — не удаётся вести файл журнала (предупреждение).

#### Scenario: Остановка в журнале событий
- **WHEN** пользователь выполняет `remove`, а сервис работал
- **THEN** в журнале событий есть событие 1001 с уровнем «Сведения»

### Requirement: Коды событий папки и запросов
События о сетевой папке и запросах SHALL иметь постоянные коды и уровни:
- 2000 и 2002 — папка недоступна, по-прежнему недоступна (предупреждение);
- 2001 — папка снова доступна (сведения);
- 2003 и 2004 — медленная папка, папку не удалось создать при запуске (предупреждение);
- 3000 — ошибка доступа к файлу при скачивании (предупреждение);
- 4000 — непредвиденная ошибка запроса (ошибка).

#### Scenario: Фильтр по коду
- **WHEN** администратор фильтрует журнал Application по источнику `FilePickerAPI` и коду 2000
- **THEN** он видит только события о недоступности сетевой папки, с уровнем «Предупреждение»

### Requirement: Отображение в Event Viewer
Текст события SHALL полностью отображаться в Event Viewer: на русском, без искажения кириллицы и без сообщения «Не найдено описание для события». Для ошибок ОС в тексте SHALL быть путь, код ошибки Windows и её системное описание. Текст длиннее 31 839 символов SHALL обрезаться с пометкой об обрезке.

#### Scenario: Сетевая папка филиала недоступна
- **WHEN** сервис запущен, а сервер сетевой папки филиала не отвечает, и приходит `GET /files`
- **THEN** в Event Viewer событие 2000 показывает UNC-путь папки, код ошибки Windows (например, 53) с её описанием и ответ 404, текст читается без искажений

#### Scenario: Отказ запуска
- **WHEN** сервис не запустился из-за `FILES_DIRECTORY` в `.env`
- **THEN** в Event Viewer событие 1002 с уровнем «Ошибка» показывает причину и трассировку полностью

### Requirement: Повторяющиеся ошибки
Повтор той же ошибки (тот же код события и та же причина) SHALL записываться в журнал событий не чаще раза в час: первое событие сразу, остальные считаются. Накопленное число SHALL отправляться напоминанием по таймеру через час после последней записи, даже если новых запросов нет, и при остановке. В файл журнала SHALL записываться каждый случай. Повторы MUST NOT теряться.

#### Scenario: Частые ошибки скачивания
- **WHEN** фронтенд 500 раз за минуту получает 403 при скачивании `a.txt` из-за прав на сетевой папке, а потом запросы прекращаются
- **THEN** в журнале событий одно событие 3000 и через час напоминание с числом 499, а в файле журнала 500 строк

#### Scenario: Остановка с накопленными повторами
- **WHEN** после события 3000 было 20 повторов, и сервис останавливается раньше чем через час
- **THEN** перед событием 1001 в журнале событий появляется напоминание с числом 20

#### Scenario: Ошибка прекратилась
- **WHEN** после события 3000 повторов не было больше часа, а потом та же ошибка случилась снова
- **THEN** новое событие 3000 пишется сразу, как первое

### Requirement: Повторы записей без кода события
Записи журнала с уровнем WARNING и выше без явного кода события (например, от Uvicorn) SHALL учитываться по тем же правилам повторов с ключом «логгер и шаблон сообщения». Один запрос MUST NOT давать больше одного события: ошибки, которые обработчики уже учли или передали в учёт, повторно в журнал событий не попадают.

#### Scenario: Некорректные HTTP-запросы
- **WHEN** сканер портов присылает на порт 8000 сто соединений с мусором, и Uvicorn сто раз пишет «Invalid HTTP request received.»
- **THEN** в журнале событий одно событие 3000 и через час напоминание с числом 99, а в файле журнала 100 строк

#### Scenario: Один запрос — одно событие
- **WHEN** скачивание `a.txt` завершилось ошибкой доступа к файлу, которую обработчик пишет в журнал
- **THEN** в журнале событий одно событие 3000, в файле журнала одна строка об ошибке

### Requirement: Ограничение числа ключей повторов
Число одновременно учитываемых причин SHALL быть ограничено 50 на код события. Ошибка с новой причиной сверх лимита MUST учитываться в одном общем ключе переполнения этого кода — без `fileId` и `winerror`. Ключ хранит только число ошибок, поэтому его память не растёт. Он подчиняется тем же правилам повторов, а в файл журнала по-прежнему пишется каждый случай с `fileId` и `winerror`.

#### Scenario: Много разных fileId при отказе доступа
- **WHEN** при отказе доступа к сетевой папке за минуту приходит 1000 запросов на скачивание с разными `fileId`
- **THEN** в журнале событий не больше 50 событий 3000 и одно событие о переполнении, через час — напоминание с числом ошибок, а в файле журнала 1000 строк

#### Scenario: Переполнение с разными кодами ошибок
- **WHEN** 50 ключей 3000 уже заняты, и приходят ошибки доступа к файлам с кодами Windows 5 и 32
- **THEN** обе учитываются в одном ключе переполнения 3000 и дают одно событие о переполнении, а коды ошибок видны в файле журнала

#### Scenario: Поток новых имён весь час
- **WHEN** при отказе доступа клиент целый час присылает запросы с новыми `fileId`
- **THEN** число ключей повторов не превышает 50 на код события плюс один ключ переполнения, и память учёта не растёт с числом имён

### Requirement: Состояние директории в журнале
Сервис SHALL записывать недоступность директории (событие 2000) при первой ошибке и при смене причины, напоминание (2002) раз в час, пока она недоступна, и восстановление (2001) с длительностью недоступности и числом ошибочных ответов. Состояние MUST определяться только по результату обращений, которые сервис и так делает для ответа: без дополнительных обращений к сетевой папке и других хостов.

#### Scenario: Папка пропала
- **WHEN** сетевая папка становится недоступной, и фронтенд 100 раз за 10 минут запрашивает `GET /files`
- **THEN** все 100 ответов — 404 `Files directory not found`, а в журнале событий одно событие 2000

#### Scenario: Папка недоступна долго
- **WHEN** сетевая папка недоступна больше часа, и запросы продолжают приходить
- **THEN** каждый час в журнале событий появляется событие 2002 с числом ошибочных ответов за час

#### Scenario: Папка вернулась
- **WHEN** после недоступности папка снова доступна, и приходит `GET /files`
- **THEN** ответ — список файлов, а в журнале событий одно событие 2001 с длительностью недоступности и общим числом ошибочных ответов

#### Scenario: Смена причины
- **WHEN** папка была не найдена (404), а затем стала отвечать отказом в доступе (403)
- **THEN** в журнале событий появляется новое событие 2000 с новой причиной

### Requirement: Сетевые ошибки при скачивании
Если при скачивании ОС сообщает о недоступности сети или ресурса (а не об отсутствии самого файла), сервис SHALL учитывать это как недоступность директории (события 2000, 2002, 2001). Отсутствие запрошенного файла (404 при доступной папке) MUST NOT давать события. Прочие ошибки ОС при доступе к файлу (403, 500) SHALL давать событие 3000 с `fileId` и кодом ошибки Windows.

#### Scenario: Скачивание при недоступной папке
- **WHEN** сетевая папка недоступна, и клиент запрашивает `GET /files/test1.txt`
- **THEN** клиент получает 404 `File not found`, а в журнале событий — событие 2000 о недоступности папки, а не 3000

#### Scenario: Файла нет
- **WHEN** папка доступна, и клиент запрашивает несуществующий `GET /files/missing.txt`
- **THEN** клиент получает 404, а в журнале событий новых событий нет

### Requirement: Медленная сетевая папка
Если обработка запроса, обращающегося к директории, заняла больше 10 секунд, сервис SHALL записать событие 2003 с маршрутом и длительностью, с тем же ограничением повторов. Измерение MUST NOT добавлять обращений к сетевой папке.

#### Scenario: Зависшая папка
- **WHEN** сервер сетевой папки отвечает на запрос списка через 25 секунд
- **THEN** клиент получает ответ, а в журнале событий есть событие 2003 с маршрутом `GET /files` и длительностью около 25 секунд

### Requirement: Учёт чтения скачиваемого файла
Открытие и чтение тела файла при скачивании, которые идут после обработчика, SHALL учитываться так же, как обращения в обработчике: время до конца отправки — для события 2003 (в тексте указывается размер файла), ошибки ОС — как недоступность директории (2000) или ошибка доступа к файлу (3000). Учёт MUST NOT добавлять обращений к сетевой папке.

#### Scenario: Медленное чтение тела
- **WHEN** атрибуты файла получены быстро, но чтение его содержимого по SMB идёт 15 секунд
- **THEN** клиент получает файл, а в журнале событий есть событие 2003 с маршрутом `GET /files/{fileId}`, длительностью и размером файла

#### Scenario: Обрыв при чтении тела
- **WHEN** атрибуты файла получены, а чтение содержимого падает с сетевой ошибкой Windows
- **THEN** ответ клиенту обрывается, а в журнале событий есть событие 2000 о недоступности папки
