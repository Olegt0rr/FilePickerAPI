# Design

## Context

Сейчас поставка устроена так:
- Nuitka в режиме standalone собирает папку `FilePickerAPI` с `FilePickerAPI.exe`. Директория с файлами зашита в `app/_build_config.py` при сборке. В папку сборки копируются `run_test.bat` и `run_production.bat`. Релиз — архив `FilePickerAPI-<филиал>.zip`.
- `run_production.bat` запускает exe свёрнутым окном, через `curl.exe` проверяет `http://127.0.0.1:8000/openapi.json` и пишет одну строку в `%LOCALAPPDATA%\FilePickerAPI\startup.log`. Его запускает пользователь вручную или задачей Планировщика от своего имени. В сетевую папку сервис ходит с учётными данными этого пользователя.
- `app/__main__.py` делает `logging.basicConfig` (вывод в консоль), создаёт директорию с файлами (`mkdir(parents=True)`, предупреждение при ошибке) и вызывает `uvicorn.run(app, host="0.0.0.0", port=8000)`.
- `app/__init__.py` при импорте создаёт `Settings()`, а тот читает `.env` из рабочей папки. Из-за `FILES_DIRECTORY` в `.env` импорт падает с `ValidationError` (лишнее поле), и сервис не запускается. Это закреплено тестами `TestFilesDirectoryIsFixed`.
- Своих журналов у сервиса нет. В журнал пишут только `app/handlers/files.py` (ошибки чтения файла, ошибка разрешения пути директории) и Uvicorn: и то и другое в консоль.

Требование заказчика: доступ к сетевой папке с платёжками (`\\localmq.neadru.local\Payments\<филиал>\CENTER\RSB`) есть только у учётной записи пользователя. Права для учётных записей компьютеров, групп компьютеров и gMSA выдаваться не будут. Сервис нужен только пока пользователь работает за машиной.

Сборка и CI идут на Python 3.11. Локальная разработка может идти на более новом Python. Тесты гоняются на Ubuntu и Windows, покрытие должно быть 100%.

## Goals / Non-Goals

**Goals:**
- Дать замену bat-скриптам: сервис ставится стандартным установщиком, запускается при входе пользователя, от его имени, без хранения пароля, сам перезапускает HTTP-сервер при ошибке и мягко останавливается при выходе пользователя и обновлении. Изменение совместимое: скрипты продолжают работать с новой сборкой, филиалы переводятся по одному, а сами скрипты удаляет отдельное изменение `remove-bat-scripts`. Так реализация идёт небольшими PR в `main`, и спецификации верны на каждом промежуточном этапе.
- Не давать никому, кроме администраторов, подменить файлы сборки, которые выполняются от имени пользователя с доступом к платёжкам.
- Держать установку декларативной: транзакции, откат, замену занятых файлов и обновление делает Windows Installer, а не наш код.
- Вести постоянный журнал работы сервиса с ротацией.
- Все ошибки и предупреждения, включая сетевые проблемы в филиале, отправлять в журнал событий Windows с постоянными кодами и текстом, который читается в Event Viewer без искажений.
- Проверять в CI установку MSI и работу сервиса на настоящем Windows.

**Non-Goals:**
- Служба Windows и работа без вошедшего пользователя.
- Включение и выключение автозапуска для отдельного пользователя.
- Настраиваемые порт, адрес, папка установки, папка или срок хранения журнала.
- Правило брандмауэра и политики развёртывания (GPO, SCCM).
- Изменения HTTP API.

## Decisions

### MSI и запуск через `HKLM\…\Run`

Сервис ставится MSI-пакетом, собранным WiX. Пакет раскладывает сборку в `C:\Program Files\FilePickerAPI\` и прописывает значение `FilePickerAPI` в `HKLM\Software\Microsoft\Windows\CurrentVersion\Run`: путь к exe в кавычках, без аргументов. Explorer запускает его при входе любого пользователя, от его имени, с его токеном без повышения прав. В сетевую папку процесс ходит с учётными данными пользователя, а пароль нигде не хранится. Писать в `Program Files` и в этот ключ может только администратор.

Отклонённые варианты:
- **Служба от виртуальной учётной записи `NT SERVICE\FilePickerAPI`** — первый вариант этого изменения. В сеть она ходит как учётная запись компьютера `ДОМЕН\ИМЯ$`, а заказчик таким учётным записям права не выдаёт: `GET /files` всегда отвечал бы 403. gMSA исключена тем же требованием.
- **Служба от имени пользователя.** Пароль хранится в настройках службы, после смены пароля служба не запускается, ошибка входа может заблокировать учётную запись.
- **Своя раскладка (`deploy`) и задача Планировщика на каждого пользователя (`install`/`remove`)** — второй вариант. Установщик был бы нашим кодом: копирование с проверкой прав исходной папки, частичные сбои и откаты, блокировки, перенос `.env`, переключение задач всех пользователей при обновлении. `deploy` запускался бы из распакованной папки и сам решал, можно ли ей доверять, то есть код выполнялся бы раньше проверки. Каждый пользователь ещё выполнял бы `install`. Мейнтейнер выбрал MSI по сопровождаемости, удобству и надёжности (обсуждение в #37). Плюсы второго варианта — включение для отдельного пользователя и быстрый откат — для машин филиала не нужны.
- **`HKCU\…\Run` или ярлык в «Автозагрузке».** Их ставит и может менять сам пользователь, а MSI для каждого пользователя пришлось бы ставить в его профиль.

Несколько пользователей на одной машине — не проблема: второму свой экземпляр не нужен, сервис на порту 8000 уже работает у первого, и фронтенд второго получает файлы через него (см. «Второй экземпляр»). Если первый пользователь выходит из системы, сервис останавливается и не поднимется у второго, пока тот не войдёт заново; README это описывает.

### Содержимое MSI

`installer/FilePickerAPI.wxs` (WiX, версия закреплена в `.config/dotnet-tools.json`):

| Что | Как | Зачем |
|---|---|---|
| Тип установки | на машину (`Scope="perMachine"`), платформа x64 (`-arch x64`) | ставит администратор, работает у всех пользователей; сборка Nuitka 64-битная, а в пакете x86 `ProgramFiles64Folder` недопустим, и значение `Run` попало бы в `WOW6432Node` |
| Папка установки | `[ProgramFiles64Folder]FilePickerAPI\`; идентификатор каталога — не публичное свойство | папку нельзя указать в командной строке `msiexec`: сборка всегда там, куда пишут только администраторы |
| Файлы | вся папка сборки Nuitka, кроме bat-скриптов | bat-скрипты нужны только для запуска по-старому, им место в архиве |
| Запуск при входе | значение `FilePickerAPI` в `HKLM\Software\Microsoft\Windows\CurrentVersion\Run` = `"[папка установки]FilePickerAPI.exe"` | путь в кавычках, без аргументов; удаляется вместе с продуктом |
| Источник событий | `util:EventSource` в журнале Application, `EventMessageFile` — `[папка установки]FilePickerAPI.messages.dll`, `SupportsErrors`/`Warnings`/`Information`; компонент постоянный (`Permanent="yes"`) | текст прошлых событий читается и после удаления продукта |
| Файл сообщений | `FilePickerAPI.messages.dll` отдельным постоянным компонентом; в `.rc` есть ресурс VERSIONINFO с версией продукта | то же; DLL без версии Windows Installer заменял бы по датам и хешу, и при обновлении могла остаться старая таблица без новых кодов. С версией файл заменяется однозначно. При откате файл не заменяется более старым: остаётся новейшая таблица (см. «Откат») |
| Обновление | `MajorUpgrade` с `Schedule="afterInstallInitialize"` и `DowngradeErrorMessage`, без `AllowSameVersionUpgrades`; `Upgrade` с `OnlyDetect` на ту же версию и условие запуска `Installed OR NOT SAMEVERSIONFOUND`; один `UpgradeCode` для всех филиалов | обновление — установкой MSI новой версии; на машине один File Picker API. Та же или более старая версия поверх установленной запрещена: откат и смена филиала той же версии — удаление и установка нужного MSI (см. «Откат»). Exe разных филиалов и промежуточных сборок одной версии имеют одну версию файла, а Windows Installer не заменяет файл той же версии: сборка одного филиала осталась бы под названием другого, с чужой директорией, или exe удалился бы вместе с прежним продуктом. Без условия запуска `MajorUpgrade` такую установку не заметил бы, и в папке оказалось бы два продукта. При `afterInstallInitialize` решение о замене файлов принимается до удаления прежнего продукта, и при понижении версии файлы с более новой версией не поставились бы, а затем удалились бы вместе с ним, оставив машину без exe. Обычное лекарство `REINSTALLMODE=amus` заодно затёрло бы постоянный файл сообщений. `afterInstallInitialize` удаляет прежний продукт внутри транзакции новой установки: если установка упадёт, Windows Installer вернёт прежнюю версию. При расписании по умолчанию (`afterInstallValidate`) прежний продукт удалялся бы до транзакции, и сбой оставил бы машину без сервиса |
| Название | `File Picker API (филиал <код>)` | в «Программах и компонентах» видно, чья сборка стоит |
| Версия | `ProductVersion` — первые три числа версии `app._version.version` | см. ниже |
| Пользовательские действия | нет | всё описано декларативно, откат делает Windows Installer |

Особенности WiX 5.0.2 из пробной сборки:
- Название на кириллице требует `Codepage="1251"` у `Package` и `<SummaryInformation Codepage="1251" />`: при кодовой странице по умолчанию сборка падает с `WIX0311`.
- Папка сборки подключается через `<Files Include="$(var.Dist)\**">` с абсолютным путём в `-d Dist=…`. С `!(bindpath.…)` шаблон ничего не нашёл, WiX только предупредил (`WIX8601`), и получился пакет на 40 КБ с кодом 0. Поэтому сборка проверяет наличие `FilePickerAPI.exe` в MSI или минимальный размер пакета и падает, если файлов нет.
- Запись той же версии задаётся как `<Upgrade Id="…">`, атрибута `Code` у этого элемента нет.

`.env` в пакет не входит. Его создаёт администратор в папке установки (обычно с `CORS_ORIGINS`). Windows Installer не удаляет файлы, которые не ставил, поэтому `.env` переживает обновление и удаление. Это проверяется пробной сборкой (задача 1.6) и дымовой проверкой.

**Версии.** MSI принимает только `X.Y.Z` с ограничениями 255.255.65535. Релиз по тегу `vX.Y.Z` даёт ту же версию MSI. Сборки между тегами (`2.3.1.dev2+gaa7062aaa`) получают версию следующего релиза из их же номера (`2.3.1`): поверх другой сборки с той же версией такая сборка не ставится, сначала нужно удалить продукт. Если версия выходит за ограничения, сборка MSI падает.

**Обновление поверх работающего сервиса.** Exe работающего экземпляра занят. Windows Installer через Restart Manager закрывает приложения, которые держат файлы: процессу с окном верхнего уровня приходят `WM_QUERYENDSESSION` и `WM_ENDSESSION` с `ENDSESSION_CLOSEAPP`. Наше скрытое окно (см. «Экземпляр сервиса») останавливает сервис мягко и пишет 1001 с причиной «обновление или удаление программы». Перед этим сервис регистрируется через `RegisterApplicationRestart` с пустой командной строкой и флагами `RESTART_NO_CRASH | RESTART_NO_HANG | RESTART_NO_REBOOT`, чтобы Restart Manager запустил его снова только после установки обновления. Без этих флагов Windows могла бы перезапускать процесс и после сбоя или зависания, и после перезагрузки для обновления системы — вдобавок к `Run`. Тихая установка и удаление везде выполняются с `/norestart`: без него `/qn` позволяет Windows Installer самому перезагрузить машину, а это оборвало бы проверку в CI и сеанс пользователя в филиале.

Что происходит с работающим экземпляром, зависит от того, кто ставит MSI. Пробная сборка (задача 1.6) показала при `/qn /norestart` три исхода, и все с кодом 0, файлы в папке совпадают с новым MSI по SHA-256:

| Кто ставит | Экземпляр | Итог |
|---|---|---|
| Тот же пользователь с повышением прав, его сеанс | `WM_ENDSESSION` с `ENDSESSION_CLOSEAPP`, через секунду новый процесс новой версии от того же пользователя в том же сеансе | Сервис обновился сам |
| Другой пользователь (администратор вводит свой пароль за оператора), тот же сеанс | Тот же `WM_ENDSESSION`, но снова не запускается | Сервис остановлен до следующего входа пользователя |
| SYSTEM (SCCM, GPO) | Не закрывается и сообщений не получает: занятые файлы переименовываются в `C:\Config.Msi`, их удаление отложено до перезагрузки | Старая версия работает до выхода пользователя, новая — со следующего входа. То же при удалении продукта |

Ни в одном случае процесс не запустился не от исходного пользователя и не в чужом сеансе, поэтому `RegisterApplicationRestart` остаётся. Кода 3010 в этих проверках не было, но он остаётся допустимым исходом: `REBOOT=ReallySuppress` скрывает потребность в перезагрузке, и другие условия на машине филиала могут её вернуть. README описывает все три исхода.

**Откат.** Два шага: удаление установленного продукта и установка нужного MSI из релиза на GitHub. Установка старого MSI поверх нового и MSI той же версии поверх установленного, в том числе другого филиала, отказывает с сообщением об этом, поэтому смена филиала без смены версии идёт так же. Сервис между шагами недоступен, но файлы гарантированно совпадают с прежним MSI, а откат — редкая операция. Файл сообщений при откате не меняется: компонент постоянный и при удалении остаётся, а установка прежнего MSI не заменяет файл более старой версией. Так и задумано: сохраняется новейшая таблица, она содержит все коды старых версий, потому что коды только добавляются, а смысл существующих не меняется. Поэтому сверка файлов после отката исключает `FilePickerAPI.messages.dll`.

**Подпись.** В MSI должны попасть уже подписанные файлы, а сейчас подпись идёт после сборки: `release.yml` скачивает неподписанные папки из джоба `build` и подписывает их в отдельном джобе `sign` (окружение `code-signing`). Поэтому релиз идёт тремя джобами. `sign` подписывает файлы, как сейчас. Новый джоб `msi` без окружения `code-signing` и без секретов скачивает подписанные папки, ставит WiX и собирает MSI каждого филиала: WiX из NuGet не должен работать рядом с сертификатом, а у `sign` к тому же есть только `.github/scripts`. Версия MSI берётся из тега, потому что Python и `app._version` там нет. Затем джоб `sign-msi` в окружении `code-signing` подписывает только готовые MSI тем же `sign.ps1` (скрипт расширяется на `*.msi`), и `release` публикует их. В `build-exe.yml` MSI собирается только для дымовой проверки и в релиз не идёт: из двух копий папки сборки вне `dist/`, подписанных одноразовым сертификатом. `dist/` и артефакт джоба `build` остаются неподписанными: на файлах с одноразовой подписью боевой `sign.ps1` остановил бы релиз. Копии и пробный MSI в артефакт не входят, а сам артефакт выкладывается после дымовой проверки.

### pywin32, без обёрток

Используются `win32api`, `win32con`, `win32security`, `win32evtlog`, `win32gui` и `win32com.shell` (`SHGetKnownFolderPath`). `GetExtendedTcpTable` и `RegisterApplicationRestart` в pywin32 не обёрнуты: их вызывает небольшой модуль `app/winapi.py` через `ctypes`. Он устроен как вызовы WinAPI в `app/handlers/files.py`: импортируется на любой ОС, библиотеки загружаются лениво, а разбор таблицы `MIB_TCPTABLE_OWNER_PID` — чистая функция над байтами. Поэтому покрытие 100% достигается и на Linux, тестами разбора и подменой вызовов. Тесты с пометкой `windows_only` дополнительно проверяют модуль на настоящем Windows (PID слушателя на занятом сокете). `pywin32` добавляется в `dependencies` с маркером `sys_platform == 'win32'` и точной версией. На Linux он не ставится. pip-audit на Windows и Dependabot его видят.

### Один режим exe, путь не принимается

`app/__main__.py` принимает только запуск без аргументов: работа сервиса (см. «Экземпляр сервиса»). Любые аргументы, в том числе пути и ключи, дают сообщение об использовании в stderr и код 2. Exe собирается с `--windows-console-mode=attach`: запущенный из `cmd` или PowerShell, он пишет журнал в эту консоль и останавливается по Ctrl+C, а запущенный при входе, двойным щелчком или `run_production.bat` работает без окна. Журнал при этом всегда пишется в файл, поэтому ошибку запуска видно и без окна. `python -m app` работает так же, в консоли.

У такого exe подсистема GUI, поэтому интерактивные `cmd` и PowerShell его не ждут: приглашение возвращается сразу, журнал перемешивается с вводом, а Ctrl+C в этой консоли останавливает и сервис. README поэтому советует для разбора ошибок `start /wait FilePickerAPI.exe` в `cmd`: он ждёт exe. Bat-файлы GUI-программу тоже ждут, и `run_test.bat` работает как раньше: exe пишет в его окно, после выхода exe скрипт доходит до `pause`, а по Ctrl+C `cmd` спрашивает `Terminate batch job (Y/N)?`. Всё это, как и остановка по Ctrl+C и запись события при закрытии окна консоли (`CTRL_CLOSE_EVENT`), подтверждено пробной сборкой (задача 1.5).

**Вне Windows.** `python -m app` на Linux и macOS остаётся способом разработки (README описывает его), а pywin32 там не ставится. Поэтому `app/runner.py` выбирает ветку по `sys.platform`, и ветка вне Windows не импортирует ни одного модуля pywin32:
- журнал — только в консоль: нет `SHGetKnownFolderPath`, файла журнала в `%LOCALAPPDATA%` и журнала событий; учёт повторов и коды событий работают как обычно, но записи уходят только в консоль;
- нет скрытого окна, `RegisterApplicationRestart`, `SetConsoleCtrlHandler` и проверки прав на папку сборки (1003);
- остановка — по `SIGINT` (Ctrl+C) и `SIGTERM`: обработчики сигналов в главном потоке вызывают ту же функцию остановки, что и `WM_CLOSE` на Windows, с обычной финализацией (до 20 секунд, напоминания, итоговая строка остановки);
- второй экземпляр, перезапуск HTTP-сервера при ошибке, ошибка настроек с кодом 1 и рабочая папка (для `python -m app` — текущая, как сейчас) — как на Windows.

Это проверяет отдельный процесс на Linux в CI без подмены модулей pywin32: `python -m app` запускается, отвечает на `/openapi.json`, по `SIGTERM` и по `SIGINT` завершается с кодом 0, а с `FILES_DIRECTORY` в `.env` — с кодом 1 и строкой об ошибке в выводе.

### Exe работает из своей папки, настройки читаются только при создании HTTP-приложения

Собранный exe первым делом переходит в папку, где лежит сам exe: `os.chdir`, а путь к exe берётся у Windows через `win32api.GetModuleFileName(None)`. Пробная сборка (#42) показала, что другие способы в сборке Nuitka не годятся: `sys.executable` указывает на несуществующий `python.exe` в той же папке (в короткой форме 8.3), а `__compiled__.containing_dir` — на папку выше папки сборки. Explorer запускает программы из `Run` с рабочей папкой профиля пользователя, поэтому без перехода сервис читал бы `.env` оттуда.

Для `.env` поведение не меняется: `run_test.bat` и `run_production.bat` тоже переходили в папку exe. Папка установки в `Program Files` доступна на запись только администраторам. Значит, `.env` рядом с exe (`CORS_ORIGINS`) задаёт только администратор, а `FILES_DIRECTORY` в нём по-прежнему не даёт сервису запуститься.

Перенести `import app` внутрь функции запуска недостаточно. Импорт любого модуля пакета (`app.logging_setup`, `app.runner`) сначала выполняет `app/__init__.py`, а сейчас он создаёт FastAPI-приложение и вызывает `get_settings()` для CORS. Ошибка в `.env` оборвала бы запуск до настройки журнала. Поэтому:
- `app/__init__.py` становится лёгким: ни FastAPI-приложения, ни чтения настроек при импорте пакета;
- приложение создаёт фабрика `create_app()` в модуле `app/api.py`. Только она вызывает `get_settings()`, и вызывается она в рабочем потоке сервиса после настройки журнала;
- `app.logging_setup`, `app.runner`, `app.permissions`, `app.event_tracking` и разбор аргументов в `app/__main__.py` не импортируют `app.api` и `app.settings` на уровне модуля;
- тесты и `reload_app` переходят на `app.api.create_app()`. `TestFilesDirectoryIsFixed` проверяет то же, что и раньше: путь по-прежнему берётся только из `app/_build_config.py`.

Тогда `ValidationError` из-за `FILES_DIRECTORY` в `.env` попадает в файл журнала и в журнал событий (1002), а сервис завершается с ошибкой, а не молча. Проверяется это отдельным процессом: тест запускает `python -m app` в папке с ошибочным `.env` и проверяет код выхода и запись в журнал (журнал событий — поддельный обработчик). Дымовая проверка повторяет это на установленном exe. Nuitka не выполняет `app/__init__.py` раньше кода `app/__main__.py` (проверено в #42), но лёгкий `app/__init__.py` всё равно нужен: модули пакета его импортируют.

### Проверка прав на папку сборки при запуске

Права на `Program Files` ставит Windows Installer, но их могли изменить потом. Поэтому при каждом запуске сервис проверяет папку своего exe, её содержимое и каждую папку-предка до корня тома. Доверенными считаются только `SYSTEM`, `BUILTIN\Administrators` и `NT SERVICE\TrustedInstaller`:
- **папка и её содержимое:** ни у кого, кроме доверенных, нет прав `FILE_WRITE_DATA`/`FILE_ADD_FILE`, `FILE_APPEND_DATA`/`FILE_ADD_SUBDIRECTORY`, `FILE_WRITE_EA`, `FILE_WRITE_ATTRIBUTES`, `DELETE`, `WRITE_DAC`, `WRITE_OWNER`, `GENERIC_WRITE`, `GENERIC_ALL`, а у директорий ещё и `FILE_DELETE_CHILD`;
- **каждый предок:** ни у кого, кроме доверенных, нет `DELETE`, `FILE_DELETE_CHILD`, `WRITE_DAC`, `WRITE_OWNER`, `GENERIC_ALL`. Право создавать папки (`FILE_ADD_SUBDIRECTORY`, есть у пользователей на `C:\`) не опасно;
- **владелец** каждого объекта доверенный;
- **точки повторной обработки:** каждый компонент пути открывается с `FILE_FLAG_OPEN_REPARSE_POINT`, junction или символическая ссылка — нарушение.

Учитываются только разрешающие ACE, которые действуют на сам объект; ACE «только для наследования» пропускаются. Запрещающие ACE не учитываются, и это ошибка в безопасную сторону. При нарушении сервис пишет событие 1003 с перечнем объектов, учётных записей и прав и продолжает работу: отказ запуска остановил бы приём платёжек в филиале. Проверка локальная и обращений к сетевой папке не добавляет.

Сравнение прав — отдельная чистая функция в `app/permissions.py`: на вход SID владельца, состояние DACL, ACE (маска, флаги) и набор доверенных SID-ов, на выход нарушения. Её можно проверить без Windows. Состояние DACL передаётся отдельно: отсутствующая или NULL DACL — нарушение «полный доступ у всех» до обхода ACE; пустая DACL — не нарушение.

### Экземпляр сервиса

Работа сервиса (exe без аргументов) устроена так:
1. Настраивается журнал (см. «Журнал»), ставятся обработчики остановки и создаётся скрытое окно верхнего уровня класса `FilePickerAPI.Instance` в отдельном потоке с циклом сообщений. Процесс без окна не получил бы сообщений о завершении сеанса и о закрытии от Restart Manager. Всё это идёт до опроса порта, потому что он длится до 10 секунд: остановка работает и в это время.
2. **Второй экземпляр.** Если порт 8000 уже занят, сервис несколько раз в течение 10 секунд запрашивает `http://127.0.0.1:8000/openapi.json` (без прокси): первый экземпляр может ещё запускаться. Опрос заканчивается раньше, как только порт освободился: тогда сервис сразу идёт к запуску. Запрос остановки тоже прерывает опрос, и это исход «остановка до старта слушателя» (см. «Буфер стартовых событий»). Если ответ — OpenAPI с заголовком `File Picker API`, сервис пишет в файл журнала строку «сервис уже работает» и завершается с кодом 0 без перезапусков. В журнал событий он пишет ровно одно событие: 1005 (сведения) «сервис уже работает» с PID владельца порта 8000 (`GetExtendedTcpTable`, права на чужой процесс для этого не нужны) и версией из ответа. Если версия из ответа не совпадает с собственной, вместо 1005 пишется 1006 (предупреждение). Так администратор видит, кто держит порт, даже если это посторонняя программа, которая выдаёт себя за File Picker API: раньше `run_production.bat` хотя бы писал `FAILED port 8000 is already in use`. Код филиала в ответе API не передаётся, поэтому сверяется только версия. Второй экземпляр запускается один раз на вход, поэтому ограничение повторов внутри процесса тут ничего не даёт: одно событие на вход — допустимый объём. Буфер стартовых событий (1000, 1003, 1004, 2004) у него по-прежнему отбрасывается. В консоли эта строка тоже видна. Проверка по процессу не подходит: процесс другого пользователя обычный пользователь открыть не может. Если ответил кто-то другой или никто — это ошибка HTTP-сервера (см. ниже). Порт может оказаться свободен на этом шаге и занят к моменту старта Uvicorn: два процесса запущены одновременно (два пользователя входят вместе или у пользователя остались и `Run`, и прежняя задача с `run_production.bat`). Поэтому сразу после ошибки привязки к порту (`WinError 10048`), до записи 1002, идёт короткая проверка: запросы к `/openapi.json` не дольше 3 секунд. Если порт занял File Picker API, процесс выходит с 1005 или 1006. Вне Windows PID не определяется: журнала событий там нет, а в консоль выводится «сервис уже работает» с версией, без вызова Windows API.
   Права на папку сборки (1003) проверяются после этого шага и в отдельном потоке, параллельно со стартом Uvicorn: второй экземпляр, который сразу завершится, их не проверяет, а обход сотен файлов standalone-сборки не задерживает начало приёма запросов при входе. Результат проверки (событие 1003) поток записывает только после того, как собственный слушатель Uvicorn запустился (`server.started`); если процесс выходит как второй экземпляр, результат отбрасывается.
3. Сервис вызывает `RegisterApplicationRestart` с флагами `RESTART_NO_CRASH | RESTART_NO_HANG | RESTART_NO_REBOOT` (см. «Обновление поверх работающего сервиса»).
4. Событие 1000: версия, филиал, директория, путь к exe, пользователь (`ДОМЕН\пользователь`) и способ запуска (консоль или без окна). Оно пишется, когда собственный слушатель Uvicorn запустился (`server.started`), а не перед стартом: иначе процесс, проигравший гонку за порт и вышедший как второй экземпляр, оставил бы 1000 без пары. Если сервер не запустился, вместо 1000 будет только 1002.
5. В рабочем потоке создаётся приложение (`create_app()`) и запускается `uvicorn.Server`. Директория создаётся (`ensure_files_directory`) в отдельном демоническом потоке параллельно со стартом Uvicorn: `mkdir` на недоступной UNC-папке может занять десятки секунд (таймауты SMB, по разу на уровень пути). Главный поток просто ждёт события завершения `threading.Event`, без опроса (см. «Завершение процесса»). Ctrl+C обрабатывается одним путём на платформу: на Windows — консольным обработчиком `SetConsoleCtrlHandler`, который для `CTRL_C_EVENT` и `CTRL_BREAK_EVENT` вызывает функцию остановки и возвращает TRUE (до обработчика Python, и `KeyboardInterrupt` не возникает); вне Windows — обработчиками сигналов `SIGINT` и `SIGTERM`.

**Буфер стартовых событий.** Пока исход запуска не ясен, события могут появиться не только от 1000 и проверки прав: настройка журнала пишет 1004, если файл журнала недоступен, а `ensure_files_directory` — 2004, если `mkdir` быстро отказал. Поэтому `EventLogHandler` до исхода запуска не пишет в журнал событий, а складывает записи в буфер в памяти; файл журнала и консоль получают их сразу. Момент старта отслеживает подкласс `uvicorn.Server`: у Uvicorn нет обратного вызова на старт, рабочий поток занят в `server.run()`, главный ждёт без опроса, а lifespan выполняется до привязки к порту. Подкласс переопределяет `startup()` и после `super().startup()`, если `self.started` истинно и остановка не запрошена, закрывает буфер и пишет 1000. При ошибке привязки `super().startup()` завершается `sys.exit`, и этот код не выполняется. При неудачном lifespan он возвращается штатно, но `self.started` остаётся ложным. Исходов четыре:
- собственный слушатель запустился (`server.started`) — буфер отправляется в журнал событий в порядке записей, дальше записи идут напрямую;
- запуск завершился ошибкой — буфер отправляется перед 1002;
- остановка запрошена до старта слушателя — накопленные предупреждения отправляются вместе с финализацией, перед 1001; 1000 и 1002 в этом случае нет;
- процесс выходит как второй экземпляр (в том числе после проигранной гонки за порт) — буфер отбрасывается, в журнале событий остаётся только 1005 или 1006 (см. шаг 2). Исключение — выход между повторными попытками: буфер уже отправлен перед первым 1002 (см. «Ошибка HTTP-сервера»).

Буфер ограничен 100 записями; сверх этого в него добавляется одна пометка о числе отброшенных, а сами записи остаются в файле журнала. Так отдельные отсрочки для 1000 и 1003 (шаги 2 и 4) становятся частными случаями буфера.

**Остановка.** Все сигналы вызывают одну идемпотентную функцию под `threading.Lock`: она запоминает причину, выставляет событие остановки и `server.should_exit`. Повторный сигнал остановку второй раз не запускает. Дальше два режима:
- **Обычный** — Ctrl+C в консоли (`CTRL_C_EVENT`, `CTRL_BREAK_EVENT`) и `WM_CLOSE`. Uvicorn завершается с `timeout_graceful_shutdown=10`, главный поток ждёт рабочий поток не дольше 20 секунд: обращения к SMB нельзя прервать изнутри процесса. Поток `ensure_files_directory` не ждём: зависшее создание директории не держит Uvicorn, а этот поток демонический, поэтому после рабочего потока достаточно проверить `is_alive()`. Затем финализация: ненулевые счётчики повторов сбрасываются напоминаниями, пишется ровно одно событие 1001 (причина и, если не завершился рабочий поток или ещё жив поток `ensure_files_directory`, пометка о незавершённом обращении к сетевой папке), обработчики журнала сбрасываются, процесс завершается через `os._exit(0)`. `os._exit` нужен, чтобы зависший поток пула не держал процесс.
- **Срочный** — когда Windows завершит процесс сразу после возврата из обработчика. Это закрытие окна консоли (`CTRL_CLOSE_EVENT`: Windows ждёт обработчик не дольше 5 секунд и завершает процесс после его возврата) и `WM_ENDSESSION` с `wParam = TRUE`. Обработчик не возвращается, пока не закончит остановку и финализацию: ожидание Uvicorn и рабочего потока не дольше 3 секунд, затем проверка `is_alive()` потока `ensure_files_directory`, напоминания, 1001, сброс журнала и `os._exit(0)` прямо из обработчика. Причина в 1001 берётся из сигнала: закрытие консоли; для `WM_ENDSESSION` по `lParam` — `ENDSESSION_CLOSEAPP` («обновление или удаление программы», это Restart Manager), `ENDSESSION_LOGOFF` («выход пользователя»), иначе «выключение Windows».

На `WM_QUERYENDSESSION` окно только отвечает «можно» и ничего не останавливает: выход из системы могут отменить (другая программа откажется закрываться), и тогда придёт `WM_ENDSESSION` с `wParam = FALSE`. На него сервис тоже ничего не делает и продолжает работать: остановленный сервис при отменённом выходе никто бы не запустил до следующего входа.

Сброс повторов при получении сигнала не годится: запросы во время мягкой остановки ещё могут завершаться с ошибками. Поэтому напоминания пишутся в финализации, после остановки сервера.

**Завершение процесса.** Событие, которое ждёт главный поток, выставляет не только функция остановки. Рабочий поток запоминает под тем же `threading.Lock` исход, и первый записанный исход выигрывает:
- остановка — финализация из раздела «Остановка», с 1001;
- сбой — ошибка настроек или исчерпанные попытки: рабочий поток уже записал напоминания и 1002, главный сбрасывает журнал и вызывает `os._exit(1)`, 1001 нет;
- второй экземпляр — 1005 или 1006 уже записано, главный сбрасывает журнал и вызывает `os._exit(0)`, 1001 нет.

**Ошибка HTTP-сервера** (порт 8000 занят не нашим сервисом, неудачный lifespan, исключение Uvicorn). Uvicorn при занятом порте пишет ошибку и вызывает `sys.exit`. В потоке это `SystemExit`: `except Exception` его не ловит, а `threading.excepthook` молча проглатывает. Тогда процесс жил бы без слушателя на порту 8000. Поэтому рабочий поток оборачивает `create_app()` и `server.run()` в `except BaseException`. При неудачном lifespan `sys.exit` делает только `uvicorn.run`, а `server.run()` просто возвращается, поэтому возврат из него без запрошенной остановки тоже считается ошибкой. Дальше:
- ошибка настроек (`ValidationError` из `create_app()`, например `FILES_DIRECTORY` в `.env`) — событие 1002 с причиной и трассировкой, напоминания о повторах, код выхода 1 без повторных попыток: они дали бы тот же результат;
- остальные ошибки — событие 1002 с причиной и номером попытки, затем новый `uvicorn.Server` через 10, 30 и 60 секунд (ожидание прерывается остановкой). Ошибка привязки к порту на любой попытке сначала проходит короткую проверку на второй экземпляр (шаг 2) и только потом считается сбоем. Если порт занял File Picker API, процесс завершается с кодом 0 и событием 1005 или 1006; после повторной попытки 1002 прежних попыток и отправленный буфер остаются в журнале, а это событие объясняет, чем всё закончилось. Отдельной проверки перед попыткой нет: привязка в этом случае упадёт сама. Ожидание 10, 30 и 60 секунд считается от конца предыдущей попытки, короткая проверка добавляет к нему не больше 3 секунд. После четвёртой неудачи подряд — напоминания и код выхода 1; событие 1002 о четвёртой попытке и есть последнее, в нём пометка «попытки исчерпаны», отдельного события нет. Успешная работа дольше часа сбрасывает счётчик попыток;
- если остановка уже запрошена, ошибка во время мягкой остановки сбоем не считается: она попадает пометкой в 1001, код выхода 0.

Uvicorn при неудачном старте сам пишет ошибку в `uvicorn.error` до `sys.exit`. Записи `uvicorn.error` уровня ERROR до `server.started` идут только в файл журнала, а их текст рабочий поток добавляет в 1002: одна ошибка запуска — одно событие.

Падение самого процесса (например, его завершил антивирус) никто не перезапустит до следующего входа; это видно по отсутствию события 1001 после 1000.

Uvicorn запускается через `uvicorn.Server(uvicorn.Config(...))`, а не `uvicorn.run`: остановка по `should_exit` нужна снаружи. `Config` получает `log_config=None`, чтобы Uvicorn не переписывал наши обработчики журнала. `host`, `port` и приложение те же, что сейчас.

### Журнал

Настройку журнала делает отдельный модуль `app/logging_setup.py`. Формат строк прежний: `%(asctime)s %(levelname)s %(name)s: %(message)s`.

- **Консоль.** Если exe запущен из консоли (или `python -m app`), корневой обработчик выводит в неё (stderr) с уровня INFO, Uvicorn пишет через него.
- **Файл.** Всегда, в том числе в консоли. Обработчик на основе `TimedRotatingFileHandler` пишет в `%LOCALAPPDATA%\FilePickerAPI\logs\FilePickerAPI.log` пользователя: ротация в полночь, UTF-8. `%LOCALAPPDATA%` берётся через `SHGetKnownFolderPath` (`FOLDERID_LocalAppData`), а не из переменной окружения. Вызов может отказать: в пробной сборке у процесса другого пользователя он вернул `E_ACCESSDENIED`. Такой отказ не роняет запуск, а считается недоступным файлом журнала (событие 1004). Папка в профиле пользователя: пишет в неё только он сам и администраторы, отдельной защиты не нужно. Срок хранения считается по возрасту, а не по количеству: `backupCount` ограничивает число архивов и не удалит один 60-дневный архив, оставшийся после отпуска. Поэтому подкласс переопределяет `getFilesToDelete`: архивы `FilePickerAPI.log.*` со временем изменения старше 30 дней. `doRollover` вызывает `getFilesToDelete` только при `backupCount > 0`, поэтому `backupCount` задаётся ненулевым и заведомо большим (1000): по количеству он ничего не ограничивает, а удаление по возрасту при ротации работает. Та же очистка выполняется при запуске, до первой ротации. Подкласс переживает открытого читателя: если файл открыт без `FILE_SHARE_DELETE` (например, `Get-Content -Wait`), переименование в полночь падает с `WinError 32`, а стандартный `doRollover` к этому моменту уже закрыл поток, не сдвинув `rolloverAt`, и каждая следующая запись снова пыталась бы ротировать и терялась. Поэтому при ошибке переименования подкласс заново открывает текущий файл на дозапись, продолжает писать в него и назначает следующую попытку через час; о неудаче пишется одна строка на эпизод. Ошибка удаления отдельного архива тоже глушится, и он удаляется при следующей очистке. Уровень INFO для `app`, `uvicorn.error` и `uvicorn.access` (журнал запросов с адресом клиента, методом, путём и кодом ответа). Второй экземпляр того же пользователя пишет в этот файл только одну строку перед выходом.
- **Журнал событий.** Если источник `FilePickerAPI` зарегистрирован (ключ `HKLM\SYSTEM\CurrentControlSet\Services\EventLog\Application\FilePickerAPI` есть; его создаёт MSI), обработчик `EventLogHandler` пишет в Application через `win32evtlog.ReportEvent` все записи с уровня WARNING от любых логгеров (`app`, `uvicorn.error`, необработанные исключения), кроме `uvicorn.access`. С уровнем INFO туда идут только записи с явным кодом события: запуск (1000), остановка (1001), восстановление папки (2001). Без MSI (распакованный архив, bat-скрипты) журнал событий не используется, чтобы не плодить события без текста: зарегистрировать источник сам сервис не может, у пользователя нет прав. Код события передаётся в записи журнала через `extra={"event_id": ...}`; у записи без кода — 4000 для ERROR и выше и 3001 («прочее предупреждение») для WARNING: код 3000 оставлен только ошибкам доступа к файлу, чтобы фильтр по нему не смешивал их с шумом из сети, чтобы ни одна ошибка не потерялась, даже если её источник не знает про коды. Записи без явного кода тоже идут через учёт повторов `app/event_tracking.py` с ключом «логгер + `record.msg`» (шаблон сообщения без подстановок) и тем же лимитом ключей. Иначе Uvicorn, который пишет в `uvicorn.error` с уровнем WARNING о данных из сети («Invalid HTTP request received.», «Unsupported upgrade request.», «Exceeded concurrency limit.»), давал бы отдельное событие 3001 на каждое соединение сканера портов: сервис слушает `0.0.0.0:8000`. Записи с флагом «только в файл» (`extra={"event_log": False}`) в журнал событий не идут вовсе. Трассировка исключения (`exc_info`) добавляется к тексту события. Стандартный `logging.handlers.NTEventLogHandler` не используется: он сам пытается зарегистрировать источник в реестре, а у пользователя нет на это прав, и у него один код на все события.
- **Ошибка записи в журнал событий** (журнал переполнен, служба EventLog остановлена) не должна ронять запрос: обработчик глушит её через `handleError`, запись остаётся в файле журнала.
- **Файл журнала недоступен на запись** (профиль на квоте, файл заблокирован). Сервис работает без файла и пишет событие 1004. Не принимать запросы из-за журнала было бы хуже.
- **Необработанные исключения запросов.** Обработчик исключений FastAPI для `Exception` пишет ERROR с кодом 4000, маршрутом и трассировкой и отвечает 500 как сейчас. Но часть непредвиденных ошибок до него не доходит: `_collect_file_info()` уже превращает любое исключение в `HTTPException(500, "Unexpected error when reading directory: …")`. После #41 обработчики `app/handlers/files.py` сами пишут такие ошибки в журнал: `logger.warning` об ошибке чтения директории, об ошибке чтения файла и о неразрешённом пути директории, `logger.exception` о непредвиденной ошибке списка. Без изменений `EventLogHandler` превратил бы их в события 3000 и 4000 в обход учёта повторов: 500 событий вместо одного при частых ошибках скачивания и второе событие 4000 рядом с событием обработчика `HTTPException`. Поэтому эти четыре вызова переводятся на учёт через `app/event_tracking.py`: в файл журнала по-прежнему пишется каждый случай, но с флагом «только в файл», а в журнал событий ошибка попадает один раз, через учёт повторов, и учтённое исключение помечается. Кроме того, `create_app()` регистрирует обработчик `HTTPException`. Для кода 500 и выше он пишет событие с исходной причиной (`exc.__cause__`) и её трассировкой, а затем вызывает стандартный `http_exception_handler`, так что ответ и `detail` не меняются. Код события зависит от причины: ошибка ОС учитывается через `app/event_tracking.py` (2000 или 3000, если она ещё не учтена там же), прочие исключения дают 4000. Чтобы одна ошибка не попала в журнал событий дважды, учтённое исключение помечается атрибутом: это делают `app/event_tracking.py` и оба обработчика, `Exception` и `HTTPException`. Пометку проверяет не только обработчик `HTTPException`, но и сам `EventLogHandler`. После обработчика `Exception` Starlette выбрасывает исключение дальше, и Uvicorn пишет его через `uvicorn.error` с `exc_info`. Для записи, у которой исключение в `exc_info` помечено, `EventLogHandler` не создаёт события, а в файл журнала она попадает как обычно. Остальные ошибки `uvicorn.error` (без пометки) по-прежнему дают событие, кроме ошибок запуска сервера, которые входят в 1002 (см. «Экземпляр сервиса»).

### Файл сообщений и отображение в Event Viewer

Event Viewer показывает текст события по таблице сообщений из DLL, указанной при регистрации источника (`EventMessageFile`). Если кода события в таблице нет, вместо текста пишется «Не найдено описание для события с кодом …», а наши строки видны только как вставки.

Поэтому в репозитории лежит `app/messages/FilePickerAPI.mc`: для каждого кода из спецификации (1000–1006, 2000–2004, 3000, 3001, 4000) текст сообщения — `%1`, то есть вся строка, которую передал сервис, плюс символическое имя для читаемости. В CI перед Nuitka `mc.exe -U` компилирует его в `.rc` с таблицей в Unicode (`-U` — сообщения в `.bin` в Unicode; `-u` означал бы, что сам `.mc` в UTF-16, а он в однобайтовой кодировке: тексты сообщений — ASCII, кириллица есть только в комментариях, которые `mc` копирует в заголовок `.h`), `rc.exe` — в `.res` (в `.rc` добавляется ресурс VERSIONINFO с версией продукта, чтобы Windows Installer заменял DLL при обновлении по версии), `link.exe /DLL /NOENTRY` — в ресурсную DLL без кода `FilePickerAPI.messages.dll`, которая копируется в папку сборки, подписывается вместе с остальными файлами и входит в MSI постоянным компонентом. `mc`, `rc` и `link` берутся из того же MSVC, что использует Nuitka (`--msvc=latest`), через `vswhere` и `vcvars64`. Таблица сообщений новой версии содержит все коды, поэтому старые события читаются и после обновления.

Решения по тексту события:
- Строка передаётся в `ReportEventW` (pywin32 вызывает Unicode-версию), поэтому кириллица сохраняется. Пробная сборка (#42) подтвердила это на раннере CI с английской локалью: `Get-WinEvent` вернул текст события с «ёЁ» побайтно. А вот текстовый вывод `wevtutil qe /f:text`, прочитанный из консоли, показал кириллицу вопросами: консоль перекодирует его в свою кодовую страницу. Поэтому кириллица проверяется только через `Get-WinEvent`, а `wevtutil` — только на отсутствие «Не найдено описание».
- Для ошибок ОС текст содержит путь, `winerror` и системное описание ошибки (`win32api.FormatMessage(winerror)`): по коду 53 администратор сразу видит «Не найден сетевой путь», а по 5 — «Отказано в доступе». Отказ в доступе к ресурсу означает, что у этого пользователя нет прав на сетевую папку: в тексте 1000 есть его имя.
- Длина одной вставки у `ReportEvent` ограничена 31 839 символами. Длиннее (например, огромная трассировка) — обрезается с пометкой «… (обрезано, полный текст в FilePickerAPI.log)».
- Уровень события: ERROR и выше — `EVENTLOG_ERROR_TYPE`, WARNING — `EVENTLOG_WARNING_TYPE`, INFO — `EVENTLOG_INFORMATION_TYPE`. Категории не используются.

### Учёт ошибок: повторы, состояние директории, медленная папка

Модуль `app/event_tracking.py` решает, что из ошибок отправить в журнал событий, и не делает обращений к файловой системе. Он получает от обработчиков `app/handlers/files.py` результат уже сделанного обращения: успех или исключение `OSError` с `winerror`.

- **Повторы.** Ключ повтора — код события и причина (для ошибок ОС — `winerror` и, для 3000, `fileId`). Первое событие с ключом пишется сразу, следующие только считаются. Накопленный счётчик отправляет таймер, а не следующий запрос: демонический поток раз в минуту просматривает ключи, и если с последней записи по ключу прошёл час и счётчик не нулевой, пишет напоминание с числом повторов и обнуляет счётчик. Ключ без повторов в течение часа после последней записи закрывается без события. Число активных ключей ограничено: не больше 50 на код события. Иначе при отказе доступа к папке каждый новый `fileId` давал бы свой ключ 3000 и сразу своё событие, и память и журнал Application росли бы с числом разных имён в запросах. Ошибка с новым ключом сверх лимита учитывается в одном общем ключе переполнения этого кода, без `fileId` и `winerror`: иначе число таких ключей росло бы с числом разных причин. Ключ переполнения хранит только число ошибок, без множества имён, поэтому его память постоянна даже при часовом потоке новых `fileId`. Первое переполнение даёт одно событие с пометкой, что дальнейшие ошибки этого кода объединяются, затем — напоминания по таймеру не чаще раза в час с числом ошибок. Подробности каждого случая, включая `fileId` и `winerror`, есть в файле журнала. После закрытия ключа следующая такая же ошибка снова пишется сразу как первая. При остановке ненулевые счётчики сбрасываются напоминаниями перед событием 1001 (или 1002, если процесс завершается с ошибкой). Так ни один повтор не остаётся без отражения в журнале событий: он попадает либо в напоминание по таймеру, либо в итог при остановке. Для директории итог даёт и событие 2001 (см. ниже). В файл журнала пишется каждый случай с уровнем WARNING без отправки в журнал событий (флаг в `extra`). Часы — `time.monotonic`, в тестах подменяются вместе с тактом таймера.
- **Состояние директории.** Хранится последнее состояние: доступна или недоступна с причиной, время начала и счётчик ошибочных ответов. Переход в «недоступна» и смена причины — событие 2000. Пока недоступна — напоминание 2002 раз в час с числом ошибочных ответов с прошлой записи: его пишет тот же такт таймера, новых запросов не нужно; если ответов не было, напоминания нет. При остановке недоступной папки финализация пишет итоговое 2002 с этим числом и длительностью перед 1001 или 1002, иначе повторы потерялись бы: 2001 в этом случае уже не будет. Первый успешный ответ после недоступности — 2001 с длительностью и общим числом ошибочных ответов. Обновление под `threading.Lock`: обработчики работают в пуле потоков.
- **Сетевые ошибки при скачивании.** Если `lstat()` или поиск имени файла упал с сетевым `winerror` (53, 64, 67, 1219, 1222, 1311, 2250 и подобные из списка в модуле) — это недоступность директории (2000), а не 3000. `winerror` 2 и 3 при доступной папке — обычный 404 без события. Остальные ошибки доступа к файлу (403, 500) — 3000.
- **Медленная папка.** Обработчики списка и скачивания замеряют своё время (`time.monotonic` до и после обращений к ФС). Больше 10 секунд — событие 2003 с маршрутом и длительностью, с тем же ограничением повторов (ключ — маршрут). Дополнительных обращений к сетевой папке замер не делает.
- **Тело скачиваемого файла.** `get_file()` возвращает ответ раньше, чем файл открыт и прочитан: Starlette читает его уже после обработчика. Поэтому скачивание отдаёт `TrackedFileResponse` — подкласс `FileResponse`, который оборачивает отправку тела (`__call__`). Он замеряет время от начала отправки до конца: открытие и чтение файла по SMB плюс передача клиенту. Если обработка вместе с отправкой длилась больше 10 секунд — событие 2003 с маршрутом `GET /files/{fileId}`. При `OSError` во время открытия или чтения ошибка учитывается так же, как ошибки обработчика: сетевой `winerror` — недоступность директории (2000), прочие — 3000. Затем исключение пробрасывается: заголовки уже отправлены, и клиент получает оборванный ответ, как и сейчас. Время передачи медленному клиенту тоже попадает в замер, поэтому в тексте 2003 для скачивания указывается размер файла: администратор отличит медленную папку от медленной сети клиента. Новых обращений к ФС обёртка не делает: читает тот же файл, что и `FileResponse`.
- **Директория при запуске.** Ошибка `mkdir` в `ensure_files_directory` — событие 2004 с путём и ошибкой Windows.

Почему не каждое событие отдельно: фронтенд опрашивает список каждые несколько секунд, и за час недоступности папки в Application были бы тысячи одинаковых записей. Они вытеснили бы другие события (журнал Application по умолчанию 20 МБ с перезаписью), а администратор не увидел бы, когда проблема началась и закончилась. С ограничением повторов ничего не теряется: число повторов есть в напоминаниях и в событии восстановления, а каждый случай — в файле журнала.

В журнале нет ничего, чего нет в API: имена файлов и адреса клиентов. Содержимое файлов в журнал не пишется. Журнал событий Application читают все пользователи машины: это нужно для разбора проблем на месте без прав администратора.

### Тесты без Windows и проверка на Windows в CI

- Модули pywin32 импортируются лениво, внутри функций `app/runner.py`, `app/permissions.py` и `app/logging_setup.py`. Тесты подставляют поддельные модули через `sys.modules`. Так на Ubuntu и Windows проверяются: второй экземпляр, остановка, перезапуск HTTP-сервера, разбор аргументов и обработка ошибок. Покрытие 100% сохраняется на обеих платформах.
- Проверка прав (чистая функция) тестируется на наборах ACE: NULL или отсутствующая DACL у папки, файла или предка при доверенном владельце — нарушение; пустая DACL — не нарушение; `FILE_DELETE_CHILD` на папке сборки или её подпапке без `DELETE` на файлах; `WRITE_DAC` или чужой владелец у предка; право удаления у предка вида `C:\Users\alice\container`; ACE «только для наследования» и право создания папок на `C:\` — без нарушения. На Windows-джобе дополнительно (с пометкой `windows_only`) — настоящие временные папки с `icacls` и junction в пути.
- Второй экземпляр: поддельный сервер на занятом порте, отвечающий OpenAPI `File Picker API`, — код 0, строка в файле журнала и одно событие 1005 с PID владельца порта; другая версия в ответе — 1006; другой ответ или его отсутствие — 1002; первый экземпляр отвечает только с третьей попытки — всё равно код 0; порт освободился во время опроса — запуск сразу и без 1002; остановка во время опроса — опрос прерывается, 1001 и накопленные предупреждения в журнале событий, 1000 и 1002 нет; порт свободен при проверке, но занят File Picker API к моменту старта Uvicorn (ошибка привязки) — код 0 и только 1005 (ни 1000, ни 1003, ни 1002), даже если права на папку сборки нарушены; второй экземпляр, вышедший до проверки прав, её не выполняет.
- Остановка: тест с подменённым `ensure_files_directory`, который блокируется до конца теста, и поддельным `os._exit` проверяет, что `WM_CLOSE` в этот момент приводит к ровно одному событию 1001 с пометкой о незавершённом обращении и вызову `os._exit` не позже чем через 20 секунд по поддельным часам. `CTRL_CLOSE_EVENT` и `WM_ENDSESSION` с `wParam = TRUE` — напоминания, 1001 с нужной причиной (закрытие консоли; обновление или удаление программы; выход пользователя; выключение Windows) и `os._exit` до возврата из обработчика, ожидание не дольше 3 секунд. `WM_QUERYENDSESSION`, а затем `WM_ENDSESSION` с `wParam = FALSE` (отменённый выход) — сервис продолжает отвечать, событий нет. Повтор ошибки во время мягкой остановки попадает в итоговое напоминание до 1001. Зависший `ensure_files_directory` при уже остановленном Uvicorn тоже даёт пометку в 1001. Остановка до старта Uvicorn: сервер не создаётся, накопленные предупреждения и 1001 попадают в журнал событий, 1000 и 1002 нет. Два сигнала подряд — одна остановка.
- Ошибка HTTP-сервера: тест «порт занят» с настоящим `uvicorn.Server` на заранее занятом сокете, который не отвечает OpenAPI (подделка не бросила бы `SystemExit`): после накопленных повторов — напоминание, затем 1002 с текстом Uvicorn и номером попытки, ни одного 4000; на поддельных часах попытки через 10, 30 и 60 секунд и код выхода 1 после четвёртой; порт освободился ко второй попытке — сервис работает; порт занял File Picker API между попытками — код 0, 1002 первой попытки и затем 1005, без 1001; работа дольше часа сбрасывает счётчик. `FILES_DIRECTORY` в `.env` — одно 1002 и код 1 без повторов и без 1001: проверяется, что процесс завершился, а не остался ждать. Исключение во время мягкой остановки после `WM_CLOSE` — одно 1001 с пометкой, код 0.
- `installer/FilePickerAPI.wxs` проверяется тестом как XML: платформа x64; папка установки в `ProgramFiles64Folder` с непубличным идентификатором; значение `Run` в `HKLM` с путём в кавычках без аргументов; `util:EventSource` и файл сообщений в постоянных компонентах; `MajorUpgrade` с `Schedule="afterInstallInitialize"` и `DowngradeErrorMessage`, без `AllowSameVersionUpgrades` и `AllowDowngrades`; `Upgrade` с `OnlyDetect` на ту же версию и условие запуска; нет пользовательских действий; нет bat-скриптов. Функция перевода версии `app._version.version` в `ProductVersion` проверяется на релизных и промежуточных версиях и на выходе за ограничения.
- Ошибочный `.env` проверяется отдельным процессом `python -m app` (код выхода, запись в журнал), а импорт `app.runner` и `app.logging_setup` при ошибочном `.env` — без исключения.
- Срок хранения: во временной папке один архив `FilePickerAPI.log.<дата>` со временем изменения 60 дней назад и пять свежих — при запуске и при ротации удаляется только старый, хотя архивов меньше 30.
- Напоминания по таймеру: на поддельных часах 500 ошибок 3000 за минуту, затем ни одного запроса — через час такт таймера даёт напоминание с числом 499; ключ без повторов закрывается без события; при остановке ненулевой счётчик уходит в итоговое напоминание до 1001.
- Скачивание: `TrackedFileResponse` с поддельным чтением, которое ждёт по поддельным часам 15 секунд, даёт 2003 с размером файла. С чтением, которое падает сетевым `winerror`, даёт 2000, с прочей `OSError` — 3000.
- Журнал событий в pytest проверяется с поддельным `win32evtlog`: какой код, тип и текст получает `ReportEvent` для каждого события из спецификации; трассировка в тексте; обрезка длинного текста; `winerror` и его описание; что `uvicorn.access` не попадает; что ошибка `ReportEvent` не роняет запрос; что без зарегистрированного источника событий нет. Отдельный тест сверяет, что каждый код из `app/event_tracking.py` есть в `FilePickerAPI.mc` и наоборот, — иначе Event Viewer показал бы «Не найдено описание».
- Реальную установку и работу проверяет дымовой скрипт `.github/scripts/msi-smoke.ps1` в джобе `build` сразу после сборки MSI. Раннер GitHub работает от пользователя с правами администратора, но без интерактивного входа, поэтому вход пользователя скрипт заменяет запуском exe без аргументов (`Start-Process`). Скрипт:
  1. выполняет `msiexec /i FilePickerAPI-<филиал>.msi /qn /norestart /l*v` — код 0; проверяет файлы в `C:\Program Files\FilePickerAPI\`, значение `FilePickerAPI` в `HKLM\…\Run` (путь в кавычках, без аргументов), регистрацию источника `FilePickerAPI` с `EventMessageFile` на `FilePickerAPI.messages.dll` в папке установки, отсутствие bat-скриптов;
  2. запускает установленный exe без аргументов; проверяет, что `GET /openapi.json` отдаёт версию сборки, а `GET /files` отвечает 404 `Files directory not found`, потому что UNC-путь филиала с раннера недоступен;
  3. проверяет, что в `%LOCALAPPDATA%\FilePickerAPI\logs\FilePickerAPI.log` есть строка запуска с пользователем раннера и предупреждение о директории;
  4. запускает exe второй раз — процесс завершается с кодом 0 за 15 секунд, в файле журнала строка «сервис уже работает», в журнале событий одно 1005 с PID первого экземпляра и нет 1002; запуск с аргументом `D:\x` — код 2;
  5. останавливает экземпляр сообщением `WM_CLOSE` его скрытому окну — процесс завершается, в журнале событий 1001;
  6. кладёт в папку установки `.env` с `CORS_ORIGINS`, собирает второй MSI того же филиала с версией на единицу больше из копии папки сборки, в которой у exe и DLL сообщений другая версия в ресурсах (копия делается до пробной подписи: правка ресурсов сделала бы подпись недействительной, а `sign.ps1` на этом останавливается; версия правится в `VS_FIXEDFILEINFO` через `UpdateResource` из pywin32, отдельная утилита не нужна, и `sign.ps1` принимает такой файл; обе папки затем подписываются). Копия отличается только ресурсами: версия приложения в `app._version` вшита при компиляции, поэтому `/openapi.json` у обоих MSI отдаёт одну версию, и обновление дальше проверяется по SHA-256 и `FILEVERSION` файлов, а не по ответу API. Скрипт ставит его поверх остановленного сервиса: код 0; `.env`, значение `Run` и источник событий на месте. Сервис остановлен, потому что при коде 3010 замена отложена до перезагрузки, а на раннере её нет, и сверка показала бы старые файлы. SHA-256 каждого файла в папке установки, кроме `.env`, совпадает с содержимым второго MSI; затем скрипт проверяет, что установка первого MSI поверх второго отказывает и что отказывает заново собранный второй MSI той же версии (другой `ProductCode`), выполняет откат (`msiexec /x` второго и `msiexec /i` первого, оба `/qn /norestart`), проверяет, что `.env` на месте, и так же сверяет с первым MSI все файлы, кроме `FilePickerAPI.messages.dll`: он остаётся от второго MSI (см. «Откат»), и события читаются полностью. Сборка той же версии с теми же файлами этого бы не показала: при `MajorUpgrade` решение о замене файла принимается до удаления прежнего продукта, и при совпадающих или более новых версиях файлов возможен неполный набор;
  7. занимает порт 8000 другим процессом и запускает exe — в журнале событий 1002 о первой попытке; затем освобождает порт — сервис отвечает до третьей попытки; останавливает его;
  8. кладёт в папку установки `.env` с `FILES_DIRECTORY` и запускает exe — процесс завершается с кодом 1 без повторных попыток; `.env` удаляется;
  9. выдаёт `Users` право записи на папку установки, запускает exe — событие 1003 с перечнем; права возвращаются, экземпляр останавливается;
  10. читает события источника `FilePickerAPI`, записанные с начала проверки, двумя способами: `Get-WinEvent` (свойство `Message` формируется по таблице сообщений, как в Event Viewer) и `wevtutil qe Application /f:text`. Для событий 1000, 2004, 2000, 1001 и 1002 проверяются код, уровень (`LevelDisplayName`/`Level`) и текст: нет фразы «description for Event ID» / «Не найдено описание»; есть версия сборки, UNC-путь филиала и имя пользователя раннера; у 2000 и 2004 есть код ошибки Windows и его описание; у 1002 есть `FILES_DIRECTORY` и трассировка; русские фрагменты в `Message` из `Get-WinEvent` совпадают побайтно с ожидаемыми; вывод `wevtutil` проверяется только на отсутствие «Не найдено описание», потому что консоль искажает в нём кириллицу. Тексты событий выводятся в лог джоба;
  11. запускает exe и ставит второй MSI поверх работающего экземпляра от того же пользователя: код 0 или 3010; `.env`, значение `Run` и источник событий на месте. При коде 0 файлы сверяются со вторым MSI, в журнале событий 1001 «обновление или удаление программы», а exe снова работает: порт 8000 держит новый процесс (другой PID, образ из папки установки с `FILEVERSION` второго MSI), и он отвечает на `/openapi.json` и `GET /files`. Версию в ответе API шаг не сравнивает со вторым MSI (см. шаг 6). Ожидание `msiexec` идёт без `Start-Process -Wait`: он ждёт и дочерние процессы, а перезапущенный exe работает, пока его не остановят, поэтому проверка зависла бы;
  12. останавливает экземпляр через `WM_CLOSE`, откатывается к первому MSI, как на шаге 6, запускает exe и ставит второй MSI от SYSTEM разовой задачей Планировщика, как SCCM: код 0 или 3010. При коде 0 файлы в папке установки совпадают со вторым MSI по SHA-256. При 3010 замена может быть отложена до перезагрузки, поэтому сверки нет. Вместо неё проверяется, что каждый файл в папке установки совпадает с первым или со вторым MSI, а в `PendingFileRenameOperations` есть записи о замене файлов из папки установки. В обоих случаях прежний процесс с тем же PID работает, 1001 нет. Затем через него идут несколько запросов: `/openapi.json`, `GET /files` (404 `Files directory not found`) и `GET /files/<несуществующий>`; все отвечают как до установки, в файле журнала нет ошибок загрузки модулей и DLL. Так проверяется, что старый процесс не подгружает новые файлы. После этого экземпляр останавливается через `WM_CLOSE` с 1001;
  13. выполняет `msiexec /x … /qn /norestart` — код 0 или 3010, если предыдущие шаги отложили замену; значения `Run` нет, файл сообщений и регистрация источника остались, событие 1000 по-прежнему читается полностью;
  14. запускает `run_test.bat` из папки сборки (архива) — сервис отвечает.

## Risks / Trade-offs

- **Nuitka и pywin32 — проверено пробными сборками.** Nuitka 4.3.1 на Python 3.11 сама включила модули pywin32, которые импортируются в коде, `pywintypes311.dll` и `_win32sysloader`, а также `win32gui` и `win32com.shell`. Ключ `--include-module` понадобился только для `win32timezone`.
- **Обновление через SCCM или GPO при работающем сервисе.** Старая версия работает до выхода пользователя, а файлы на диске уже новые. → Импорты pywin32 ленивые, но все они выполняются при запуске, поэтому старый процесс не подхватит новые модули; `TrackedFileResponse`, обработчики и `win32api.FormatMessage` модулей не догружают. Реализация сохраняет это свойство, а дымовая проверка (шаг 12) отправляет запросы старому процессу после замены файлов. Своих действий MSI от SYSTEM, которые закрывали бы экземпляры в сеансах пользователей, нет (решение мейнтейнера в #37). Обновление вступает в силу при следующем входе, README это описывает и советует ставить обновления вне рабочего времени.
- **Обновление, которое ставит другой пользователь.** Сервис останавливается и не поднимается до следующего входа оператора. `RegisterApplicationRestart` остаётся: без него не перезапускался бы и случай, когда оператор обновляет сам (решение мейнтейнера в #37). → README явно говорит, что сервис после такого обновления не работает, пока оператор не запустит `FilePickerAPI.exe` сам или не войдёт заново.
- **Перезапуск после сбоя.** На раннере перезапуска не было и с флагами, и в контрольном запуске без флагов, поэтому отсутствие перезапуска с `RESTART_NO_CRASH` проверкой не доказано. Решение опирается на документацию Windows, отдельная проверка не планируется (решение мейнтейнера в #37). Худший случай — после сбоя процесс поднимется второй раз и завершится как второй экземпляр.
- **`.env` администратора при обновлении** — Windows Installer не удаляет файлы, которые не ставил. Пробная сборка это подтвердила при обновлении, откате и смене филиала, дымовая проверка повторяет.
- **Выход пользователя из системы** проверить в CI нельзя: у раннера нет интерактивного входа. Обработка `WM_ENDSESSION` и `CTRL_CLOSE_EVENT` тестируется поддельными сообщениями, а в филиале проверяется вручную (Workflow follow-up). Если Windows завершит процесс раньше, не будет только 1001 и итоговых напоминаний; каждый случай остаётся в файле журнала.
- **Остановка через `os._exit`** не выполняет `finally` и обработчики `atexit` в зависших потоках. → Перед ним сбрасываются обработчики журнала; других ресурсов, требующих закрытия, у сервиса нет (он только читает файлы).
- **Политики, которые отключают `HKLM\…\Run`.** Групповая политика «Не обрабатывать список автозапуска для старых версий» (`DisableLocalMachineRun`) запрещает Explorer запускать программы из этого ключа; тогда MSI ставится с кодом 0, а сервис при входе не запускается и событий не пишет. Кроме того, Explorer запускает элементы `Run` с небольшой задержкой после входа. → README описывает проверку (`gpresult /h`, параметр `DisableLocalMachineRun` в `HKLM\Software\Microsoft\Windows\CurrentVersion\Policies\Explorer`), она есть в ручной проверке в филиале; если политика включена, это решение администраторов домена.
- **Автозапуск у всех пользователей машины.** Выключить его для одного пользователя нельзя без администратора. → Для машин филиала, за которыми работает оператор, это не нужно; второй экземпляр тихо завершается.
- **Сервис уходит вместе с первым пользователем.** Если на машине работают двое и первый выходит, сервис останавливается и не поднимется у второго до его следующего входа. → README описывает; для машин филиала это редкий случай.
- **Версии MSI.** Только `X.Y.Z` (≤255.255.65535); промежуточные сборки получают версию следующего релиза и поверх друг друга не ставятся, нужно удалить продукт. Смена филиала без смены версии делается так же. → На машинах филиала промежуточных сборок нет, а смена филиала редка; различить сборки можно по полной версии в событии 1000.
- **Откат медленнее, чем у своей раскладки:** нужны удаление продукта и прежний MSI, и между шагами сервиса нет. → MSI лежит в релизе на GitHub; откат — редкая операция.
- **Новый инструмент в CI.** WiX 5.0.2 закреплён точной версией в `.config/dotnet-tools.json`. Dependabot ненадёжно обрабатывает репозиторий, где из .NET есть только манифест инструментов (dependabot-core#9408), поэтому WiX обновляется вручную: перед повышением версии проверяются лицензионные условия (начиная с WiX 6 для коммерческого использования может действовать Open Source Maintenance Fee) и исправления безопасности (решение мейнтейнера в #37).
- **Сборка файла сообщений.** `mc.exe`, `rc.exe` и `link.exe` нужны в CI до Nuitka; на `windows-latest` они есть в Visual Studio Build Tools, но не в `PATH`. → Окружение берётся через `vswhere` и `vcvars64.bat` так же, как его находит Nuitka; при отсутствии инструмента сборка падает, а дымовая проверка событий ловит DLL без нужных кодов.
- **Без MSI нет журнала событий.** Если сборку запускают по-старому (bat-скрипты), источник может быть не зарегистрирован, и ошибки пишутся только в файл журнала. → Это переходный период до перевода филиала.
- **Ограничение повторов скрывает точную картину в журнале событий.** → Каждый случай есть в файле журнала, а число повторов — в напоминаниях 2002 и в итоговом 2001.
- **Сетевые `winerror` перечислены списком.** Ошибка, которой нет в списке, при скачивании даст 3000 вместо 2000. Это ошибка в безопасную сторону. Список дополняется по результатам проверки в филиале.
- **Подпись.** Файлы pywin32 (`.pyd`, `pywintypes311.dll`) не подписаны. `sign.ps1` подпишет их как неподписанные: это штатное поведение. Дополнительно подписывается MSI.
- **Проверка прав не учитывает запрещающие ACE и членство в группах.** Ошибка тут в безопасную сторону: лишнее предупреждение 1003.
- **Обратная совместимость.** Изменение совместимое: exe без аргументов работает как раньше, поэтому `run_production.bat`, `run_test.bat` и прежние задачи Планировщика работают с новой сборкой из архива без изменений. Несовместимым будет только `remove-bat-scripts`.
- **MSI и прежняя задача с `run_production.bat` у одного пользователя.** Если прежнюю забыть удалить, при входе запустятся оба; второй экземпляр тихо завершится, а `run_production.bat` запишет `FAILED`, если порт уже занят. → README напоминает удалить прежнюю задачу или ярлык.

## Migration Plan

Филиалы переводятся по одному, в удобное время: до перевода новая сборка из архива работает со старыми bat-скриптами. На машине:
1. Пользователь закрывает прежний сервис (окно или `run_production.bat`) и удаляет свою задачу Планировщика или ярлык с `run_production.bat`, если они есть.
2. Администратор ставит `FilePickerAPI-<филиал>.msi` вручную, через GPO или SCCM. Если рядом с прежним exe лежал `.env` с `CORS_ORIGINS`, администратор кладёт его в `C:\Program Files\FilePickerAPI\`.
3. Со следующего входа пользователя сервис запускается сам; сразу — запуском `C:\Program Files\FilePickerAPI\FilePickerAPI.exe`. Права на сетевую папку не меняются: сервис работает от имени того же пользователя, что и раньше.

Обновление версии: администратор ставит MSI новой версии тем же способом. `.env` остаётся на месте.

Откат версии и смена филиала той же версии: удаление продукта и установка нужного MSI из релиза. Установка старого MSI или MSI той же версии поверх установленного отказывает. Откат на схему с bat-скриптами: удаление продукта в «Программах и компонентах» и прежняя задача или ярлык с `run_production.bat` из архива — скрипты есть в нём, пока не выполнено `remove-bat-scripts`.

Когда переведены все машины, отдельным изменением `remove-bat-scripts` (BREAKING, версия 3.0.0) из репозитория и архива удаляются `run_test.bat` и `run_production.bat`, а из спецификации `distribution` — требование «Скрипты запуска для Windows».
