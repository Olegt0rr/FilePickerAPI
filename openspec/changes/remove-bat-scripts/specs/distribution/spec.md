## MODIFIED Requirements

### Requirement: Сборка для Windows
Проект SHALL собираться через Nuitka в режиме standalone: папка `FilePickerAPI` с `FilePickerAPI.exe` и его зависимостями (включая модули pywin32 и файл сообщений, см. `user-logon-autostart`), которая запускается без установленного Python. Bat-скрипты в папку сборки MUST NOT входить. Из папки SHALL собираться MSI (см. `user-logon-autostart`, «Установка MSI»). Под каждый филиал из `branches.toml` SHALL собираться своя папка и свой MSI. Режим onefile MUST NOT использоваться: он распаковывает неподписанные файлы во временную папку пользователя, что несовместимо с подписью и WDAC/AppLocker. Сборка SHALL выполняться в CI только после успешного прохождения линтера и тестов, и каждый MSI SHALL проверяться в CI установкой и запуском на Windows.

#### Scenario: Сборка в CI
- **WHEN** в ветку `main`/`master` отправлен коммит или открыт pull request в одну из этих веток
- **THEN** CI запускает ruff и pytest на Linux и pytest на Windows. Если они прошли, CI собирает папку `FilePickerAPI` и MSI на Windows для каждого филиала из `branches.toml`, проверяет MSI дымовой проверкой и публикует как артефакт `FilePickerAPI-<филиал>` (например, `FilePickerAPI-5400`)

#### Scenario: Тесты упали
- **WHEN** линтер или тесты завершились с ошибкой
- **THEN** сборка не выполняется

#### Scenario: Путь филиала в сборке
- **WHEN** CI собирает папку филиала 5400
- **THEN** перед компиляцией CI сверяет записанный путь с `files_directory` филиала 5400 в `branches.toml`, и при расхождении сборка падает; сборки филиалов отличаются только зашитой директорией с файлами

#### Scenario: Ошибка в списке филиалов
- **WHEN** `branches.toml` не проходит проверку (см. «Список филиалов»)
- **THEN** джоб с тестами падает с сообщением о причине, и ни одна сборка не выполняется

#### Scenario: Дымовая проверка MSI
- **WHEN** CI собрал MSI филиала на Windows-раннере
- **THEN** CI проверяет по порядку:
  - `msiexec /i … /qn /norestart` завершается с кодом 0, сборка лежит в `C:\Program Files\FilePickerAPI\` без bat-скриптов, значение `FilePickerAPI` в `HKLM\…\Run` указывает на exe в кавычках без аргументов, источник `FilePickerAPI` зарегистрирован;
  - запущенный exe отвечает: `GET /openapi.json` отдаёт версию сборки, `GET /files` — 404 `Files directory not found`;
  - в файле журнала пользователя и в журнале событий есть событие запуска, после остановки — событие остановки;
  - второй запуск завершается с кодом 0 без события ошибки, запуск с аргументом — с кодом 2;
  - MSI следующей версии с другим exe ставится поверх работающего сервиса, все файлы в папке установки совпадают с ним по SHA-256, `.env` администратора остаётся на месте, а откат на первый MSI возвращает его файлы;
  - при порте 8000, занятом другой программой, пишется ошибка, а после освобождения порта сервис запускается;
  - с `.env`, где указан `FILES_DIRECTORY`, сервис не запускается;
  - при праве записи `Users` на папку установки пишется предупреждение;
  - `msiexec /x … /qn /norestart` завершается с кодом 0, значения `Run` нет, а текст прошлых событий читается.

  При любой неудаче сборка падает, и артефакт не публикуется

#### Scenario: Проверка событий в журнале событий
- **WHEN** дымовая проверка прошла сценарии запуска, недоступной папки филиала (при создании директории и при `GET /files`), остановки и отказа запуска из-за `.env`
- **THEN** CI читает события источника `FilePickerAPI` через `Get-WinEvent` (тот же текст, что показывает Event Viewer) и проверяет коды 1000, 2004, 2000, 1001 и 1002, их уровни, полный текст и кириллицу без искажений, а через `wevtutil qe /f:text` — что нет «Не найдено описание для события»; при расхождении сборка падает

#### Scenario: Нет bat-скриптов в сборке
- **WHEN** CI собрал папку филиала
- **THEN** в папке нет файлов `*.bat`

### Requirement: Автоматический релиз
При публикации тега вида `vX.Y.Z` из цифр SHALL создаваться GitHub Release, к которому для каждого филиала из `branches.toml` прикреплены архив `FilePickerAPI-<филиал>.zip` с подписанной папкой сборки этого филиала и подписанный `FilePickerAPI-<филиал>.msi`, собранные из этого тега после успешного прохождения тестов и дымовой проверки. Теги с суффиксом (например, `v3.0.0-rc1`) MUST NOT создавать релиз.

#### Scenario: Публикация тега
- **WHEN** в репозиторий отправлен тег `v3.0.0`
- **THEN** создаётся релиз `v3.0.0` с архивами `FilePickerAPI-5000.zip`, `FilePickerAPI-5100.zip` и `FilePickerAPI-5400.zip` (внутри каждого папка `FilePickerAPI` с подписанным `FilePickerAPI.exe` своего филиала и его зависимостями, без bat-скриптов) и подписанными `FilePickerAPI-5000.msi`, `FilePickerAPI-5100.msi` и `FilePickerAPI-5400.msi` версии `3.0.0`

#### Scenario: Предварительная версия
- **WHEN** в репозиторий отправлен тег `v3.0.0-rc1`
- **THEN** релиз не создаётся

## REMOVED Requirements

### Requirement: Скрипты запуска для Windows
**Reason**: `run_test.bat` и `run_production.bat` заменены установкой MSI с запуском при входе пользователя (см. `user-logon-autostart`), и все филиалы на неё переведены. Логика запуска на cmd не тестируется автоматически и даёт риск подмены системных утилит и файлов сборки.
**Migration**: на машине, где сервис всё ещё запускается через `run_production.bat`, до обновления до 3.0.0: пользователь удаляет свою задачу или ярлык с `run_production.bat`, администратор ставит `FilePickerAPI-<филиал>.msi`. Вместо `run_test.bat` — запуск `FilePickerAPI.exe` без аргументов из консоли. Вместо `%LOCALAPPDATA%\FilePickerAPI\startup.log` — `%LOCALAPPDATA%\FilePickerAPI\logs\FilePickerAPI.log` и журнал событий Application (источник `FilePickerAPI`).
