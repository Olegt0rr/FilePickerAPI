Веб-сервер на базе FastAPI для просмотра списка и загрузки файлов из настроенной директории.

## Возможности

- 🚀 Быстрый и легковесный API на базе FastAPI
- 📁 Просмотр списка файлов из настроенной директории
- ⬇️ Загрузка отдельных файлов
- 🔒 Безопасность: защита от атак обхода директорий
- 🌐 CORS включен для интеграции с фронтендом
- 🪟 Автоматическая сборка Windows исполняемого файла через GitHub Actions

## API Endpoints

### `GET /files`
Получить список всех файлов в настроенной директории, отфильтрованных по размеру и формату.

Только файлы формата .txt возвращаются в ответе. Файлы разделяются на две категории:
- **availableFiles** - файлы формата .txt размером меньше 10 МБ (доступные для импорта)
- **unavailableFiles** - файлы формата .txt размером 10 МБ и больше (не доступные для импорта)

Файлы других форматов полностью игнорируются и не возвращаются в ответе.

Файлы в каждом списке отсортированы по `createdAt` в порядке убывания (новые файлы первыми). `createdAt` — время создания файла; на Linux, где ОС его не отдаёт, — время последнего изменения.

**Ответ:**
```json
{
  "availableFiles": [
    {
      "id": "example.txt",
      "name": "example.txt",
      "size": 1024,
      "createdAt": "2025-12-15T10:30:29.150000Z"
    }
  ],
  "unavailableFiles": [
    {
      "id": "large_file.txt",
      "name": "large_file.txt",
      "size": 15728640,
      "createdAt": "2025-12-15T10:30:29.100000Z"
    }
  ]
}
```

**Ошибки:**

| Код | `detail` | Когда |
|---|---|---|
| 404 | `Files directory not found` | директории нет или сетевая папка недоступна («сетевой путь не найден») |
| 400 | `Files path is not a directory` | настроенный путь указывает на файл |
| 403 | `Permission denied when reading directory: <текст ошибки>` | у учётной записи сервиса нет прав на чтение |
| 500 | `OS error when reading directory: <текст ошибки>` | прочие ошибки ввода-вывода (сбой сети, диска) |
| 500 | `Unexpected error when reading directory: <текст ошибки>` | любая другая ошибка |

Текст ошибки ОС с путём к папке попадает в `detail` намеренно, для диагностики: клиент здесь ничего не передаёт и не может так исследовать файловую систему.

### `GET /files/{fileId}`
Скачать определенный файл по его ID.

**Параметры:**
- `fileId` - ID файла для загрузки (имя файла)

**Ответ:** Загрузка файла (application/octet-stream)

**Ошибки:**

| Код | `detail` | Когда |
|---|---|---|
| 400 | `Invalid filename` | `fileId` — не имя файла (путь, UNC-путь, `..`, имя устройства Windows и т.п.), ОС отвергает имя, файл — символическая ссылка на Windows или лежит не прямо в директории |
| 400 | `Path is not a file` | `fileId` указывает на директорию |
| 403 | `File is not available for download` | файл не `.txt` или не меньше 10 МиБ |
| 403 | `Permission denied when reading file` | нет прав на файл |
| 404 | `File not found` | файла нет или сетевая папка недоступна |
| 500 | `OS error when reading file` | прочие ошибки ввода-вывода, в том числе сбой самой директории |

Здесь текст ошибки ОС клиенту не отдаётся (в нём путь к сетевой папке), он пишется в лог сервиса.

## Установка

### Запуск из исходного кода

1. Клонируйте репозиторий:
```bash
git clone https://github.com/Olegt0rr/FilePickerAPI.git
cd FilePickerAPI
```

2. Установите зависимости:
```bash
pip install -e .
```

3. Запустите приложение:
```bash
python -m app
```

API будет доступен по адресу `http://localhost:8000`

**💡 Совет:** Откройте `http://localhost:8000/docs` в браузере для доступа к интерактивной документации Swagger UI

### Использование Windows исполняемого файла

1. Скачайте из [Releases](../../releases/latest) архив своего филиала `FilePickerAPI-<код филиала>.zip`
2. Распакуйте архив в папку, куда у пользователей нет прав на запись (например, `C:\Program Files\FilePickerAPI`)
3. Запустите `run_production.bat` или `run_test.bat` из этой папки

Путь к директории с файлами зашит в сборку филиала (см. [Сборка под филиалы](#сборка-под-филиалы)).

Также можно скачать артефакты из последних [GitHub Actions workflow runs](../../actions)

#### Скрипты запуска

- **`run_test.bat`** — запускает сервис в текущем окне консоли, ошибки запуска видны сразу. Используйте его, чтобы разобраться, почему сервис не стартует.
- **`run_production.bat`** — запускает сервис в свёрнутом окне в фоне и проверяет, что он действительно отвечает. Подходит для ручного запуска и для Планировщика заданий, работает и из сетевой папки (UNC-путь).

После запуска `run_production.bat` до 30 раз с паузой 2 секунды опрашивает `http://127.0.0.1:8000/openapi.json` (если сервис так и не ответил, ожидание занимает 1–2 минуты) и дописывает итог в `%LOCALAPPDATA%\FilePickerAPI\startup.log`:
- `FilePickerAPI started in daemon mode at <дата> <время>` — сервис ответил, код выхода 0;
- `FilePickerAPI FAILED to start at <дата> <время>: <причина>` — сервис не запустился, код выхода 1. Причины: exe завершился при старте (например, из-за `FILES_DIRECTORY` в `.env`, см. «Директория с файлами», или потому что порт 8000 занят программой, которая не отвечает по HTTP), порт 8000 уже отвечает по HTTP (например, уже работающий экземпляр — второй не запускается), `FilePickerAPI.exe` уже запущен, но ещё не отвечает (остановите его в диспетчере задач или дождитесь ответа), Windows не дал запустить exe (например, его блокирует AppLocker), сервис не ответил за время ожидания (процесс при этом не останавливается, и пока его не завершить, следующий запуск будет сообщать, что exe уже запущен), рядом нет `FilePickerAPI.exe` или в системе нет `curl.exe`.

В Планировщике заданий результат виден в столбце «Результат последнего запуска»: `0x0` — сервис запущен, `0x1` — ошибка, причина в `startup.log`. Журнал пишется в профиль учётной записи, от имени которой выполняется задание: для задания от имени SYSTEM это `C:\Windows\System32\config\systemprofile\AppData\Local\FilePickerAPI\startup.log`, а не `%LOCALAPPDATA%` администратора. При ошибке скрипт не ждёт нажатия клавиши: окно закрывается само через 30 секунд.

Для проверки запуска нужен системный `curl.exe` (Windows 10 версии 1803 и новее, Windows Server 2019 и новее). Скрипты не принимают параметров и не меняют директорию с файлами.

## Конфигурация

### Директория с файлами

Директория с файлами **зашивается в сборку** и не настраивается пользователем. Для каждого филиала собирается своя сборка со своим путём (см. [Сборка под филиалы](#сборка-под-филиалы)). При запуске из исходного кода, без шага `configure`, приложение обслуживает файлы из директории `./files`.

**Требование:** пользователь не должен иметь возможности подменить директорию, из которой API отдаёт файлы. Поэтому:

- путь объявлен как `ClassVar`, а не как поле настроек, и не читается из переменных окружения;
- переменная окружения `FILES_DIRECTORY` игнорируется;
- если в `.env` указан `FILES_DIRECTORY`, приложение не запускается (ошибка валидации), а не переключается на другую директорию.

Это поведение закреплено тестами (`TestFilesDirectoryIsFixed`). Изменить директорию можно только правкой `branches.toml` и новой сборкой (см. `openspec/specs/service-configuration/spec.md`).

### Сборка под филиалы

Список филиалов и их путей хранится в [`branches.toml`](branches.toml):

```toml
[[branch]]
name = "5400"
files_directory = '\\localmq.neadru.local\Payments\5400\CENTER\RSB'
```

CI собирает отдельную сборку под каждый филиал из этого файла из одной и той же кодовой базы. Чтобы добавить филиал, допишите новый блок `[[branch]]` и сделайте коммит. Строку пути пишите в одинарных кавычках: тогда обратные слэши указываются как есть, без экранирования. Путь должен быть абсолютным (UNC `\\сервер\...` или с буквой диска), а коды филиалов — уникальными без учёта регистра; иначе CI не запустит сборку. Для сетевой папки указывайте только UNC-путь: буква подключённого сетевого диска (`Z:\...`) существует лишь в сеансе пользователя, который его подключил, и не видна задаче Планировщика (см. [Работа с сетевой папкой](#работа-с-сетевой-папкой)). Букву диска используйте только для локального диска.

Перед сборкой `scripts/branches.py configure <код филиала>` записывает путь в `app/_build_config.py` (файл не хранится в git), и Nuitka компилирует его в exe.

### Работа с сетевой папкой

В филиалах сервис отдаёт файлы из сетевой папки по UNC-пути (`\\сервер\ресурс\...`). Что нужно учитывать при установке и эксплуатации:

**Учётная запись и права.** К сетевой папке сервис обращается от имени учётной записи, под которой запущен `FilePickerAPI.exe`, и ей нужно право на чтение ресурса и папки. Если сервис запускается задачей Планировщика от имени SYSTEM, в сеть он ходит как учётная запись компьютера (`ДОМЕН\ИМЯ_КОМПЬЮТЕРА$`): права на ресурс нужно выдать ей (или группе компьютеров), а не пользователю. Без прав `GET /files` отвечает 403.

**Только UNC-путь.** Подключённый сетевой диск (`Z:`) виден только в сеансе пользователя, который его подключил; задача Планировщика и другие сеансы его не видят, и сервис ответит 404. Поэтому в `branches.toml` для сетевой папки указывается UNC-путь.

**Создание папки при запуске.** При старте сервис создаёт обслуживаемую директорию вместе с недостающими родительскими, если у учётной записи есть права на запись. При опечатке в пути на ресурсе появится пустая папка, а список файлов будет пустым — проверяйте путь в `branches.toml`. Если создать папку не удалось (ресурс недоступен, нет прав), сервис всё равно запускается и пишет предупреждение в консоль.

**Недоступная папка.** Пока сетевая папка недоступна, `GET /files` отвечает 404 (`Files directory not found`), 403 или 500, а скачивание — 404 или 500 (см. коды ошибок в [API Endpoints](#api-endpoints)). Когда папка снова становится доступна, сервис работает дальше без перезапуска. Если папка пропала, пока сервис читал список, ответ — 404, а не пустой список.

**DFS и число обращений.** На Windows сервис обращается к файлу прямо по UNC-пути из сборки и не разрешает путь сам: скачивание делает два обращения к сетевой папке — за атрибутами файла и за его настоящим именем (плюс чтение содержимого), а переключение DFS на другой сервер обрабатывает SMB-клиент Windows.

**Зависшая папка.** У обращений к сетевой папке нет собственного таймаута: их длительность определяет SMB-клиент Windows. Запросы выполняются в пуле потоков (по умолчанию 40 потоков), поэтому медленная папка не блокирует остальные запросы, но если папка «повисла» и все потоки ждут её ответа, сервис перестаёт отвечать, пока Windows не прервёт обращения.

**Безопасность.** Ни запрос, ни символическая ссылка в папке не заставят сервис подключиться к чужому хосту — только к серверам, через которые Windows обслуживает саму настроенную папку (сервер ресурса, цели DFS): `fileId` проверяется до любого обращения к файловой системе, а символическим ссылкам на Windows сервис не следует. Иначе ссылка или `fileId` вида `\\host\share\x.txt` заставили бы сервис подключиться к чужому хосту и отдать ему NTLM-хеш своей учётной записи (см. [Безопасность](#безопасность)). Остаётся узкое окно: если файл подменят ссылкой между проверкой и открытием, ОС при открытии пойдёт по ссылке; для этого нужно право записи в папку.

**Дата создания.** `createdAt` для файла в сетевой папке — время создания, которое отдаёт файловый сервер: время появления файла на ресурсе или время, сохранённое при копировании (например, robocopy), а не время на машине сервиса.

### CORS Origins

По умолчанию CORS включен для всех источников (`*`). Для производственного использования следует ограничить это определенными доменами, установив переменную окружения `CORS_ORIGINS` со списком источников через запятую:

**Linux/Mac:**
```bash
export CORS_ORIGINS="http://localhost:3000,https://yourdomain.com"
python -m app
```

**Windows:**
```cmd
set CORS_ORIGINS=http://localhost:3000,https://yourdomain.com
FilePickerAPI.exe
```

Передача учётных данных (куки, HTTP-аутентификация) разрешается только для явного списка источников. При `*` ответ содержит `Access-Control-Allow-Origin: *` без `Access-Control-Allow-Credentials`.

## Разработка

```bash

# Запустите проверки линтера
```

Вся конфигурация управляется через `pyproject.toml`:
- Зависимости и dev-зависимости
- Конфигурация pytest с настройками покрытия
- Конфигурация линтера ruff с правилом "ALL"

Набор тестов покрывает:
- Все конечные точки API (список файлов, загрузка файла)
- Функции безопасности (защита от обхода директорий)
- Конфигурацию CORS
- Обработку исключений (ошибки доступа, исключения безопасности)
- Обработку ошибок и граничные случаи
- Блок выполнения main
- Метаданные файлов, сортировку и специальные символы

### Спецификации (OpenSpec)

Поведение сервиса описано в формате [OpenSpec](https://github.com/Fission-AI/OpenSpec) в директории `openspec/`:
- `openspec/config.yaml` — контекст проекта (стек, соглашения, проверки) для AI-ассистентов
- `openspec/specs/` — текущие требования по возможностям: `file-listing`, `file-download`, `service-configuration`, `api-documentation`, `distribution`
- `openspec/changes/` — предложения изменений, которые ещё не внесены в спецификации

Изменения поведения начинаются с предложения (`/opsx:propose` в Claude Code или `openspec new change`), а после реализации архивируются (`openspec archive`), обновляя `openspec/specs/`.

```bash
npm install -g @fission-ai/openspec
openspec list --specs
openspec validate --all --strict
```

Ту же проверку (`--all`: спецификации и незаархивированные изменения) выполняет CI в workflow Docs.

### Локальная сборка исполняемого файла

Сборка выполняется [Nuitka](https://nuitka.net/): код компилируется в C, а затем в нативный бинарник. Нужен компилятор C (на Windows — MSVC из Visual Studio Build Tools).

```powershell
pip install -e .[build]
# Зашить путь нужного филиала из branches.toml (создаёт app/_build_config.py)
python scripts/branches.py configure 5400
python -m nuitka --mode=standalone --msvc=latest --assume-yes-for-downloads --remove-output `
  --output-dir=build --output-folder-name=FilePickerAPI `
  --output-filename=FilePickerAPI.exe `
  --include-package=app --include-module=app._build_config `
  --include-package=uvicorn `
  app/__main__.py
```

Результат — папка `build/FilePickerAPI.dist/` с `FilePickerAPI.exe` и его зависимостями. Используется режим standalone (папка), а не onefile: onefile при запуске распаковывает неподписанные файлы во временную папку пользователя, что несовместимо с подписью и WDAC/AppLocker.

### Подпись кода

Бинарники подписываются только при релизе, в отдельном джобе `sign` воркфлоу `release.yml`. Подписываются все `exe`/`dll`/`pyd` сборки сертификатом Authenticode; уже подписанные сторонние файлы (например, `python311.dll`) не трогаются. Обычные сборки из push и PR остаются неподписанными.

Сертификат хранится в секретах GitHub Environment `code-signing` (не в секретах репозитория):

- `WINDOWS_SIGNING_CERT_PFX_BASE64` — PFX-файл сертификата подписи кода в base64 (`[Convert]::ToBase64String([IO.File]::ReadAllBytes("cert.pfx"))`)
- `WINDOWS_SIGNING_CERT_PASSWORD` — пароль от PFX

Настройка окружения (Settings → Environments → `code-signing`):

1. **Deployment branches and tags** → *Selected branches and tags* → добавить правило для тегов `v*`. Без этого любая ветка или PR с изменённым воркфлоу сможет получить сертификат и подписать произвольный код.
2. Создавать теги `v*` должны только доверенные люди: Settings → Rules → Rulesets, правило для тегов `v*` с ограничением на создание.
3. По желанию — *Required reviewers*: подпись релиза потребует ручного подтверждения.

Без секретов в окружении релиз падает: неподписанный релиз не публикуется.

Подпись сама по себе не мешает запустить изменённый файл: она только позволяет это обнаружить. Чтобы подменённый или пропатченный бинарник не запускался, на рабочих местах нужно включить WDAC или AppLocker с правилом «разрешить только файлы, подписанные нашим сертификатом» (через доменную GPO), а пользователи не должны быть локальными администраторами. В политике также нужно разрешить издателей Microsoft и Python Software Foundation: их подписи остаются на `vcruntime*.dll`, `python311.dll` и других сторонних файлах сборки. Bat-файлы подписать нельзя, поэтому если в AppLocker включены правила для скриптов, разрешите `run_*.bat` правилом по пути к папке установки.

## GitHub Actions

Репозиторий включает несколько workflow GitHub Actions:

### Build and Test (`.github/workflows/build-exe.yml`)

Автоматически:
- Запускает набор тестов на Ubuntu и на Windows (на Windows — в том числе проверки UNC-путей, недопустимых имён файлов и символических ссылок)
- Собирает Windows-версию через Nuitka отдельно под каждый филиал из `branches.toml` (только если тесты прошли)
- Загружает отчеты о покрытии тестами
- Загружает папку сборки каждого филиала как артефакт `FilePickerAPI-<код филиала>`
- Проверяет скрипт подписи (`.github/scripts/sign.ps1`) на этих сборках с одноразовым самоподписанным сертификатом — боевой сертификат здесь не используется

Триггеры workflow:
- Push в ветку main/master (кроме изменений только в документации)
- Pull request в ветку main/master (кроме изменений только в документации)
- Ручной запуск workflow

Если в push или PR изменена только документация (`*.md`, `openspec/`, `.claude/`, `.github/openspec/`), workflow не запускается: код и сборка от неё не меняются. Если вместе с ней изменён любой другой файл, workflow запускается целиком. Так же устроен Dependency Audit, а вместо них запускается лёгкая проверка Docs.

Артефакты:
- Сборка для Windows: хранится 30 дней
- Отчет о покрытии: хранится 7 дней

### Dependency Audit (`.github/workflows/audit.yml`)

Проверяет зависимости на известные уязвимости через [pip-audit](https://github.com/pypa/pip-audit):
- Ставит проект со всеми extras (`dev`, `build`, `audit`) на Windows, как для сборки, и проверяет каждый установленный пакет по базе PyPI Advisory
- Падает, если у какого-либо пакета есть известная уязвимость или пакет не удалось проверить; в логе — идентификаторы (CVE, GHSA) и версии с исправлением
- Вызывается из Release: релиз с известной уязвимостью не подписывается и не публикуется

Триггеры workflow:
- Push в ветку main/master (кроме изменений только в документации)
- Pull request в ветку main/master (кроме изменений только в документации)
- Ежедневно по расписанию (новые CVE выходят без коммитов в репозиторий)
- Ручной запуск workflow

Если проверка упала, обновите уязвимый пакет в `pyproject.toml` (транзитивную зависимость закрепите явно, как `starlette`). Пропускать уязвимость через `--ignore-vuln` можно только с комментарием-причиной в workflow.

### Docs (`.github/workflows/docs.yml`)

Лёгкая проверка для изменений документации: на Ubuntu, без зависимостей проекта и сборки, проверяет спецификации и незаархивированные изменения OpenSpec командой `openspec validate --all --strict`. Версии Node и openspec закреплены: openspec со всеми зависимостями — в `.github/openspec/package-lock.json`, его обновляет Dependabot. Списки путей в трёх workflow сверяет тест `tests/test_workflows.py`.

Триггеры workflow:
- Push и pull request в ветку main/master, если изменены `*.md`, `openspec/`, `.claude/`, `.github/openspec/` или сам `docs.yml`
- Ручной запуск workflow

### Release (`.github/workflows/release.yml`)

Автоматически создаёт релизы с собранными артефактами:
- Срабатывает при создании тега версии (формат: `vX.Y.Z` из цифр, например `v2.3.0`)
- Собирает Windows-версии всех филиалов и подписывает их в окружении `code-signing` (без сертификата или при известной уязвимости в зависимостях релиз падает)
- Создаёт GitHub Release с описанием и прикрепляет к нему архив `FilePickerAPI-<код филиала>.zip` для каждого филиала

**Создание нового релиза:**

Версия проекта хранится только в git-теге: `pyproject.toml`, `/docs` и свойства exe получают её автоматически через [setuptools-scm](https://setuptools-scm.readthedocs.io/). Поднимать версию в файлах не нужно — достаточно создать тег:

```bash
git tag v2.3.0
git push origin v2.3.0
```

Сборки между релизами получают версию вида `2.3.1.dev4+g1a2b3c4` (следующий патч, число коммитов после тега и хэш коммита).

Релиз запускают только теги вида `vX.Y.Z` из цифр; теги вроде `v2.3.0-rc1` релиз не создают.

При локальной разработке версия фиксируется в момент `pip install -e .`; чтобы `/docs` показал новую версию после коммитов или тега, выполните установку повторно.

После отправки тега workflow автоматически:
1. Соберёт и подпишет Windows-версии всех филиалов из `branches.toml`
2. Создаст GitHub Release с именем тега (например, `v2.3.0`)
3. Прикрепит к релизу архивы `FilePickerAPI-<код филиала>.zip`

Релиз создаётся после сборки и подписи: сначала черновиком, к которому прикладываются архивы, затем публикуется.

Через интерфейс GitHub отдельный тег не создать, поэтому можно выпустить версию и там: Releases → Draft a new release → Choose a tag → ввести `v2.3.0`, Target: `main` → Create new tag → Publish release. Второго релиза workflow не создаёт: он прикладывает архивы к уже опубликованному релизу. Только до конца сборки (около 15 минут) релиз висит без архивов.

У выпуска через интерфейс есть ограничения, потому что релиз публикуется до сборки:
- Если сборка или подпись упала (например, нет сертификата), опубликованный релиз остаётся без архивов. Удалите его и тег вручную, исправьте причину и выпустите версию заново.
- Тег должен быть вида `vX.Y.Z` из цифр. Для тега вроде `v2.3.0-rc1` workflow не запускается, и опубликованный релиз так и останется без архивов.
- Если в настройках репозитория включены неизменяемые релизы (immutable releases), к опубликованному релизу архивы не приложить: выпускайте версию тегом из терминала.

Описание релиза в обоих случаях формирует workflow: сначала текст про установку и конфигурацию, ниже — автоматический список изменений GitHub с предыдущего релиза. Текст, вписанный при создании релиза через интерфейс, заменяется.

Пользователи смогут скачать архив своего филиала со страницы [Releases](../../releases)

## Безопасность

- `fileId` должен быть просто именем файла, и это проверяется до любого обращения к файловой системе: путь, UNC-путь, `..`, а на Windows двоеточие, символы `*?"<>|`, точка или пробел в конце имени и имена устройств (`CON`, `NUL`, `nul.txt`, `COM0`–`COM9`, `LPT0`–`LPT9` и т.п.) отклоняются с 400. Иначе на Windows `fileId` вида `\\host\share\x.txt` заставил бы сервис подключиться к чужому хосту и отдать ему NTLM-хеш своей учётной записи. Кроме того, Windows находит файл без учёта регистра и по короткому имени 8.3 (`REPORT~1.TXT` для `report.txtx`), поэтому проверка расширения и имя в ответе берутся из настоящего имени файла в папке, а не из `fileId`
- Отдаются только файлы, лежащие непосредственно в директории; символическая ссылка не может увести в поддиректорию или наружу. На Windows сервис символическим ссылкам не следует вовсе: в списке их нет, при скачивании — 400, а к цели ссылки (например, `\\host\share`) сервис не обращается
- Ошибки ОС при скачивании не раскрывают клиенту путь к сетевой папке: подробности пишутся в лог
- Только файлы (не директории) могут быть загружены
- Директория с файлами зашита в исполняемый файл при сборке и не может быть подменена пользователем: переменная окружения `FILES_DIRECTORY` игнорируется, а с `FILES_DIRECTORY` в `.env` приложение не запускается. Изменить путь филиала можно только через `branches.toml` и новую сборку
- CORS origins можно настроить через переменную окружения для производственного использования (по умолчанию разрешает все источники для разработки)
