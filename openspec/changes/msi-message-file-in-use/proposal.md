# Proposal

## Why

Служба журнала событий (`EventLog`) загружает файл сообщений `FilePickerAPI.messages.dll`, когда форматирует тексты событий (Event Viewer, `Get-WinEvent`), и держит его открытым. MSI новой версии заменяет этот файл по версии, поэтому Restart Manager считает его занятым и останавливает, а затем перезапускает `EventLog` и зависимые от неё службы. Так было в CI: в прогоне 43041542707 (шаг 6 дымовой проверки, `upgrade-2`) Restart Manager перезапустил `EventLog`, `MSMQ` и `NetMsmqActivator`, и PID этих служб сменились. Вероятно, из-за этого в прогоне 43027367514 завис раннер. В филиале то же самое: обновление перезапускает системную службу журнала, а это затрагивает чужие службы и может прервать установку.

## What Changes

- Файл сообщений ставится под именем с версией продукта: `FilePickerAPI.messages.<X.Y.Z>.dll`. Каждая версия добавляет свой файл и не заменяет файл, который может держать `EventLog`. Файлы сообщений по-прежнему постоянные: удаление продукта и установка другой версии их не трогают.
- Источник событий `FilePickerAPI` регистрируется с `EventMessageFile` на файл своей версии, только если зарегистрированный файл не новее. При откате (удаление и установка старого MSI) регистрация остаётся на новейшем файле, и тексты прошлых событий читаются полностью, как и раньше.
- Мягкая остановка работающего экземпляра через Restart Manager при обновлении не меняется: exe по-прежнему заменяется в той же папке.
- Дымовая проверка MSI на шаге 6 проверяет, что Restart Manager не включил `EventLog` в список занятых файлов, а PID службы `EventLog` не изменился. Проверки регистрации, отката и удаления сверяют файл сообщений с версией в имени.
- Сборка MSI проверяет, что версия DLL сообщений совпадает с версией пакета: от этого зависят имя файла и выбор новейшего.

Контракт HTTP API не меняется: поля, коды ответов и тексты `detail` прежние. Способов задать директорию с файлами при запуске не появляется. Тексты и коды событий не меняются.

Вне рамок изменения:
- Удаление старых файлов сообщений: они маленькие, а удаление занятого файла снова привлекло бы Restart Manager к `EventLog`.
- Машины, где уже стоит MSI с `FilePickerAPI.messages.dll` без версии в имени. До релиза MSI таких машин нет (пакет пока собирается только для проверки в CI). Если они появятся, первое обновление перерегистрирует источник на новый файл, а старый файл останется на месте и не будет заменяться.
- Остальное поведение MSI и сервиса из `user-logon-autostart`.

### Modified Capabilities
- `user-logon-autostart`: «Обновление и откат MSI» — обновление не перезапускает службу журнала событий, при откате регистрация источника остаётся на новейшем файле сообщений. «Удаление MSI» — остаются все установленные файлы сообщений. Дельта написана поверх требований изменения `user-logon-autostart` в том виде, какой они получат после его архивации.

## Impact

- `installer/FilePickerAPI.wxs`: имя файла сообщений с версией, поиск зарегистрированного файла сообщений по версии (`RegistrySearch` с `FileSearch`), условие компонента источника событий.
- `tests/test_installer.py`: проверки имени файла, поиска и условия.
- `.github/scripts/msi-smoke.ps1`: шаг 6 — нет `EventLog` в списке занятых файлов, PID службы не меняется; сверка файлов сообщений по имени с версией.
- `.github/scripts/build-msi.ps1`: сверка файлов пакета с папкой сборки с учётом нового имени и проверка версии DLL сообщений.
- `openspec/changes/user-logon-autostart/design.md`: строки «Источник событий» и «Файл сообщений» в таблице «Содержимое MSI» и раздел «Откат» ссылаются на это изменение.
- Зависимость: применяется до архивации `user-logon-autostart` или вместе с ней.
