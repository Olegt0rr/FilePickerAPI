# distribution Specification

## Purpose
Поставка и запуск сервиса на Windows: сборка Nuitka с bat-скриптами, подпись бинарников и автоматические релизы на GitHub с версией из git-тега.

## Requirements

### Requirement: Сборка для Windows
Проект SHALL собираться через Nuitka в режиме standalone: папка `FilePickerAPI` с `FilePickerAPI.exe`, его зависимостями и bat-скриптами, которая запускается без установленного Python. Режим onefile MUST NOT использоваться: он распаковывает неподписанные файлы во временную папку пользователя, что несовместимо с подписью и WDAC/AppLocker. Сборка SHALL выполняться в CI только после успешного прохождения линтера и тестов.

#### Scenario: Сборка в CI
- **WHEN** в ветку `main`/`master` отправлен коммит или открыт pull request в одну из этих веток
- **THEN** CI запускает ruff и pytest на Linux и, если они прошли, собирает папку `FilePickerAPI` на Windows и публикует её как артефакт `FilePickerAPI-Windows`

#### Scenario: Тесты упали
- **WHEN** линтер или тесты завершились с ошибкой
- **THEN** сборка не выполняется

### Requirement: Версия из git-тега
Версия проекта SHALL браться только из git-тега (`v2.3.0` → `2.3.0`) и попадать в метаданные пакета, в OpenAPI-схему и в свойства `FilePickerAPI.exe`. Версию MUST NOT поднимать вручную в файлах. Сборки между релизами получают версию вида `2.3.1.dev4+g1a2b3c4`.

#### Scenario: Сборка по тегу
- **WHEN** CI собирает проект по тегу `v2.3.0`
- **THEN** версия сборки — `2.3.0`; если вычисленная версия не совпадает с тегом, сборка падает

#### Scenario: Сборка между релизами
- **WHEN** CI собирает коммит через 4 коммита после тега `v2.3.0`
- **THEN** версия сборки — `2.3.1.dev4+g<хэш>`, а версия в свойствах exe — `2.3.1`

### Requirement: Подпись релизных бинарников
Все неподписанные `exe`/`dll`/`pyd` релизной сборки SHALL подписываться сертификатом Authenticode с меткой времени. Файлы с действительной чужой подписью (например, `python311.dll`) SHALL оставаться как есть, а файл с недействительной подписью MUST останавливать релиз. Сертификат MUST быть доступен только релизным тегам (окружение `code-signing`); без него релиз MUST NOT публиковаться.

#### Scenario: Релиз без сертификата
- **WHEN** секреты сертификата в окружении `code-signing` не заданы
- **THEN** джоб подписи падает, и релиз не создаётся

#### Scenario: Проверка подписи в pull request
- **WHEN** открыт pull request в `main`/`master`
- **THEN** CI подписывает сборку одноразовым самоподписанным сертификатом тем же скриптом, что и в релизе, не получая доступа к боевому сертификату

### Requirement: Скрипты запуска для Windows
В папке сборки SHALL поставляться два скрипта:
- `run_test.bat` — запускает `FilePickerAPI.exe` в текущем окне консоли с видимым выводом для отладки;
- `run_production.bat` — запускает `FilePickerAPI.exe` в свёрнутом окне в фоне и дописывает время запуска в журнал пользователя.

Оба скрипта SHALL работать из своей папки независимо от рабочей директории вызывающего и MUST завершаться с сообщением об ошибке, если рядом с ними нет `FilePickerAPI.exe`.

#### Scenario: Запуск в фоновом режиме
- **WHEN** пользователь запускает `run_production.bat` в папке сборки
- **THEN** сервис стартует в свёрнутом окне, а в `%LOCALAPPDATA%\FilePickerAPI\startup.log` добавляется строка с датой и временем запуска (журнал лежит в профиле пользователя, потому что в папку установки у пользователей нет прав на запись)

#### Scenario: Запуск из Планировщика заданий
- **WHEN** `run_production.bat` запускается Планировщиком заданий Windows с другой рабочей директорией
- **THEN** скрипт находит `FilePickerAPI.exe` рядом с собой и запускает его с папкой сборки в качестве рабочей

#### Scenario: Скрипты в сетевой папке
- **WHEN** папка сборки лежит в сетевой папке (UNC-путь), и пользователь запускает скрипт
- **THEN** скрипт переходит в свою папку через `pushd`, а `run_production.bat` запускает exe по исходному UNC-пути, чтобы `popd` в конце не отключил временный диск из-под работающего приложения

#### Scenario: Исполняемый файл отсутствует
- **WHEN** пользователь запускает любой из bat-скриптов в папке без `FilePickerAPI.exe`
- **THEN** скрипт выводит `Error: FilePickerAPI.exe not found!` и не запускает сервис

#### Scenario: Скрипты не задают директорию
- **WHEN** пользователь запускает любой из bat-скриптов
- **THEN** скрипт не передаёт приложению путь к директории с файлами, и сервис работает с директорией, зашитой при сборке (см. `service-configuration`)

### Requirement: Автоматический релиз
При публикации тега вида `vX.Y.Z` из цифр SHALL создаваться GitHub Release, к которому прикреплён архив `FilePickerAPI-Windows.zip` с подписанной папкой сборки, собранной из этого тега после успешного прохождения тестов. Теги с суффиксом (например, `v2.3.0-rc1`) MUST NOT создавать релиз.

#### Scenario: Публикация тега
- **WHEN** в репозиторий отправлен тег `v2.3.0`
- **THEN** создаётся релиз `v2.3.0` с архивом `FilePickerAPI-Windows.zip`, внутри которого папка `FilePickerAPI` с подписанным `FilePickerAPI.exe`, `run_test.bat` и `run_production.bat`

#### Scenario: Предварительная версия
- **WHEN** в репозиторий отправлен тег `v2.3.0-rc1`
- **THEN** релиз не создаётся
