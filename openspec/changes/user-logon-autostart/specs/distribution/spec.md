## MODIFIED Requirements

### Requirement: Сборка для Windows
Проект SHALL собираться через Nuitka в режиме standalone: папка `FilePickerAPI` с `FilePickerAPI.exe`, его зависимостями (включая модули pywin32 и файл сообщений, см. `user-logon-autostart`) и bat-скриптами, которая запускается без установленного Python. Под каждый филиал из `branches.toml` SHALL собираться своя папка. Режим onefile MUST NOT использоваться: он распаковывает неподписанные файлы во временную папку пользователя, что несовместимо с подписью и WDAC/AppLocker. Сборка SHALL выполняться в CI только после успешного прохождения линтера и тестов, и каждая собранная папка SHALL проверяться в CI раскладкой и запуском на Windows.

#### Scenario: Сборка в CI
- **WHEN** в ветку `main`/`master` отправлен коммит или открыт pull request в одну из этих веток
- **THEN** CI запускает ruff и pytest на Linux и pytest на Windows. Если они прошли, CI собирает папку `FilePickerAPI` на Windows для каждого филиала из `branches.toml`, проверяет её дымовой проверкой и публикует как артефакт `FilePickerAPI-<филиал>` (например, `FilePickerAPI-5400`)

#### Scenario: Тесты упали
- **WHEN** линтер или тесты завершились с ошибкой
- **THEN** сборка не выполняется

#### Scenario: Путь филиала в сборке
- **WHEN** CI собирает папку филиала 5400
- **THEN** перед компиляцией CI сверяет записанный путь с `files_directory` филиала 5400 в `branches.toml`, и при расхождении сборка падает; сборки филиалов отличаются только зашитой директорией с файлами

#### Scenario: Ошибка в списке филиалов
- **WHEN** `branches.toml` не проходит проверку (см. «Список филиалов»)
- **THEN** джоб с тестами падает с сообщением о причине, и ни одна сборка не выполняется

#### Scenario: Дымовая проверка раскладки и запуска при входе
- **WHEN** CI собрал папку филиала на Windows-раннере
- **THEN** CI проверяет по порядку:
  - `FilePickerAPI.exe deploy` из копии сборки в папке, доступной на запись только администраторам, завершается с кодом 0, копирует сборку в `C:\Program Files\FilePickerAPI\<версия>\` и регистрирует источник `FilePickerAPI`;
  - `install` из папки версии завершается с кодом 0, задача Планировщика пользователя создана с триггером входа, типом входа «только при входе пользователя», без повышения прав и с путём к exe без аргументов;
  - `GET /openapi.json` отдаёт версию сборки, `GET /files` отвечает 404 `Files directory not found`;
  - в файле журнала пользователя и в журнале событий есть событие запуска, после остановки — событие остановки;
  - повторный `install` завершается с кодом 0 и перезапускает сервис в новом процессе;
  - `install` не из папки версии и повторный `deploy` той же версии при работающем экземпляре завершаются с кодом 1 без изменений;
  - после `deploy` в `C:\Program Files\FilePickerAPI` остаются только папки текущей версии и версии для отката;
  - с `.env`, где указан `FILES_DIRECTORY`, сервис не запускается, а `install` завершается с кодом 1;
  - `remove` завершается с кодом 0, задачи и процесса не остаётся;
  - раскладка из папки, доступной пользователям на запись, отклоняется.

  При любой неудаче сборка падает, и артефакт не публикуется

#### Scenario: Проверка событий в журнале событий
- **WHEN** дымовая проверка прошла сценарии запуска, недоступной папки филиала (при создании директории и при `GET /files`), остановки и отказа запуска из-за `.env`
- **THEN** CI читает события источника `FilePickerAPI` через `Get-WinEvent` (тот же текст, что показывает Event Viewer) и проверяет коды 1000, 2004, 2000, 1001 и 1002, их уровни, полный текст и кириллицу без искажений, а через `wevtutil qe /f:text` — что нет «Не найдено описание для события»; при расхождении сборка падает

#### Scenario: Bat-скрипты работают с новой сборкой
- **WHEN** пользователь филиала, который ещё не переведён на запуск при входе, обновляет папку сборки и запускает `run_production.bat` или `run_test.bat`
- **THEN** exe без аргументов запускает сервис как раньше, а `run_production.bat` пишет `started` в свой журнал
